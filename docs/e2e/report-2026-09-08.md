## Blocages rencontrés et résolutions

1. **`Dockerfile.rdna4` cassé par une étiquette de base flottante.** Le
   Dockerfile communautaire fixe `FROM rocm/dev-ubuntu-22.04:latest`. Cette
   étiquette a dérivé vers ROCm 10.0 depuis la rédaction du fichier
   (paquets renommés `amdrocm-*`), donc `apt-get install rocm-ml-libraries`
   échoue (`E: Unable to locate package`). Fix appliqué dans
   `deploy/docker-compose.tts.yml` : `build.dockerfile_inline` avec le
   contenu exact du `Dockerfile.rdna4` du commit épinglé, seule la ligne
   `FROM` changée vers `rocm/dev-ubuntu-22.04:7.2.3` (version que le
   fichier ciblait explicitement à sa rédaction). Une tentative
   intermédiaire via `build.additional_contexts` (mécanisme BuildKit
   normalement adapté à ce cas) a été acceptée par `docker compose config`
   mais est restée sans effet avec un `context` Git distant — non
   investigué plus loin, `dockerfile_inline` a résolu le problème.
2. **Contrat réel de `/v1/audio/speech` et `/v1/audio/voices` différent de
   ce qu'attend `OpenAICompatibleTtsProvider`** (voir
   `shared-context.md` "Requêtes inter-agents", flagué pour
   backend-engineer, non corrigé ici — hors périmètre ops) : `model` et
   `voice` sont obligatoires dans le corps (HTTP 422 sinon), et
   `/v1/audio/voices` renvoie `{ status, voices: string[] }` (noms de
   fichiers) et non des objets `{ id, name, language }`.

Aucune image ni volume Docker n'a été supprimé pendant cette investigation.

## Accent français : diagnostic et itérations de clonage vocal (CdC §55)

Retour utilisateur initial : accent anglophone perceptible sur la phrase FR
de référence. Diagnostic (3 itérations, cause confirmée) :

1. Le modèle chargé est bien `chatterbox-multilingual` (pas un modèle
   anglais) — écarté.
2. `language` **est** honoré par `/tts` (checksums différents avec/sans),
   mais **ignoré par `/v1/audio/speech`** (checksums identiques avec/sans
   `"language":"fr"`) — bug confirmé de l'endpoint OpenAI-compatible sur ce
   serveur, indépendant du réglage de la langue.
3. **Cause racine réelle** : les 28 voix prédéfinies (`Abigail`, `Adrian`,
   `Emily`, ...) sont toutes des échantillons anglophones ; Chatterbox clone
   le timbre *et l'accent* de la référence, quel que soit `language`. Aucune
   voix prédéfinie française dans ce serveur communautaire.

### Essais de clonage avec référence française

| Référence | Source | Paramètres | Latence | Résultat |
|---|---|---|---|---|

Les 3 WAV A/B/C ont été rejoués à la suite (`paplay`, annoncés "A"/"B"/"C")
pour comparaison à l'oreille par l'utilisateur — **cet agent n'a aucune
perception audio et ne peut pas juger lui-même la qualité perçue** ; seul le
retour utilisateur en direct fait foi sur le classement A/B/C. Les logs
serveur confirment `mode='clone'` et `Using reference audio for cloning:
fr-human-librivox.wav` pour les trois appels (pas de repli silencieux sur
une voix prédéfinie).

### Recommandation

**Le mode voix prédéfinie du serveur communautaire donne un accent anglais
en français ; le provider Chatterbox doit supporter `voice_mode: clone` avec
un échantillon français, et LLM Voice doit embarquer ou générer une
référence FR par défaut (Piper siwis) — point de revue pour la PR #28 et
exigence CdC §55.** Recommandation par défaut : une courte référence
publique (LibriVox, domaine public, à figer/héberger avec attribution) fait
mieux qu'une référence Piper synthétique (retour utilisateur), mais reste un
compromis — l'option prioritaire pour l'utilisateur final doit être
d'enregistrer **sa propre voix** (15 s, `pw-record`/`arecord`, consentement
explicite, `docs/install-linux.md` §6), avec la référence embarquée
(LibriVox ou Piper) comme repli seulement si l'utilisateur ne fournit rien.
Non implémenté dans le code produit ici (hors périmètre ops, S4.3) — flagué
dans `shared-context.md` "Requêtes inter-agents" pour backend-engineer.
