# Audit UI/UX — LLM Voice (2026-11-05)

**Commandité par** : plainte utilisateur réelle du 2026-11-05 ("je ne comprends rien de ce qui se passe […] je ne sais même pas, lorsque je fais un des trois choix, ce que ça change concrètement. Il n'y a rien qui change […] dans les profils que je vois plus bas, c'est la même chose […] aucune ne me parle.")
**Portée** : lecture de code source uniquement, sept surfaces listées par la mission. Aucune modification de fichier n'a été faite dans le cadre de cet audit.
**Méthode** : lecture ligne par ligne des fichiers listés ci-dessous (TypeScript + JS + CSS), pas seulement de leurs noms ou commentaires. Les citations sont des extraits réels du code, avec chemin et ligne quand c'est pertinent.

## 1. Panneau "Lecture en cours" (`playerHtml.ts` + `player.js` + `player.css`)

**Fichiers lus** :
- `vscode-extension/src/views/player/playerHtml.ts`
- `vscode-extension/media/player/player.js`
- `vscode-extension/media/player/player.css`

### Constat

L'état initial (`body data-state="idle"`) affiche :
```html
<p id="welcome-text">Aucune lecture en cours&hellip;</p>
<button id="btn-setup-voice">Choisir une voix</button>
<button id="btn-speak-current">Lire le document actuel</button>
```
Au-dessus, quand une lecture démarre, trois zones apparaissent : `#title-line` (titre + `#profile`), `#progress-line` (barre + `#time` initialisé à `00:00`), `#transport` (⏮ ▶ ⏭ ⏹).

Le `#profile` affiché dans `title-line` reçoit `state.profile` — c'est **le libellé du profil actif** (`player.js` ligne 139 : `profileEl.textContent = typeof state.profile === "string" ? state.profile : ""`), rien d'autre. Il n'y a **aucun indicateur visuel du provider TTS**, de la voix, ni d'un éventuel changement de configuration en cours. Si l'utilisateur vient de choisir une voix via "Choisir une voix" et que le libellé du profil actif ne change pas (voir section 4 — c'est exactement le cas aujourd'hui), ce panneau ne montre **rien** de différent avant/après le choix.

Le compteur `00:00` est purement un minuteur de lecture (`formatTime`), pas un indicateur d'état système — il n'existe aucun texte expliquant que "00:00" est normal/attendu tant qu'aucune lecture n'a démarré ; il est simplement masqué par CSS tant que `data-state="idle"` (`player.css` ligne 136-139 : `body[data-state="idle"] #transport, body[data-state="idle"] #progress-track { display: none; }`).

### Problème pour un utilisateur non technique

- Rien dans ce panneau ne relie "j'ai choisi une voix" à un effet observable. Le `#profile` span montre le nom du profil (ex. "Lecture fidèle"), pas la voix/provider réellement sélectionné — un changement de provider TTS (system → Chatterbox) sans renommer le profil est **invisible ici par construction**.
- Les boutons "Choisir une voix" / "Lire le document actuel" ne disent pas ce qu'ils vont déclencher ensuite (pas de sous-texte, pas d'aperçu).
- Le panneau "Inbox" mentionné dans la capture n'apparaît nulle part dans `playerHtml.ts` — il s'agit probablement d'une autre Tree View (`InboxTreeProvider.ts`, non lu dans cet audit, hors périmètre demandé) ; son rôle n'est pas documenté ici et mérite d'être vérifié séparément.

### Proposition concrète

- Ajouter dans `#title-line` (ou juste sous `#profile`) un span `#voice` qui affiche le **provider/voix réellement actif** (ex. "Voix système" / "Chatterbox — voix clonée"), alimenté par le même message `state` que `#profile`. C'est le changement le plus direct pour que "choisir une voix" produise un effet visible immédiatement après le choix, sans attendre une lecture.
- Donner un sous-texte à chaque bouton de `#welcome-actions` (ex. un `<small>` ou l'attribut `title`) expliquant en une phrase ce qui va se passer ("Ouvre un choix entre 3 niveaux de qualité vocale" / "Lit à voix haute le fichier actuellement ouvert dans l'éditeur").

## 2. Panneau "Profils" (`profileTreeItems.ts` + `ProfilesTreeProvider.ts`)

**Fichiers lus** :
- `vscode-extension/src/views/profiles/profileTreeItems.ts`
- `vscode-extension/src/views/profiles/ProfilesTreeProvider.ts`
- `vscode-extension/src/profiles/defaults.ts` (pour vérifier le contenu réel affiché)

### Constat — ce qui marche déjà

Le correctif du 2026-11-05 (`GAO-fix-liste-de-001`) est réel et visible dans le code : `buildProfileTreeItems` affiche désormais la `description` en clair d'un profil (ex. *"Explication orale pédagogique, avec analogies quand elles aident."*) à la place du couple technique `"ollama · chatterbox"`, ce dernier reculant au tooltip. Les 5 profils par défaut (`defaults.ts`) ont tous une description en français compréhensible, et les libellés (`"Professeur technique"`, `"Résumé LLM"`, `"Révision rapide"`, `"Voix système (aucune installation)"`, `"Lecture fidèle"`) sont déjà assez parlants pour distinguer les usages. **C'est un vrai progrès, à conserver.**

### Ce qui ne marche pas encore

- Le marqueur "actif" n'est qu'un texte `"Actif — <description>"` préfixé dans la `description` du `TreeItem` (ligne 62) plus une icône `check` (vs `lock`/`cloud`). Rien n'explique à l'utilisateur ce que "🔒"/"☁" signifient (local vs distant) — il n'y a pas de légende visible dans le panneau lui-même, seulement dans un commentaire de code (`icon: isActive ? "check" : isRemoteProfile(profile) ? "cloud" : "lock"`).
- Aucun indice visuel ne dit à l'utilisateur *comment* changer de profil actif depuis ce panneau (clic ? clic droit ? commande palette ?) — ce fichier ne contient aucune action de sélection, seulement un rendu en lecture ("Read-only listing + hover actions", commentaire ligne 3 de `ProfilesTreeProvider.ts`). Si l'action réelle existe ailleurs (`llmVoice.profilesView.*` dans `package.json`, non lu ici), son existence n'est pas du tout communiquée visuellement dans l'arbre lui-même.
- Le lien entre ce panneau "Profils" et le panneau "Lecture en cours" n'est pas établi visuellement : les deux affichent un `label`/`profile` possiblement identique, mais rien n'indique explicitement "c'est le même profil que celui affiché en haut".

### Proposition concrète

- Documenter l'icône cloud/lock directement dans l'UI : ajouter un préfixe texte court à la description (ex. "Local · Explication orale pédagogique…" / "Distant · …") plutôt que de compter uniquement sur l'icône + le tooltip, pour un utilisateur qui ne survole jamais les lignes.
- Si une action de clic existe déjà côté `package.json`/commandes (hors périmètre de cet audit — à vérifier), l'exposer visuellement via un bouton inline ou un contextValue qui active une icône "cliquable" (`$(check)` cliquable vs statique) plutôt que de laisser l'utilisateur deviner qu'un item de liste est actionnable.

## 3. Éditeur de profil (`profileEditorHtml.ts` + `ProfileEditorPanel.ts` + `profileEditor.js`/`.css`)

**Fichiers lus** :
- `vscode-extension/src/views/profileEditor/profileEditorHtml.ts`
- `vscode-extension/src/views/profileEditor/ProfileEditorPanel.ts` (120 premières lignes)
- note : `media/profileEditor/profileEditor.js` et `.css` n'ont pas pu être lus dans cette passe (budget d'audit) — voir incertitudes en fin de rapport.

### Constat

C'est, de loin, la surface la plus problématique pour un public non technique. Le formulaire expose en une seule page, sans aucune explication contextuelle (pas de `<p>` d'aide, pas de tooltip visible dans le HTML statique), des champs comme :

```html
<select id="field-narrator-provider" name="narratorProvider">
  <option value="">Aucun</option>
  <option value="ollama">Ollama (local)</option>
  <option value="openai-compatible">Compatible OpenAI</option>
</select>
...
<select id="field-tts-provider" name="ttsProvider">
  <option value="chatterbox">Chatterbox (local)</option>
  <option value="kokoro">Kokoro (local)</option>
  <option value="kyutai-pocket">Kyutai Pocket TTS (local, avancé)</option>
  <option value="system">Voix système</option>
  <option value="openai-compatible">Compatible OpenAI</option>
</select>
```

Un utilisateur qui ne connaît ni Ollama, ni Chatterbox, ni Kokoro, ni Kyutai, ni la différence entre "narrateur" et "voix (TTS)" ne peut tout simplement pas remplir ce formulaire de manière informée — c'est exactement le symptôme décrit dans la plainte ("aucune ne me parle"), mais ici au niveau de l'éditeur, pas seulement de la liste. Même des champs plus anodins ("Vitesse", "Markdown › Code › Ignorer/Lire/Expliquer/Résumer", "Synchronisation › Surlignage éditeur") n'ont aucune phrase d'aide.

Le champ "Consigne de narration" (`field-style`, un simple `<textarea>`) est en réalité le prompt LLM envoyé au narrateur (cf. `TECHNICAL_TEACHER_PROFILE.style` dans `defaults.ts`) — rien dans le formulaire ne dit à l'utilisateur qu'il écrit un prompt pour une IA, ni ne donne d'exemple, ni n'explique l'effet d'un changement.

Les erreurs de validation remontent dans une zone générique `#validation-errors` (`role="alert"`) — le contenu réel des messages d'erreur est généré côté JS (non lu ici), donc je ne peux pas évaluer s'ils sont compréhensibles.

### Problème pour un utilisateur non technique

Le formulaire suppose une connaissance préalable de l'écosystème TTS/LLM local (Ollama, Chatterbox, Kokoro, Kyutai, "OpenAI-compatible"). C'est exactement la plainte de l'utilisateur appliquée à l'éditeur : il n'y a aucune description en clair équivalente à celle ajoutée dans le panneau Profils (section 2) — ce correctif n'a visiblement pas été répercuté ici.

### Proposition concrète

- Ajouter sous chaque `<select>` un texte d'aide d'une ligne en clair, dans le même esprit que les `description` déjà écrites pour les profils par défaut. Exemple concret pour `field-tts-provider` : remplacer silencieusement les options par des libellés qui portent l'explication, pas seulement le nom du produit — ex. `"Voix système (déjà installée, aucune config)"`, `"Chatterbox — voix clonée, qualité maximale (nécessite Docker)"`, `"Kokoro — voix locale rapide"`, `"Kyutai Pocket TTS (avancé)"`. **Limite signalée par la relecture Sentinel** : les textes de `voiceTiers.ts` ne couvrent que 3 niveaux de voix (système/Piper/Chatterbox), pas les 5 moteurs proposés ici (`chatterbox`, `kokoro`, `kyutai-pocket`, `system`, `openai-compatible`) — réutiliser ce qui existe pour "system"/"chatterbox" est possible, mais il faudra écrire de nouveaux textes pour Kokoro, Kyutai Pocket TTS et "Compatible OpenAI", qui n'ont aujourd'hui aucune description en clair nulle part dans le code.
- Renommer le fieldset "Narration" en quelque chose qui dit ce qu'il fait (ex. "Réécriture par IA avant la lecture") et ajouter une phrase fixe au-dessus de `field-style` : "Ce texte est une instruction donnée à l'IA qui reformule le contenu avant de le lire — modifiez-le pour changer le ton."
- Ajouter un exemple concret affiché en italique sous `field-style` (ex. le contenu de `TECHNICAL_TEACHER_PROFILE.style`) pour qu'un utilisateur comprenne par l'exemple plutôt que par l'abstraction.

## 4. Assistant "Choisir une voix" et onboarding (`SetupVoice.ts`, `voiceTiers.ts`, `handleVoiceTier.ts`, `Walkthrough.ts`)

**Fichiers lus** :
- `vscode-extension/src/onboarding/SetupVoice.ts`
- `vscode-extension/src/onboarding/voiceTiers.ts`
- `vscode-extension/src/onboarding/handleVoiceTier.ts`
- `vscode-extension/src/onboarding/Walkthrough.ts`
- `vscode-extension/src/pipeline/Pipeline.ts` (méthode `applyVoiceTierChoice`, lignes ~1914-1937) — lu pour comprendre l'effet réel du choix, car c'est la pièce qui relie ce menu au reste de l'UI.
- `UseOwnVoice.ts`/`useOwnVoiceFlow.ts` : localisés (`UseOwnVoice.ts` existe) mais non lus en détail dans cette passe — voir incertitudes.

### Constat — ce qui marche déjà

Les trois options du Quick Pick (`voiceTiers.ts`, lignes 35-55) sont honnêtes et déjà écrites en langage clair, avec un `label` + `description` + `detail` pour chaque tier :
- "Voix système" → "Disponible tout de suite — qualité correcte"
- "Voix française autonome (recommandé)" → "Meilleure qualité, 100% locale — téléchargement de ~60 Mo"
- "Qualité maximale (avancé — nécessite Docker)" → "Clonage de voix, la plus naturelle — nécessite Docker"

C'est un bon texte : aucun jargon type "chatterbox"/"ollama" n'apparaît dans les libellés visibles de ce menu précis (le mot "Chatterbox" n'apparaît que dans le message modal qui s'affiche *après* avoir choisi ce tier spécifique, où il est contextuellement justifié).

### Constat — la cause racine très probable de la plainte

J'ai remonté la chaîne jusqu'à l'endroit où le choix est réellement appliqué, car c'est exactement la phrase de la plainte à vérifier ("je ne sais même pas […] ce que ça change concrètement. Il n'y a rien qui change") :

`Pipeline.ts`, `applyVoiceTierChoice` (lignes 1926-1937) :
```ts
async applyVoiceTierChoice(tier: VoiceTier): Promise<void> {
  const profile = await this.profiles.getSelected();
  const binding = ttsBindingForTier(tier);
  const updated = await this.profiles.update(profile.id, (current) => ({
    ...current,
    tts: { ...binding }
  }));
  this.currentProfileLabel = updated.label;
  void vscode.window.showInformationMessage(
    `LLM Voice : voix « ${titleCaseProviderId(binding.providerId)} » appliquée au profil « ${updated.label} ».`
  );
}
```
Ce code **ne change que le champ `tts` du profil actif** ; il ne touche jamais `updated.label`. Donc :
- Le panneau "Lecture en cours" (section 1) affiche `#profile` = le `label` du profil, qui est **identique avant et après** le choix de voix (ex. toujours "Lecture fidèle"). Rien n'y change visuellement.
- Le panneau "Profils" (section 2) affiche la même `description`/`label` en ligne visible, également inchangée par ce choix — **nuance (relecture Sentinel)** : son tooltip, lui, contient la paire technique (`formatProfileDescription`) qui reprend le nom du moteur de voix, et l'arbre se rafraîchit déjà tout seul quand `profiles.json` change (`extension.ts:168-169`). Le choix est donc visible au survol de la ligne — "aucune surface" est trop absolu ; la conclusion pratique reste : **rien n'est visible sans survol**.
- La barre de statut (section 5) affiche `profileLabel`, également inchangé.
- Le **seul** effet visible du choix est un **toast `showInformationMessage`** ("LLM Voice : voix « Chatterbox » appliquée au profil « Lecture fidèle »") — une notification non modale qui disparaît d'elle-même après quelques secondes (comportement standard VS Code pour ce type d'appel), et qui est le type de message que l'utilisateur a explicitement signalé comme "facilement manqué" ailleurs dans ses retours.

**C'est, concrètement, le bug qui explique la plainte** : le code fait bel et bien quelque chose (il réécrit le binding `tts` du profil), mais la seule confirmation visible dans toute l'UI persistante (panneau player, panneau profils, barre de statut) est... rien, parce qu'aucune de ces trois surfaces n'affiche le provider TTS, seulement le `label` du profil, qui ne change jamais ici.

Pour le tier "system" en particulier, la seule confirmation est `SYSTEM_VOICE_READY_MESSAGE`, un toast informatif — même limite.

### Problème pour un utilisateur non technique

L'utilisateur fait un choix explicite (clic sur une des 3 options), VS Code produit un toast qu'il peut manquer (changement de fenêtre, notification empilée, lecture trop rapide), et ensuite **aucune surface persistante ne confirme ni n'affiche ce qui a été choisi**. De son point de vue, c'est exactement "rien ne change" — c'est vérifiable dans le code, pas seulement une impression.

### Proposition concrète

- **Correction importante (relecture Sentinel)** : `ttsBindingForTier` (`voiceTiers.ts:115-123`) fait pointer **"Voix système" et "Voix française autonome (Piper)" vers le même `providerId: "system"`** — c'est justement la comparaison que l'utilisateur fait entre ces deux choix. Afficher `binding.providerId` seul ne les distinguerait donc toujours pas. Il faut afficher un libellé de **niveau de voix** (le `label` du tier choisi — "Voix système" / "Voix française autonome" / "Qualité maximale") ou, pour le cas "system"/"piper", le moteur réellement détecté (`SystemTtsProvider.detectEngine()`), pas seulement `providerId`.
- Dans `player.js`/`playerHtml.ts` (section 1) et `StatusBar`/`statusBarText.ts` (section 5), afficher ce libellé (ou le provider réel pour Chatterbox/les cas non ambigus) en plus du `label` du profil — c'est la correction qui règle directement la plainte, car elle rend l'effet du choix visible en permanence, pas seulement dans un toast éphémère.
- **Corrigé (relecture Sentinel)** : la méthode s'appelle `applyVoiceTierChoice`, pas `applyProviderChoice`. L'idée de "rafraîchir explicitement le panneau Profils" après son appel est en grande partie inutile : l'arbre se rafraîchit déjà automatiquement au changement de `profiles.json` (`extension.ts:168-169`). La vraie action nécessaire n'est pas de rafraîchir, mais de faire remonter le provider/niveau de voix dans la **ligne visible** du panneau Profils (pas seulement son tooltip technique).
- Remplacer le toast `showInformationMessage` (transitoire) par un message avec un bouton d'action (`"Voir le profil"` → ouvre l'éditeur de ce profil avec le nouveau binding visible), pour qu'un utilisateur qui le manque ait quand même un moyen de vérifier après coup.

### Non vérifié dans cette section

`UseOwnVoice.ts`/`useOwnVoiceFlow.ts` existent dans le dépôt mais n'ont pas été lus en détail (seul `UseOwnVoice.ts` a été localisé par `Glob`) — je ne peux pas me prononcer sur ce flux précis.

## 5. Barre de statut (`StatusBar.ts` + `statusBarText.ts` + `providerStatusText.ts`)

### Constat

`formatStatusBarText` (`statusBarText.ts`) affiche toujours `vm.profileLabel` — jamais le provider TTS, confirmant le problème structurel de la section 4 : cette surface ne peut par construction pas refléter un changement de voix qui ne renomme pas le profil.

Point positif : le commentaire et le code montrent un vrai souci de "quelque chose à voir dès l'activation" (ligne 32-37 : `"LLM Voice"` par défaut plutôt qu'un tiret vide, en réponse explicite à un retour utilisateur antérieur "j'ai trouvé le bouton en cherchant un peu partout"). ### Problème pour un utilisateur non technique

- Mélange anglais/français inexpliqué dans un menu par ailleurs francisé ("Provider Status", "Verify Local Mode", "Ready"/"Loading"/"Offline").
- Même limite structurelle que la section 4 : rien n'indique le provider/voix actif ici, seulement le profil.

### Proposition concrète

- Traduire `STATUS_LABEL` et les deux entrées de menu en français ("État des fournisseurs", "Vérifier le mode local", "Prêt"/"Chargement…"/"Hors ligne"/"Erreur"/"Non vérifié") pour la cohérence linguistique globale.
- Ajouter le provider résolu dans `StatusBarViewModel`/`formatStatusBarText`, au moins en tooltip (`formatStatusBarTooltip` ne mentionne actuellement ni le profil ni le provider, seulement un texte d'aide générique "cliquer pour les actions de lecture").

## 6. Notifications toast (`notifications.ts`)

**Fichier lu** : `vscode-extension/src/ui/notifications.ts` en entier.

### Constat — ce qui marche déjà

Il y a un vrai effort de pédagogie progressive bien pensé : `chooseTtsUnavailableMessage` montre un message générique actionnable à la première erreur (`TTS_UNAVAILABLE_MESSAGE` = "LLM Voice : aucune voix configurée.") puis un message diagnostique détaillé dès la seconde (`formatTtsUnavailableDiagnosticMessage`, qui nomme le provider, l'endpoint et l'erreur réelle) — directement motivé par un vrai bug utilisateur documenté dans le code ("Boucle infinie", 2026-09-12). `NotificationGate` évite le spam de 50 dialogues identiques. C'est une bonne mécanique, bien commentée, et orientée vers un vrai problème observé.

### Ce qui ne marche pas

- `NARRATOR_UNAVAILABLE_MESSAGE = "LLM Voice: Narrator unavailable"` est **en anglais**, au milieu d'un fichier où tous les autres messages utilisateur sont en français ("LLM Voice : aucune voix configurée.", etc.) — incohérence de langue nette, et visible directement dans une notification réelle.
- Les boutons de `notifyNarratorUnavailable` sont aussi en anglais en dur : `"Retry"`, `"Read without narration"`, `"Cancel"` (lignes 146-148), alors que `notifyTtsUnavailable` et `notifyChunkInvalid` ont des libellés français ou au moins cohérents ("Choisir une voix", "Voir les réglages", "Réessayer" vs "Skip"/"Stop" — `notifyChunkInvalid` elle-même mélange un message anglais ("LLM Voice: audio chunk failed after…") avec des boutons anglais "Skip"/"Stop", ligne 170-180).
- Ces toasts sont par nature transitoires (c'est la nature même d'un `showInformationMessage`/`showErrorMessage` non modal) — déjà identifié par la mission comme un facteur de confusion ; rien dans le code ne persiste cette information ailleurs (pas d'écriture dans l'Inbox ou le panneau Profils après une notification manquée), donc un utilisateur qui ferme/manque le toast d'erreur n'a aucun second endroit où relire ce qui s'est passé.

### Problème pour un utilisateur non technique

Un sous-ensemble des messages/boutons de cette fenêtre d'erreur spécifique (`notifyNarratorUnavailable`, `notifyChunkInvalid`) est resté en anglais alors que la cible annoncée (`project-context.yaml`, "Language: Français") est le français — pour quelqu'un de non technique, un message d'erreur en anglais est une barrière de plus à la compréhension, à un moment (une erreur) où la clarté compte le plus.

### Proposition concrète

- Traduire `NARRATOR_UNAVAILABLE_MESSAGE`, les boutons de `notifyNarratorUnavailable` et le message/boutons de `notifyChunkInvalid` en français, au même niveau de qualité que `notifyTtsUnavailable`.
- Envisager de dupliquer le contenu d'un toast d'erreur important dans l'Inbox (hors périmètre direct de cet audit, mais `#welcome-text`/Inbox existe déjà comme concept dans la capture fournie) pour qu'il reste consultable après disparition du toast.

## Synthèse priorisée

### Bloque la compréhension de base

1. **Le choix de voix n'a aucun effet visible persistant** (section 4) — `applyVoiceTierChoice` ne change que `tts`, jamais `label`/`profileLabel`, et les trois surfaces persistantes (`player.js` `#profile`, `ProfilesTreeProvider`, `StatusBar`) n'affichent que le `label` ; le panneau Profils ne reflète le changement qu'en tooltip, jamais en ligne visible. Le seul retour immédiat et bien visible est un toast transitoire. **C'est la cause racine la plus probable et la plus directement vérifiable de la plainte utilisateur citée dans cette mission.** Complication supplémentaire (relecture Sentinel) : "Voix système" et "Voix française autonome (Piper)" pointent vers le même `providerId: "system"` en interne — une correction qui afficherait seulement le `providerId` ne distinguerait toujours pas ces deux choix, alors que c'est précisément la comparaison que l'utilisateur fait ; il faut un libellé de niveau de voix, pas le seul nom du moteur. *(Fusionne les points 1 et 3 d'un brouillon antérieur — même cause racine : aucune surface n'affiche le provider/niveau de voix réellement actif.)*
2. **L'éditeur de profil (webview) suppose une connaissance préalable d'Ollama/Chatterbox/Kokoro/Kyutai/OpenAI-compatible, sans aucune explication en clair**, alors que le panneau Profils a déjà reçu ce traitement. L'incohérence entre les deux surfaces veut dire que l'utilisateur peut retrouver le même mur de jargon une étape plus loin, dès qu'il clique pour éditer.

### Gênant mais contournable

3. Incohérence linguistique anglais/français dans plusieurs notifications d'erreur (`narrator unavailable`, `chunk invalid`) et dans le menu/libellés de la barre de statut ("Provider Status", "Ready"/"Loading"/"Offline") — gênant pour un public non technique mais contournable (le sens général reste déductible).
4. Le panneau Profils ne documente pas visuellement la signification des icônes 🔒/☁, et ne montre pas d'action de sélection claire — contournable via essai-erreur ou la documentation.
5. Toasts d'erreur transitoires non persistés ailleurs — contournable en relançant l'action pour revoir le message, mais frustrant.

### Cosmétique

6. Boutons "Choisir une voix"/"Lire le document actuel" sans sous-texte explicatif dans le panneau player — le libellé seul reste compréhensible, un sous-texte serait un plus, pas un correctif de blocage.
7. Absence de `<small>`/aide contextuelle pour les champs secondaires de l'éditeur de profil (Markdown, Synchronisation) — moins critique que les champs provider/narrateur du point 2, car leurs valeurs par défaut fonctionnent sans y toucher.

## Ce qui marche déjà et ne doit pas être refait

- Les descriptions en clair des 5 profils par défaut (`defaults.ts`) et leur remontée en tête de ligne dans le panneau Profils (`profileTreeItems.ts`, correctif `GAO-fix-liste-de-001`).
- Le texte des 3 options de "Choisir une voix" (`voiceTiers.ts`) — déjà honnête, déjà en clair, déjà sans jargon dans les libellés visibles du menu lui-même.
- La progression pédagogique des messages d'erreur TTS (`chooseTtsUnavailableMessage`) — mécanique bien pensée, à répliquer pour le narrateur plutôt qu'à remplacer.
- Le CodeLens "▶ Lire cette section" — simple, clair, à citer en exemple.
- Le choix de montrer "LLM Voice" dans la barre de statut dès l'activation plutôt qu'un symbole vide, en réponse déjà actée à un retour utilisateur antérieur.

Le problème central n'est donc pas une ignorance générale de l'UX de la part de l'équipe (plusieurs correctifs montrent le contraire), mais une **incohérence de profondeur** : les surfaces "de premier niveau" (liste de profils, menu de choix de voix) ont été retravaillées, les surfaces "en aval" (éditeur de profil, confirmation persistante d'un choix) ne l'ont pas encore été — exactement le symptôme d'une correction ponctuelle (CdC des deux tickets déjà traités) plutôt que d'un audit transverse, ce que la refonte demandée doit corriger.
