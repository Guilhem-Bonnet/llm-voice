# Assembler LLM Voice depuis des briques existantes

Aucun projet open source ne peut être repris tel quel pour construire LLM Voice : le marché des lecteurs vocaux VS Code est jeune et fragmenté (aucune extension identifiée ne dépasse ~2 000 installs), l'écosystème "TTS pour Claude Code" tient sur une poignée de projets mono-mainteneur, et même les meilleures piles Node/WASM pour l'ingestion de documents s'arrêtent net dès qu'il faut gérer un PDF scanné ou une mise en page complexe ([Markdown Read Aloud](https://marketplace.visualstudio.com/items?itemName=Larsini.offline-markdown-read-aloud), [Duck Talk](https://github.com/dhuynh95/duck_talk)). En revanche, chaque brique du pipeline a un ou deux équivalents open source solides à réutiliser directement : **sherpa-onnx** (Apache-2.0) comme moteur pivot unique pour TTS, STT et VAD sans Python ni Docker, **mpv en sous-processus** comme la seule voie documentée offrant simultanément pause, reprise, seek et position sans étape de compilation, et **pdf.js/unpdf + mammoth + officeParser + Readability** comme socle Node pur pour l'ingestion de documents propres. Le nœud dur non résolu par l'écosystème est la lecture audio native hors webview avec surlignage synchronisé et lecture gapless en streaming : aucune source consultée ne documente d'implémentation VS Code existante de ce pattern précis, ce qui en fait un vrai développement à budgéter plutôt qu'une brique à récupérer. Enfin, plusieurs briques séduisantes sont des pièges de licence pour une extension MIT — le rewrite 2025 de Piper est passé sous **GPL-3.0**, MuPDF/PyMuPDF sont en **AGPL-3.0**, et les poids de XTTS-v2, F5-TTS et Fish Speech sont **non commerciaux (CPML/CC-BY-NC/CC-BY-NC-SA)** — et doivent être écartées ou cantonnées à un tier optionnel séparé.

## Un marché naissant où deux produits méritent d'être étudiés de près

Le positionnement de LLM Voice — lecture de documents à la demande + lecture des réponses d'agents de code + conversation vocale locale — chevauche directement deux catégories déjà peuplées mais peu consolidées. Côté VS Code, **Markdown Read Aloud (Piper)** ([Marketplace](https://marketplace.visualstudio.com/items?itemName=Larsini.offline-markdown-read-aloud)) est le concurrent architectural le plus proche : moteur Piper local, nettoyage markdown, lecture soit en webview soit via des lecteurs système, mais avec des défauts documentés à ne pas reproduire — le surlignage de phrase se désactive si le document est édité pendant la lecture, les lecteurs système ne permettent pas de vraie pause, et l'export Supertonic est mono-process. **Markdown TTS: Read Aloud & AI Narration** ([Marketplace](https://marketplace.visualstudio.com/items?itemName=AbhishekShr.markdown-tts)) est le concurrent fonctionnel le plus proche sur la "réécriture par LLM avant lecture" (narration IA "bring your own key" + résumé vocal de `git diff`), mais son parsing markdown par regex et son absence totale d'offline sur Linux sont deux pièges à éviter. **ElevenLabs Text-to-Speech for VSCode** ([Marketplace](https://marketplace.visualstudio.com/items?itemName=lekman.tts-code)) apporte la seule référence UX crédible de surlignage synchronisé trouvée côté extensions, et sa bonne pratique de sécurité (clés API dans `SecretStorage`) est directement transposable.

Côté "écouter son agent de code", l'écosystème Claude Code compte au moins huit projets 2025-2026, tous MIT, mais un seul avec une vraie traction : **VoiceMode** (mbailey), 1,4k étoiles, 195 forks, 2 149 commits, serveur **MCP** avec STT Whisper.cpp local et TTS Kokoro local, conversation mains libres ([GitHub](https://github.com/mbailey/voicemode)). C'est la référence la plus proche de la future fonctionnalité "conversation vocale avec un modèle local" de LLM Voice, bien qu'aucune source ne confirme un support Ollama spécifique — un vrai point à vérifier avant de s'en inspirer sur ce point précis. **Duck Talk** (dhuynh95, MIT, 24 étoiles) est la référence architecturale directe pour le "live streaming" : un relais TypeScript intercepte les tokens bruts de Claude Code et les envoie phrase par phrase à Google Gemini TTS, avec une latence ajoutée par le relais estimée à ~1 ms par les auteurs ([GitHub](https://github.com/dhuynh95/duck_talk)). À l'inverse, **Claude Read Aloud** (MichaelPGifford) illustre un pattern à éviter absolument : il patche localement les fichiers de l'extension Claude Code pour ajouter un bouton dans le chat, une approche "userscript-style" fragile à chaque mise à jour de l'outil ciblé ([GitHub](https://github.com/MichaelPGifford/claude-read-aloud)) — LLM Voice doit lui préférer la lecture de fichier de transcript stable ou un hook officiel documenté, comme le fait ce même projet pour capturer la réponse.

Deux angles morts confirment l'opportunité : Microsoft a fermé "not planned" la demande générique de TTS pour tout Copilot Chat ([microsoft/vscode#266638](https://github.com/microsoft/vscode/issues/266638)), préférant investir dans son **Voice Mode** conversationnel (`agents.voice.*`), qui fait du STT on-device par défaut (modèle Nemotron local) mais dont le moteur TTS de sortie n'est documenté nulle part publiquement ([VS Code docs](https://code.visualstudio.com/docs/configure/accessibility/voice)) — et Cursor comme aider n'ont *aucune* lecture vocale de réponse native, seulement de la dictée en entrée. Les plaintes documentées sur le TTS natif de VS Code — lecture non interruptible même à la fermeture de VS Code, préfixe parasite "agent" sur chaque phrase, lecture du contenu intermédiaire verbeux (tool calls, "thinking") plutôt que la réponse finale ([microsoft/vscode#296720](https://github.com/microsoft/vscode/issues/296720), [#301431](https://github.com/microsoft/vscode/issues/301431)) — pointent vers deux exigences produit non négociables pour LLM Voice : un stop/pause fiable, et la lecture de la seule réponse finale.

## Trois familles de moteurs TTS couvrent le français sans Python ni Docker

Le paysage des moteurs TTS locaux se divise nettement en deux blocs : un bloc "zéro dépendance lourde" directement embarquable dans le daemon Node, et un bloc GPU/Python de qualité supérieure qui exige un sidecar. Pour le premier bloc, **sherpa-onnx** (k2-fsa, Apache-2.0) est la brique la plus stratégique : il publie des addons Node N-API précompilés par plateforme, charge indifféremment des voix Piper/VITS, Kokoro et Supertonic via une seule API, expose une génération en streaming par callback ("émet des échantillons audio au fur et à mesure qu'ils sont produits"), et couvre en prime ASR, VAD, identification de locuteur et débruitage dans le même paquet ([DeepWiki](https://deepwiki.com/k2-fsa/sherpa-onnx/3.2-text-to-speech-(tts)), [nodejs-addon-examples](https://github.com/k2-fsa/sherpa-onnx/blob/master/nodejs-addon-examples/README.md)). C'est un choix "une intégration, plusieurs moteurs" qui réduit fortement la surface de code à maintenir. **Kokoro**, via le paquet npm `kokoro-js` (Apache-2.0/MIT), tourne en pur JS/ONNX dans Node sans Python ni Docker, inclut des voix françaises européennes et canadiennes, et s'est classé premier de l'Open TTS Arena de Hugging Face pour la qualité mono-locuteur — un classement toutefois non spécifique au français ([HF post Xenova](https://huggingface.co/posts/Xenova/503648859052804)). **Piper** reste la référence CPU la plus légère avec quatre voix françaises natives (`siwis`, `upmc`, `tom`, `gilles`) et des retours communautaires contrastés : `siwis` est jugée "légèrement robotique mais compétitive" ([quick-tts.com](https://quick-tts.com/voice/fr-fr-siwis-medium/)), `upmc` a un bug de vitesse documenté qui la rend difficilement compréhensible ([issue Home Assistant #105819](https://github.com/home-assistant/core/issues/105819)), et `tom` est décrite comme plus adaptée à la prose longue.

Le tableau ci-dessous synthétise les briques TTS à retenir, en signalant explicitement les pièges de licence :

| Moteur | Licence code / poids | Rôle pour LLM Voice | Maturité |
|---|---|---|---|
| **sherpa-onnx** | Apache-2.0 / variable par modèle | Backend TTS+STT+VAD par défaut, addon Node natif | Très active, ajouts 2026 (Supertonic, ZipVoice) ([GitHub](https://github.com/k2-fsa/sherpa-onnx)) |
| **Kokoro** (`kokoro-js`) | Apache-2.0 (code+poids) | Voix françaises par défaut, streaming texte long | Active |
| **Piper (legacy rhasspy)** | MIT (dépôt **archivé** le 6/10/2025) | Fallback CPU ultra-léger, binaires prêts à l'emploi | Figé, développement transféré |
| **Piper (piper1-gpl, 2025)** | **GPL-3.0** — ⚠️ incompatible avec une extension MIT sans isolation en process séparé | À éviter en dépendance liée ; utilisable seulement comme binaire externe spawné, à valider juridiquement | Active sous l'Open Home Foundation ([Grokipedia](https://grokipedia.com/page/Piper_text-to-speech_system)) |

Aucun serveur local compatible OpenAI (`Kokoro-FastAPI`, `OpenedAI-Speech`, `Speaches`) ne documente d'honorer un paramètre `language` standard — tous font transiter la langue par le choix de voix ou de modèle, ce qui impose à LLM Voice de maintenir sa propre table de correspondance voix→langue quel que soit le backend retenu. Sur la machine de développement (AMD RDNA4/ROCm), l'accélération GPU via `onnxruntime-node`/sherpa-onnx n'est pas garantie : le support ROCm côté serveur a été retiré d'ONNX Runtime à partir de la version 1.23 au profit de MIGraphX, information non re-vérifiée pour les paquets Node prébuildés ([onnxruntime.ai](https://onnxruntime.ai/docs/execution-providers/ROCm-ExecutionProvider.html)) — le CPU doit rester l'hypothèse de planification par défaut, avec **Chatterbox-TTS-Server** comme seule option documentant explicitement un chemin ROCm de bout en bout si un sidecar Python devient acceptable.

## Le STT et la VAD locaux dessinent la même carte à trois familles

Comme pour le TTS, trois familles évitent toute dépendance Python côté utilisateur final : **whisper.cpp** (MIT, poids Whisper/Silero VAD également MIT), avec des bindings npm actifs comme `nodejs-whisper` et un serveur HTTP intégré ([ggml-org/whisper.cpp](https://github.com/ggml-org/whisper.cpp)) ; **sherpa-onnx**, à nouveau pivot unique puisqu'il embarque ASR streaming/non-streaming et VAD dans le même addon Node ; et **Vosk** (Apache-2.0), le plus léger (modèles ~50 Mo, ~300 Mo de RAM) avec des bindings Node officiels, mais moins précis (~12% WER contre 9,3% en short-form pour le meilleur modèle français distillé) ([alphacephei.com](https://alphacephei.com/vosk/models)). Pour la précision française spécifique, **`eustlb/distil-large-v3-fr`** affiche 9,34% de WER en short-form et 11,13% en long-form, dans une marge de 2% par rapport à Whisper large-v3 tout en étant nettement plus rapide ([Hugging Face](https://huggingface.co/eustlb/distil-large-v3-fr)) — un bon candidat pour la vérification automatisée de TTS (voir plus bas), consommable via faster-whisper ou converti pour whisper.cpp.

Pour la conversation vocale mains-libres visée à terme, aucun des moteurs "sans Python" n'offre de transcription incrémentale native comparable à **Kyutai STT** (`kyutai/stt-1b-en_fr`, CC-BY-4.0), qui combine un modèle dédié anglais/français, un délai de traitement de ~0,5 s et une **VAD sémantique intégrée** au modèle lui-même ([Hugging Face](https://huggingface.co/kyutai/stt-1b-en_fr)) — mais ses performances CPU pures ne sont pas confirmées, seuls des chiffres GPU L40S (64 connexions simultanées à un facteur temps réel de 3x) ayant été trouvés, et aucun binding Node n'a été identifié. En pratique, whisper.cpp reste utilisable en "streaming approximatif" par fenêtres pour du push-to-talk (l'utilisateur relâche un bouton, l'enregistrement est transcrit d'un coup), suffisant pour un usage initial mais pas pour un mode mains-libres avec retour mot-à-mot. Côté détection de fin de parole, **Silero VAD** (MIT, distribué via PyTorch Hub mais consommable en ONNX depuis Node) domine les comparatifs 2026 face à WebRTC VAD sur les faux positifs à seuil bas, tandis qu'un nouvel entrant, **TEN VAD**, revendique une précision supérieure aux deux pour une complexité de calcul moindre, sans toutefois de binding Node actif confirmé ([Picovoice blog](https://picovoice.ai/blog/best-voice-activity-detection-vad/), [TEN-framework/ten-vad](https://huggingface.co/TEN-framework/ten-vad)). Enfin, la capture microphone en Node reste structurellement un problème de sous-processus plutôt qu'une brique native mûre : `node-record-lpcm16` (dépendant de SoX) n'a pas été mis à jour depuis 7 ans, et le pattern recommandé consiste à spawn soi-même `sox`/`rec`, `pw-record` ou `arecord` selon la plateforme plutôt que de dépendre d'un paquet npm historique peu maintenu.

## La lecture audio native hors webview est le nœud dur non résolu

C'est ici que se joue la décision d'architecture la plus lourde de conséquences pour LLM Voice, et c'est aussi la zone où les notes de recherche documentent le moins de solutions "prêtes à l'emploi". Le point de départ du problème est confirmé : VS Code applique la politique d'autoplay Chromium standard, et plusieurs issues ouvertes documentent l'erreur `NotAllowedError`/`play() can only be initiated by a user gesture` aussi bien dans des webviews d'extension que dans le propre service d'accessibilité interne de VS Code (`audioCueService`) ([vscode#66050](https://github.com/microsoft/vscode/issues/66050), [vscode#197937](https://github.com/microsoft/vscode/issues/197937)). Le modèle Chromium "User Activation v2" pose un bit d'activation **sticky** au premier geste, qui en théorie ne devrait pas se réinitialiser tant que le document webview n'est ni rechargé ni détruit — mais aucune documentation VS Code officielle ne confirme ce comportement pour ses propres webviews, ni ce qu'il advient de ce bit lors d'un cycle hidden→shown avec `retainContextWhenHidden`. Cela signifie concrètement que jouer de l'audio *dans* le webview reste un pari fragile pour un usage répété dans la durée d'une session, ce qui justifie le choix produit déjà pressenti par LLM Voice de sortir l'audio du webview.

Une fois hors du webview, aucune option ne coche toutes les cases (start + pause/resume + seek + position + flux PCM par stdin + sélection de périphérique) sans compromis. Les addons natifs Node butent tous sur un problème : **node-speaker** et **naudiodon** exigent `node-gyp` donc un compilateur natif chez l'utilisateur ; **audify** (RtAudio) propose des prebuilds N-API mais n'expose ni `pause()` ni seek, seulement `start()`/`stop()` et un `streamTime` en lecture seule ; **node-web-audio-api** (ircam-ismm, Rust/NAPI) est la seule option avec des prebuilts actifs sur les trois OS en 2026, mais ses binaires Linux sont construits avec le backend **Jack** (nécessitant `pipewire-jack`), sa licence n'a pas été confirmée dans cette recherche, et l'implémentation d'un vrai pause/resume par source individuelle demande de recomposer `AudioContext.suspend()/resume()` avec un calcul manuel d'offset — un détail non cité verbatim dans sa documentation et donc à vérifier avant de s'y engager ([GitHub ircam-ismm](https://github.com/ircam-ismm/node-web-audio-api)). Face à cela, **spawn un lecteur système déjà présent, en particulier `mpv` piloté par son socket IPC JSON (`--input-ipc-server`)**, ressort comme la voie la plus robuste documentée : mpv expose nativement une propriété `pause` lisible/modifiable, `playback-time`/`time-pos` pour la position, `--gapless-audio` pour l'enchaînement sans coupure, et un mode `--demuxer=rawaudio` qui accepte du PCM brut via stdin ([mpv manual](https://mpv.io/manual/stable/)) — au prix de devoir bundler un binaire mpv portable, puisqu'il n'est préinstallé sur aucun des trois OS cibles. Sur Linux, `aplay -i` offre un pause/resume interactif mais verrouillé par un test `isatty` non scriptable (ticket ouvert sans réponse mainteneur depuis des années, [alsa-utils#155](https://github.com/alsa-project/alsa-utils/issues/155)) ; sur macOS, `afplay` n'a ni pause ni position ; sur Windows, il faut passer par un objet .NET/COM piloté en PowerShell (`System.Windows.Media.MediaPlayer` a Pause+Position mais démarre un hôte PowerShell par appel, coût non chiffré dans les sources trouvées).

Pour le chaînage gapless de chunks TTS en streaming, le pattern qui ressort de deux pipelines Python matures (**RealtimeTTS** et **Pipecat**) est la **concaténation pure de PCM sans crossfade** dans un flux unique vers un process de sortie long-lived, avec la position calculée côté application par comptage d'octets écrits divisé par le débit (`sample_rate × channels × sample_width`) plutôt que par une requête native au lecteur, aucun des lecteurs CLI Linux étudiés (`pw-cat`, `pacat`, `aplay`) n'exposant de requête de position interrogeable ([RealtimeTTS stream_player.py](https://raw.githubusercontent.com/KoljaB/RealtimeTTS/master/RealtimeTTS/stream_player.py), [Pipecat docs](https://reference-server.pipecat.ai/en/latest/_modules/pipecat/transports/base_output.html)). Aucune source consultée ne documente d'implémentation existante, VS Code ou Electron, de ce pattern précis avec rapport de position pour synchroniser un surlignage — c'est un vrai trou de recherche, explicitement non couvert, qui doit être traité comme du développement propre à LLM Voice plutôt qu'une brique récupérable. En amont de ce pipeline, il n'existe pas non plus d'équivalent Node/TypeScript direct du découpeur de phrases Python `stream2sentence` (gestion des abréviations, décimales, tuning vitesse/fiabilité) : les candidats npm trouvés (`llm-text-splitter`, `llm-splitter`, `llm-chunk`) sont conçus pour du chunking de corpus complet à des fins de RAG, pas pour un découpage incrémental d'un flux de tokens — la solution la plus solide identifiable est de combiner `Intl.Segmenter({granularity: 'sentence'})` (natif, sans dépendance ni licence) avec une liste d'exceptions d'abréviations codée à la main, en s'inspirant des règles documentées par `stream2sentence` et par les tickets `hass-edge-tts`/`backtalk` sur les coupures indues (virgules décimales lues comme des pauses, "Dr." coupé en deux) ([GitHub KoljaB/stream2sentence](https://github.com/KoljaB/stream2sentence)).

Enfin, ce choix a un coût de packaging documenté : depuis `vsce` 1.99.0, `vsce package --target` permet de produire un VSIX par plateforme parmi une liste fixe (`win32-x64`, `win32-arm64`, `linux-x64`, `linux-arm64`, `linux-armhf`, `alpine-x64/arm64`, `darwin-x64`, `darwin-arm64`, `web`), ce qui implique de maintenir une matrice CI d'au moins cinq cibles réalistes et de renoncer au support VS Code for the Web pur si un binaire natif ou un mpv embarqué est nécessaire ([Publishing Extensions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)).

## L'ingestion de documents révèle un fossé structurel Node/Python et un piège AGPL

Pour du texte "propre" — PDF natif, DOCX, EPUB, HTML — une chaîne 100% Node/WASM existe et fonctionne : **pdfjs-dist** (Apache-2.0) ou **unpdf** (MIT, "alternative moderne activement maintenue à pdf-parse") pour le PDF texte, **mammoth** (BSD-2-Clause) pour convertir DOCX en HTML sémantique en s'appuyant sur les styles Word, **officeParser** (MIT, 568 942 téléchargements/semaine) comme filet de sécurité multi-format incluant l'ODT, et **`@mozilla/readability`** (Apache-2.0) combiné à **linkedom** (plus léger que jsdom, coût de démarrage ~3× inférieur) pour l'extraction d'article HTML ([GitHub unjs/unpdf](https://github.com/unjs/unpdf), [GitHub mwilliamson/mammoth.js](https://github.com/mwilliamson/mammoth.js/), [GitHub harshankur/officeParser](https://github.com/harshankur/officeParser)). Côté EPUB, aucune alternative n'est activement maintenue en 2026 : `epub2` (150k téléchargements/semaine) et `epubjs` (5,8k étoiles) datent respectivement de 2023 et 2022, un vrai gap à budgéter.

Le vrai piège de licence est **MuPDF/mupdf.js** (Artifex) : c'est la meilleure qualité d'extraction WASM pure disponible, mais distribuée en **AGPL-3.0-or-later** ou licence commerciale Artifex — un choix qui, s'il est intégré tel quel dans le daemon, imposerait soit de divulguer l'intégralité du code source du démon sous AGPL, soit d'acheter une licence commerciale ([npm mupdf](https://www.npmjs.com/package/mupdf)). Son cousin Python **PyMuPDF/fitz** porte la même réserve AGPL-3.0. Ces deux briques doivent être explicitement écartées d'une extension MIT, au profit de pdf.js/unpdf malgré leur structuration plus pauvre. Dès qu'il faut préserver l'ordre de lecture, ignorer les en-têtes/pieds de page/numéros et gérer des tableaux complexes — ce qui compte pour une vraie narration — le seul outil qui modélise explicitement cette séparation "corps" vs "mobilier" est **Docling** (IBM, MIT, Python, CPU-friendly), dont le format `DoclingDocument` sépare `body` et `furniture` et reconstruit la hiérarchie des titres et tableaux au lieu de les aplatir ([docs Docling](https://docling-project.github.io/docling/concepts/docling_document/)). Aucun composant Node/WASM équivalent n'a été trouvé, ce qui pousse vers un palier Python optionnel ("tier avancé") pour les documents structurellement complexes, plutôt que vers une réimplémentation maison des heuristiques d'en-tête/pied de page. Pour le PDF scanné, **tesseract.js**/**tesseract-wasm** (Apache-2.0) restent la seule option "zéro Python", avec une qualité assumée comme inférieure à Docling/PaddleOCR sur les documents complexes.

Pour le mapping segment-parlé→position nécessaire au surlignage synchronisé, pdf.js expose nativement des items de texte positionnés (matrice de transformation convertible en bbox via `viewport.convertToPdfPoint()`), ce qui permet de reconstruire un mapping phrase→bbox si l'on conserve les offsets de caractères pendant la segmentation ; côté HTML, la bonne pratique documentée est de créer un `Range` DOM par phrase **avant** que Readability ne clone/élague le DOM, car aucune bibliothèque ne maintient automatiquement cette correspondance à travers une passe d'extraction ([blog Nutrient.io](https://www.nutrient.io/blog/pdfjs-text-highlight-annotations/)). Enfin, la normalisation du texte français avant synthèse (nombres, dates, unités, sigles, identifiants de code) n'a pas d'équivalent npm "tout-en-un" : `n2words` et `to-words` couvrent la conversion nombre→lettres, mais dates/unités/sigles/code devront être traités par des règles maison inspirées des conventions typographiques françaises documentées (espace insécable avant l'unité, mois non abrégés) — un vrai axe de développement interne plutôt qu'une brique récupérable ([GitHub forzagreen/n2words](https://github.com/forzagreen/n2words)).

## Aucun framework voix Node tout fait : s'inspirer des patterns, pas des librairies

Sur l'architecture sidecar elle-même, deux patterns coexistent chez les extensions VS Code matures qui embarquent un process lourd : soit le cœur logique tourne **in-process** dans le runtime Node de l'extension host (Continue.dev sur VS Code), soit un **process Node/binaire natif standalone** dialogue en JSON-RPC sur stdio ou socket (l'agent Cody de Sourcegraph, le binaire de rust-analyzer téléchargé dans le répertoire de l'extension, les kernels Jupyter via ZeroMQ) ([DeepWiki Continue](https://deepwiki.com/continuedev/continue/2.1-system-architecture), [npm @sourcegraph/cody-agent](https://www.npmjs.com/package/@sourcegraph/cody-agent)). Le nouvel **Agent Host** de VS Code (documenté en août 2026) formalise exactement ce problème avec un process dédié adressable en JSON-RPC (message port en local, WebSocket à distance), conçu pour survivre à la fermeture de la fenêtre et fonctionner en local, en Dev Container ou à distance — la référence la plus proche documentée d'un "un seul serveur partagé, N clients UI légers" ([VS Code docs — Agent Host](https://code.visualstudio.com/docs/agents/concepts/agent-host)). Une contrainte structurante à ne pas manquer : `ExtensionKind: "ui"` s'exécute toujours sur la machine locale de l'utilisateur, tandis que `"workspace"` s'exécute là où vit le workspace (SSH distant, WSL, conteneur, Codespaces) — tout composant qui doit produire du son sur les haut-parleurs de l'utilisateur doit donc être, ou déléguer à, un composant côté "ui", jamais au sidecar côté workspace ([VS Code docs — Remote Development](https://code.visualstudio.com/api/advanced-topics/remote-extensions)). Un piège documenté à éviter : s'appuyer sur `ELECTRON_RUN_AS_NODE` pour éviter de bundler un binaire Node fonctionne pour un spawn purement local mais casse dès que l'extension tourne contre un serveur distant non-Electron, car `server-cli.js` redirige alors le module `fs` vers `original-fs`, absent du Node de base ([issue microsoft/vscode#240901](https://github.com/microsoft/vscode/issues/240901)) — un daemon "zéro install, partout" doit bundler son propre runtime Node ou un binaire compilé par plateforme, à l'image de rust-analyzer ou Tabnine.

Sur le pipeline voix lui-même, la quasi-totalité des frameworks documentés avec précision — **Pipecat**, **RealtimeTTS/RealtimeSTT**, **Vocode**, **LiveKit Agents**, **Moshi/Unmute** de Kyutai — sont Python et donc réutilisables uniquement comme *patterns de conception*, pas comme librairies important dans du TypeScript. Le pattern à reproduire, documenté de façon convergente par Pipecat et RealtimeTTS, consiste à bufferiser les tokens LLM jusqu'à une frontière de phrase (ponctuation + garde-fous abréviations/décimales + longueur minimale ~10 caractères), lancer la synthèse de la phrase N pendant que la phrase N-1 joue encore, et traiter la détection de fin de tour (VAD + modèle sémantique/acoustique, comme chez LiveKit) comme une préoccupation séparée du découpage en phrases ([Pipecat docs](https://docs.pipecat.ai/pipecat/learn/text-to-speech), [LiveKit turn detection](https://docs.livekit.io/agents/v1/build/turn-detection/configuration/)). Le protocole **Wyoming** (MIT, JSONL + PCM sur TCP, utilisé par Home Assistant) est l'analogue transport le plus proche, agnostique au langage et simple à réimplémenter nativement en Node pour orchestrer wake-word/STT/TTS entre process. Pour la conversation vocale avec un agent, **VoiceMode** reste la référence à imiter dans son principe : exposer la voix comme un **outil MCP explicite** que l'agent appelle de sa propre initiative, plutôt qu'un hook externe qui relaierait tout texte vers le TTS indépendamment du jugement de l'agent — sans confirmation trouvée, cependant, qu'il propose aussi un mode par hook Claude Code.

## Vérifier un pipeline TTS sans oreille humaine reste un chantier CI séparé

La combinaison standard 2025-2026 pour une vérification automatique existe et est documentée : un **WER/CER** calculé avec le paquet Python `jiwer` en transcrivant l'audio synthétisé via un ASR de référence (idéalement `distil-large-v3-fr` pour le français), complété par un prédicteur de naturalité (**UTMOS/UTMOSv2**, **NISQA**, **DNSMOS**) et une similarité de locuteur par embeddings (**ECAPA-TDNN**, **RawNet3**). Le toolkit **`open-tts-eval`** (Inworld AI, à vérifier en détail) package déjà cette combinaison hors-ligne ([GitHub inworld-ai/open-tts-eval](https://github.com/inworld-ai/open-tts-eval)). Deux réserves méthodologiques sourcées doivent être retenues : le WER/CER hérite des propres erreurs de l'ASR de vérification, ce qui impose de figer un moteur ASR de référence versionné plutôt que de le changer entre deux exécutions de la suite de tests ; et aucun prédicteur MOS (UTMOS/NISQA/DNSMOS) n'a de binding Node natif confirmé — tous nécessitent Python/PyTorch, ce qui en fait une étape de CI séparée plutôt qu'une dépendance runtime du daemon Node. Aucune source, dans cette recherche ni dans les six autres notes, ne documente une comparaison de ces prédicteurs MOS spécifiquement sur du français — un point à valider empiriquement avant de faire confiance à un score de naturalité sur des voix françaises.

Avant de trancher l'ADR-012 (daemon + lecture native vs réécriture Rust), plusieurs questions doivent être réglées avec une preuve directe plutôt qu'une inférence : le comportement réel du bit d'activation Chromium dans un webview VS Code à travers un cycle `retainContextWhenHidden` hidden→shown n'a été confirmé par aucune documentation officielle et mérite un test direct plutôt qu'une hypothèse ; la faisabilité et la latence réelle d'un mpv bundlé piloté par IPC sur les trois OS (y compris sous PipeWire/Wayland, session audio Windows 11, sandbox macOS) n'a fait l'objet d'aucune recherche dédiée dans ce lot de notes ; le statut légal exact d'espeak-ng et de piper1-gpl utilisés comme *processus externes spawnés* plutôt que comme bibliothèques liées (la distinction qui détermine si la GPL "contamine" ou non le daemon MIT) doit être validé avec un juriste plutôt que déduit ; la licence de `node-web-audio-api` n'a pas été confirmée alors qu'il reste la seule alternative native crédible à mpv ; et la performance CPU réelle de Kyutai STT/TTS en français — actuellement documentée seulement sur GPU L40S — doit être mesurée localement avant de la retenir comme cible "streaming premium". Sur ce dernier point comme sur le choix Node-daemon-plus-binaires-spawnés versus une réécriture native en Rust, la research ne tranche pas : elle confirme seulement qu'aucune brique existante ne résout la lecture audio native gapless avec surlignage, ce qui signifie que le coût d'ingénierie de cette fonctionnalité sera comparable dans les deux architectures, et que le choix Rust vs Node devrait donc se décider sur d'autres critères (empreinte mémoire, packaging multi-plateforme via `vsce --target`, accès aux bindings napi-rs pour `rodio`/`cpal` non encore éprouvés en production) plutôt que sur la disponibilité de briques prêtes à l'emploi.
