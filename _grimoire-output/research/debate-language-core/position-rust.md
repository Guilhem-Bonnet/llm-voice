# Position — pour un Core en Rust

> Débat structuré ADR-012 (daemon audio local). Avocat : Rust. Rôle : bâtir le dossier le plus solide possible pour Rust, et lister honnêtement où Rust perd. Sources citées ; aucun chiffre inventé — ce qui n'est pas confirmé est marqué **non vérifié**.

## 1. Thèse en 5 lignes

Le nœud dur de LLM Voice — lecture audio native gapless avec pause/reprise/position hors webview — n'a **aucune brique Node "zero-compile" satisfaisante** : les addons natifs Node (`node-speaker`, `naudiodon`) exigent `node-gyp`, `audify` n'expose ni pause ni seek, et même `node-web-audio-api` (déjà du Rust sous NAPI) doit recomposer un vrai pause/resume par-dessus `AudioContext.suspend()/resume()`. Puisque ce développement est neuf dans les deux cas (research §"Aucun projet ne documente ce pattern"), autant l'écrire directement dans le langage qui a l'écosystème audio bas-niveau le plus mûr (`cpal`/`rodio`), le meilleur accès aux runtimes d'inférence locale (`sherpa-onnx` a maintenant des bindings Rust **officiels**), un binaire unique sans runtime à embarquer (pas de Node.js à bundler pour contourner le piège `ELECTRON_RUN_AS_NODE`/`original-fs` documenté en remote), et un empreinte mémoire/démarrage nettement inférieure pour un daemon qui doit tourner en permanence en tâche de fond sur la machine de l'utilisateur. Le prix : un rewrite du pipeline TS existant (956 tests unitaires, ~100 Ko pour le seul `Pipeline.ts`) et une productivité d'agents IA (Claude) probablement moindre en Rust qu'en TypeScript, faute de retour d'expérience direct comparable. La proposition n'est donc pas "tout réécrire" mais un **Core Rust minimal (audio + inférence locale) exposé en HTTP/WS**, le reste (segmentation, cache, orchestration profils, UI) restant en TypeScript côté extension.

## 2. Preuves citées par critère

### Performance / latence audio
- Le nœud dur documenté par la recherche projet (`lecture-audio-native.md`) est qu'aucune option Node "zero-compile" ne couvre pause+resume+seek+position : `audify` (RtAudio) n'a que `start()`/`stop()` et un `streamTime` en lecture seule ; `node-web-audio-api` (déjà un binding Rust/NAPI) n'a pas de `pause()` par source individuelle, seulement `AudioContext.suspend()/resume()` global + recomposition manuelle d'un offset pour le seek.
- `cpal` gère nativement play/pause et l'accès au buffer/horloge du flux ; l'écosystème documente un crate dédié `rodio_playback_position` pour un suivi de position par interpolation d'échantillons ([RustAudio/cpal](https://github.com/RustAudio/cpal), [rodio_playback_position sur docs.rs](https://docs.rs/rodio_playback_position/latest/rodio_playback_position/)). Un vrai pause/resume "gapless" au niveau du callback audio (sortie de silence sans consommer la file, reprise exacte) est un pattern documenté dans l'écosystème Rust en 2025-2026, y compris avec fade sur pause/resume ([recherche 2026](https://github.com/radiosilence/koan/pull/431)).
- Note honnête : `rodio` a son moteur central en cours de réécriture au moment de la recherche ("fonctionne mais sous-documenté, au moins un mois de travail restant" — 2025-2026, source secondaire, à re-vérifier avant de s'engager dessus en dépendance directe).
- Empreinte : RSS idle mesuré/rapporté ≈2 Mo pour un binaire Rust contre ≈46 Mo pour un process Node comparable ; démarrage à froid de l'ordre de 1-5 ms pour Rust contre 100-500 ms pour Node ([Rust vs Node.js 2026, mgsoftware.nl](https://www.mgsoftware.nl/en/vergelijking/rust-vs-nodejs)). Ces chiffres proviennent d'articles de blog non académiques (méthodologie non détaillée) — à traiter comme indicatifs, pas comme un benchmark propre au cas d'usage LLM Voice.

### Écosystème IA locale (TTS/STT/inférence)
- **sherpa-onnx a désormais des bindings Rust officiels** (le crate tiers `sherpa-rs` est marqué déprécié au profit de l'API Rust officielle en amont), sous licence MIT, couvrant TTS/STT/VAD/diarisation/speaker-ID sur Windows/Linux/macOS ([crates.io sherpa-rs](https://crates.io/crates/sherpa-rs/0.4.0), [thewh1teagle/sherpa-rs](https://github.com/thewh1teagle/sherpa-rs)) — c'est la même brique pivot déjà retenue côté recherche produit (`Briques existantes pour LLM Voice.md`), mais consommée nativement sans traverser une couche N-API tierce.
- `whisper-rs` (bindings Rust vers whisper.cpp) et `candle` (framework ML Rust, HuggingFace, avec un module Whisper intégré) donnent deux voies indépendantes pour le STT local à venir, sans dépendre d'un runtime Python ([candle-transformers whisper](https://docs.rs/candle-transformers/latest/candle_transformers/models/whisper/index.html)).
- `ort` (wrapper Rust d'ONNX Runtime) est documenté comme offrant des perfs "3-5x plus rapides et 60-80% moins de mémoire" que l'équivalent Python pour de l'inférence ONNX en production — chiffre non ré-audité indépendamment, source non académique.
- Un crate émergent `any-tts` (Candle) propose une API unique pour Kokoro et plusieurs autres modèles TTS avec sélection automatique CPU/CUDA/Metal, mais **sans binding Node confirmé** — argument qui joue en faveur d'un Core Rust natif plutôt que d'aller chercher cette brique depuis Node.
- Non résolu dans les deux langages : le retrait du backend ROCm côté ONNX Runtime serveur à partir de la version 1.23 (au profit de MIGraphX) touche `onnxruntime-node` **et** tout binding Rust basé sur le même ONNX Runtime — ce n'est donc pas un point de différenciation Rust/Node.

### Lecture audio native (hors webview)
- Confirmé par la recherche projet : aucune source ne documente une implémentation existante (VS Code ou Electron) du pattern gapless + position pour surlignage — développement neuf dans les deux architectures. La question n'est donc pas "quelle brique existe déjà" mais "quel écosystème bas-niveau est le plus mûr pour l'écrire" : `cpal`/`rodio` a une communauté et une historique (RustAudio) que Node n'a pas au même niveau pour du contrôle PCM fin sans compilation utilisateur.
- Alternative de repli identique dans les deux langages : spawn de `mpv` en sous-processus piloté par IPC JSON — cette option ne dépend pas du choix Rust/TS et reste la voie la plus robuste documentée pour pause/resume/seek/position ([mpv manual](https://mpv.io/manual/master/)).
- PipeWire/Linux : `cpal` documente explicitement le cas où PipeWire/PulseAudio tient le device ALSA par défaut en exclusif, provoquant un `DeviceBusy` sur une seconde tentative d'ouverture via le host ALSA, et rappelle qu'ALSA reste nécessaire même derrière JACK/PipeWire/PulseAudio ([RustAudio/cpal](https://github.com/RustAudio/cpal)) — un problème connu et documenté, donc anticipable, plutôt qu'un angle mort côté Rust. Aucune source trouvée sur un problème équivalent (ou son absence) côté Node/`node-web-audio-api` sous PipeWire — non comparable faute de données symétriques.

### Packaging multi-plateforme
- `vsce package --target` impose de toute façon une matrice d'au moins cinq cibles réalistes (`win32-x64`, `linux-x64`, `linux-arm64`, `darwin-x64`, `darwin-arm64`) dès qu'un binaire natif est embarqué — **ce coût existe déjà, que le binaire soit un addon Node natif (napi-rs/N-API) ou un daemon Rust autonome** ([Publishing Extensions, VS Code docs](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)). Rust ne l'aggrave pas : `cross-rs` fournit une cross-compilation "zero setup" pour Linux (GNU/musl), Windows et macOS, avec des actions GitHub prêtes à l'emploi (`houseabsolute/actions-rust-cross`) pour driver une matrice CI ([cross-rs/cross](https://github.com/cross-rs/cross), [actions-rust-cross](https://github.com/houseabsolute/actions-rust-cross)).
- Un daemon Rust compilé est un **binaire unique statiquement liable**, sans runtime Node à embarquer séparément — ce qui évite le piège documenté `ELECTRON_RUN_AS_NODE` (fonctionne en spawn local mais casse en remote non-Electron car `server-cli.js` redirige `fs` vers `original-fs`, absent du Node de base — [vscode#240901](https://github.com/microsoft/vscode/issues/240901)), déjà noté dans la recherche produit comme un piège à éviter pour "un daemon zéro-install partout". Un Core Rust supprime structurellement ce risque : il n'y a pas de second runtime Node à gérer pour le sidecar.
- Taille : ordre de grandeur rapporté de 2-5 Mo pour un binaire Rust simple (contre 200-500 Mo pour une image Node avec dépendances en conteneur — comparaison non directement transposable à un binaire embarqué dans un VSIX, à re-mesurer sur le binaire réel du projet).

### Productivité des agents IA (le facteur le plus défavorable à Rust, à traiter honnêtement)
- Aucune étude contrôlée trouvée comparant directement la productivité d'agents Claude/Copilot en Rust vs TypeScript sur une tâche équivalente. Le point de comparaison le plus proche trouvé est le benchmark Aider polyglot, qui teste plusieurs langages (Python, JS, TS, Go, Rust, Java, C++) mais rapporte un score global par modèle, pas un score par langage — donc **inexploitable tel quel** pour trancher Rust vs TS spécifiquement.
- Anecdote citée dans la presse tech (non un benchmark contrôlé) : Jarred Sumner rapporte avoir porté ~750 000 lignes de Zig vers Rust en 11 jours avec un taux de réussite des tests de 99,8% via des "Dynamic Workflows" — preuve que des agents LLM peuvent conduire un rewrite Rust à grande échelle avec succès, mais un seul cas, un seul auteur, pas de comparatif contre un rewrite TS équivalent.
- Le facteur objectif qui pénalise Rust ici : le compilateur Rust est plus strict (borrow checker, lifetimes), ce qui produit généralement plus d'itérations de compilation/correction par un agent qu'en TypeScript — non chiffré dans les sources trouvées pour ce projet précis, à traiter comme un coût réel mais non mesuré.
- Contrepoint favorable à Rust : le compilateur agit comme un filtre de correction automatique — une classe entière de bugs (use-after-free, data race, null deref) que le TypeScript ne détecte pas à la compilation est rejetée avant même l'exécution, ce qui peut réduire le nombre de tours de debug-en-production nécessaires à un agent, au prix de plus de tours de debug-à-la-compilation. Aucune source ne quantifie ce compromis net.

### Sécurité mémoire
- Argument à nuancer honnêtement : **TypeScript/Node est déjà mémoire-sûr** (VM V8 avec GC) — Rust n'apporte donc pas ici un gain de sécurité mémoire *par rapport à TypeScript lui-même*. L'argument mémoire-sûr ne joue que **par rapport aux alternatives C/C++** que Node devrait sinon utiliser pour l'audio bas niveau : `node-speaker` (nécessite `node-gyp` + compilateur C, code C sous-jacent non audité par cette recherche côté mémoire-sûreté) et RtAudio/`audify` (wrapper C++). Le vrai gain Rust n'est donc pas "Rust vs TypeScript" mais "Rust-safe vs bindings-C/C++-historiques" pour la même fonctionnalité audio bas niveau.
- Chiffres généraux (hors-projet, contexte de l'industrie, à ne pas surinterpréter pour ce cas précis) : Microsoft rapporte qu'environ 70% des CVE qu'elle assigne chaque année sont des problèmes de sécurité mémoire ; Google rapporte le même ordre de grandeur (~70%) pour les bugs sérieux de sécurité de Chrome ; l'adoption de Rust dans Android a fait chuter la part des vulnérabilités mémoire de 76% (2019) à une valeur attendue de 24% (fin 2024), avec une densité de vulnérabilités mémoire rapportée 1000x inférieure au code C/C++ équivalent ([The Hacker News, nov. 2025](https://thehackernews.com/2025/11/rust-adoption-drives-android-memory.html), [Dark Reading](https://www.darkreading.com/application-security/google-microsoft-take-refuge-in-rust-languages-better-security)). Ces chiffres concernent des bases de code C/C++ historiques à très grande échelle (Android, Chrome) — pas un daemon Node de la taille de LLM Voice ; à citer comme contexte industriel, pas comme preuve directe applicable ici.

### Réutilisation du code existant
- Défavorable à Rust : le pipeline (`Pipeline.ts`, ~100 Ko), les providers TTS (`SystemTtsProvider.ts` 36 Ko, `ChatterboxProvider.ts` 20 Ko, `PiperSetup.ts` 16 Ko), la lecture (`AudioQueue.ts` 24 Ko, `PlaybackController.ts` 20 Ko), le segmenteur, le cache disque et le registre de profils sont déjà en TypeScript "vscode-free" testable (fait confirmé par le contexte projet : 956 tests unitaires + 63 tests d'intégration headless). Aucun de ce code n'est directement réutilisable en Rust — c'est un rewrite, pas un port mécanique.
- Favorable à un Core Rust *ciblé* : seule la partie qui doit de toute façon être réécrite (lecture PCM native + inférence locale bas niveau) migre ; la logique métier (segmentation de phrases, orchestration de profils, cache, gestion d'inbox) peut rester en TypeScript côté extension et parler au Core Rust par HTTP/WS — limitant le rewrite au strict périmètre où Node n'a de toute façon pas de solution mûre.

### Coût de migration
- Contrats partagés : `specta` (Rust) génère des types TypeScript par introspection de traits (approche runtime, "stable" pour la cible TS), `typeshare` fait de l'analyse statique de fichiers Rust ; les deux sont des solutions établies pour synchroniser les types Rust ↔ TypeScript sans dupliquer les schémas à la main ([docs.rs/specta](https://docs.rs/specta), [comparatif specta/typeshare](https://docs.rs/specta)) — donc le risque de dérive de contrat entre l'extension TS et le Core Rust est outillable, pas un point bloquant, mais c'est un outillage supplémentaire à mettre en place et maintenir (non requis dans une architecture 100% TS).
- Parité de tests : 956 tests unitaires + 63 tests d'intégration headless existants ne migrent pas automatiquement — un Core Rust nécessite sa propre suite (`cargo test`) couvrant au minimum le pause/resume/position/gapless et les providers TTS locaux repris, en parallèle de la suite TS existante qui continue de couvrir la logique métier restée en TS. C'est un effort de test dupliqué, non chiffré.
- Spawn et mise à jour du binaire : le pattern déjà identifié par la recherche produit (rust-analyzer, Tabnine — téléchargement d'un binaire par plateforme dans le répertoire de l'extension) est directement transposable pour distribuer et mettre à jour le Core Rust, sans mécanisme nouveau à inventer.
- Cas remote/SSH/WSL : la contrainte déjà documentée par la recherche produit s'applique identiquement quel que soit le langage du Core — `ExtensionKind: "ui"` s'exécute toujours côté machine locale de l'utilisateur, donc le composant qui produit du son doit être, ou déléguer à, un composant "ui" local, jamais au sidecar "workspace" distant ([VS Code docs — Remote Development](https://code.visualstudio.com/api/advanced-topics/remote-extensions)). Un Core Rust n'a pas plus (ni moins) de mal que du Node à respecter cette contrainte, à condition d'être spawné côté "ui".

### Maintenance
- Un seul binaire statique par plateforme, sans dépendance à un runtime Node à maintenir en parallèle du VS Code embarqué, réduit la surface de "quelle version de Node/Electron est disponible côté hôte" — pertinent vu le piège `ELECTRON_RUN_AS_NODE`/`original-fs` déjà documenté par la recherche produit.
- Contrepartie : deux écosystèmes de dépendances à surveiller pour les CVE (npm côté extension, crates.io côté Core) au lieu d'un seul, et deux toolchains CI à maintenir (Node + Rust) au lieu d'une.

## 3. Plan de migration réaliste

Le rewrite complet du pipeline en Rust n'est **pas** recommandé par cette position : le périmètre où Rust apporte un avantage net et non contesté par la recherche est étroit (audio bas niveau + inférence locale), et le reste du code TS existant est déjà testé et vscode-free. Plan par étapes :

1. **Étape 0 — spike isolé, avant tout code produit** : prototype Rust autonome (hors extension) validant `cpal`/`rodio` pour pause/resume/position/gapless sur les 3 OS cibles (au minimum Linux/PipeWire en premier, machine de dev). Sortie attendue : confirmer ou infirmer que `cpal`/`rodio` couvre réellement le besoin sans repasser par un spawn `mpv`. Gate : si le spike échoue, retomber sur `mpv` piloté par IPC (option neutre au choix de langage).
2. **Étape 1 — Core Rust minimal** : un seul binaire, `axum`/`tokio` pour HTTP+WebSocket localhost, exposant : lecture PCM (play/pause/resume/seek/position), enchaînement gapless de chunks, et un client HTTP simple vers Ollama et vers un serveur Chatterbox externe (pas de logique métier, pas de segmentation — juste transport et lecture). Contrats définis en Rust et exportés vers TypeScript via `specta` ou `typeshare`.
3. **Étape 2 — intégration TTS locale native** : brancher `sherpa-onnx` (bindings Rust officiels) dans le Core pour Piper/sherpa-onnx en in-process, en gardant Chatterbox et les voix système en HTTP/sous-processus externes (aucun changement d'architecture pour eux).
4. **Étape 3 — bascule de l'extension** : `PlaybackController`/`AudioQueue` côté TypeScript deviennent des clients HTTP/WS minces vers le Core, au lieu de gérer la lecture eux-mêmes. `Pipeline.ts`, le segmenteur, le cache disque, le registre de profils, l'inbox, la détection de mode Auto (logprobs Ollama) **restent en TypeScript** — aucune raison technique de les migrer, ce sont des invariants produit (P0 provider-agnostic) et une logique métier, pas du bas-niveau.
5. **Étape 4 — parité de tests avant retrait de l'ancien code** : suite `cargo test` sur le Core (pause/resume/position/gapless, providers repris) + tests d'intégration headless mis à jour pour taper sur le Core via HTTP plutôt que d'appeler `AudioQueue` en direct, avant de supprimer l'implémentation TS de lecture devenue obsolète.
6. **Étape 5 (plus tard, hors périmètre "maintenant")** : STT (`whisper-rs`/`candle`/`sherpa-onnx`), VAD, dans le même Core Rust déjà en place — coût marginal plus faible qu'une intégration Node équivalente puisque l'écosystème d'inférence locale Rust est déjà en place à ce stade.

Ce qui reste en TypeScript dans tous les cas : `Pipeline.ts`, segmentation, cache, registre de profils, inbox, extension host, UI/webview, logique de mode Auto, ingestion de documents (PDF/DOCX/HTML — pas de gain Rust identifié par la recherche produit sur ce point, `pdfjs-dist`/`mammoth`/`officeParser` restent la meilleure pile).

## 4. Concessions — où Go et TypeScript gagnent

- **TypeScript gagne sur la productivité des agents IA aujourd'hui.** C'est le point le plus lourd contre Rust dans ce projet précis : l'équipe de fait est "un humain + agents Claude écrivant la majorité du code", et aucune source trouvée ne confirme que Claude est aussi productif/fiable en Rust qu'en TypeScript sur ce type de tâche. Le compilateur Rust plus strict signifie probablement plus d'itérations de correction par tâche — coût réel, non chiffré, à absorber.
- **TypeScript gagne sur la continuité avec l'existant.** 956 tests unitaires + 63 tests d'intégration headless sont un actif direct en TS ; un Core Rust part de zéro sur son périmètre, quel que soit le langage choisi pour le reste.
- **TypeScript gagne sur le nombre de contributeurs potentiels et la vitesse de contribution ad hoc** (pas de compilation à installer, pas de toolchain supplémentaire) — pertinent si le projet vise des contributions externes au-delà de l'auteur unique.
- **Go serait un compromis raisonnable non retenu par cette position mais honnête à signaler** : compilation rapide, binaire statique, cross-compilation plus simple que Rust historiquement, courbe d'apprentissage plus faible pour un agent LLM (moins de règles de possession/lifetimes à satisfaire) — mais écosystème audio bas niveau et bindings ML locaux (`sherpa-onnx`, `candle`, `ort`) **structurellement moins riches en Go** d'après cette recherche (aucun équivalent Go de `sherpa-onnx`/`candle` officiel identifié dans les sources consultées) : Go perdrait précisément sur le critère qui motive le Core natif au départ (l'inférence locale).
- **Node/TypeScript gagne aussi sur le repli de secours documenté** : si le spike `cpal`/`rodio` (étape 0 du plan) échoue, la solution de repli (`mpv` en sous-processus + IPC JSON) est strictement identique en coût d'implémentation dans les deux langages — un argument Rust qui ne se matérialise pas si le spike échoue.

## 5. Faits non vérifiés (à traiter comme tels, pas comme des certitudes)

- Maturité réelle de la réécriture en cours du moteur central de `rodio` ("fonctionne mais sous-documenté, ~1 mois de travail restant" — source secondaire non datée précisément, à re-vérifier avant tout engagement de dépendance directe).
- Comportement de `cpal`/`rodio` sous Wayland spécifiquement (par opposition à PipeWire côté serveur audio) — aucune source trouvée dans cette recherche.
- Licence exacte et matrice de plateformes prébuildées d'`audify` (page npm inaccessible pendant la recherche produit antérieure — non revérifié ici).
- Chiffres de taille de binaire/RSS/cold-start Rust vs Node cités plus haut proviennent de blogs non académiques à méthodologie non documentée — indicatifs, pas mesurés sur le Core LLM Voice réel.
- Aucune étude contrôlée comparant directement la productivité d'agents Claude/Copilot en Rust vs TypeScript sur une tâche de taille comparable à ce projet — l'anecdote Zig→Rust (Jarred Sumner, 750k lignes, 11 jours, 99,8% de tests passants) est un cas unique, non un benchmark.
- Existence ou non d'un équivalent Go officiel à `sherpa-onnx`/`candle` : affirmé absent d'après les sources consultées dans cette recherche, mais aucune recherche dédiée "sherpa-onnx Go bindings" n'a été menée pour le confirmer formellement.
- Impact réel en tours de compilation/correction supplémentaires pour un agent Claude travaillant en Rust vs TypeScript sur ce projet précis — non mesuré, seulement inféré du fonctionnement connu du borrow checker.
- Le lien entre les statistiques mémoire-sûreté Android/Chrome (70% de CVE, 1000x de réduction de densité) et un daemon Node/TypeScript de la taille de LLM Voice n'est pas établi par les sources — ce sont des bases de code C/C++ à très grande échelle, pas un point de comparaison direct.
