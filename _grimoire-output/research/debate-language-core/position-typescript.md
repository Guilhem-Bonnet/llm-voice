# Position TypeScript/Node — LLM Voice Core (daemon local)

## 1. Thèse (5 lignes)

Le daemon local doit rester en **TypeScript sur Node 22**, avec au plus un **module natif Rust (napi-rs)** cantonné à la lecture audio si le sous-processus `mpv` s'avère insuffisant. 65 % des lignes et 82 % des fichiers de test de `vscode-extension/src` sont déjà du Node pur, sans dépendance à `vscode` : les faire tourner dans un daemon est un déplacement de frontière de processus, pas une réécriture. L'écosystème IA locale visé (Ollama HTTP, MCP officiel, sherpa-onnx) est soit HTTP-agnostique au langage, soit distribué avec des bindings Node de première classe. Le risque réel n'est pas la performance (aucune preuve que Node introduise une latence audible pour du TTS par chunks de phrases) mais l'axe audio bas niveau, où Node n'a pas de solution "zero-compile" mature — d'où l'option hybride plutôt qu'un dogme "tout TS". Migrer vers Rust/Go maintenant coûterait la réécriture de ~11 200 lignes de logique déjà testée pour un gain non chiffré face à un besoin (chunks TTS de quelques centaines de ms, pas de l'audio pro temps réel sample-accurate).

## 2. Preuves citées par critère

### Performance / latence audio

- Le pipeline visé n'est **pas** de l'audio temps réel échantillon par échantillon : c'est du chaînage gapless de chunks TTS (phrases) avec pause/resume/seek. Pipecat et RealtimeTTS, les deux pipelines de production documentés, tolèrent ~200-300 ms de latence de bufferisation par phrase et atteignent un end-to-end "souvent sous 200 ms" en mode phrase — sur des runtimes Python, pas même Node ([Pipecat docs — Text to Speech](https://docs.pipecat.ai/pipecat/learn/text-to-speech), [futureagi.com — Optimize Pipecat Voice Agent Latency](https://futureagi.com/blog/how-to-optimize-pipecat-latency-2026/)). Un budget de latence à cette échelle absorbe largement la gigue GC de Node.
- Le GC de Node peut introduire des pauses qui dégradent un flux audio **temps réel bas niveau** (thread audio interagissant avec le thread principal) — c'est un fait générique documenté depuis longtemps, pas spécifique à ce projet ([échange W3C Web Audio, Chris Rogers/Google](https://lists.w3.org/Archives/Public/public-audio/2012JulSep/0461.html) ; synthèses généralistes sur GC/latence event-loop). C'est précisément pourquoi ce projet ne fait **pas** de génération de forme d'onde en JS : il délègue la lecture à `mpv` (sous-processus C natif) ou à un futur module Rust — Node ne touche jamais l'échantillon audio lui-même dans ce plan.
- Aucune source de cette recherche ni de la veille antérieure ne mesure une latence audio comparée Node vs Rust/Go **pour ce cas d'usage précis** (chunks de phrase, sous-processus mpv) — à traiter comme non chiffré, dans un sens comme dans l'autre.
- Chiffres génériques Node vs Rust/Go trouvés concernent des **API HTTP serveur** (débit req/s, RAM par requête), pas un daemon audio local mono-utilisateur : Rust Axum ~18,3 Mo RAM vs Go Gin ~27,6 Mo, écart de débit ~30 % ([Markaicode](https://markaicode.com/vs/typescript-vs-rust/), [WriterDock](https://writerdock.in/blog/go-vs-rust-for-microservices-a-2026-performance-benchmark)) ; ces écarts existent mais leur pertinence pour un daemon localhost, un seul client, appelé en rafale de quelques requêtes par minute, n'est pas démontrée par ces sources.

### Écosystème IA locale (verrou du critère)

- **sherpa-onnx** publie des addons Node N-API **prébuildés par plateforme** sur npm — donc zéro compilation utilisateur, cohérent avec l'invariant "zéro install" du projet (note de veille `tts-locaux.md`, confirmé par [k2-fsa/sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)).
- **Ollama** est un serveur HTTP local : le client n'a aucune contrainte de langage, TypeScript n'a donc rien à perdre ici.
- Le **SDK MCP officiel** (`@modelcontextprotocol/sdk`) pour le futur serveur MCP Claude Code est écrit et maintenu en TypeScript par l'organisation MCP elle-même — l'écrire en Rust/Go signifierait réimplémenter un protocole que l'écosystème de référence fournit déjà "gratuitement" en TS ([modelcontextprotocol/typescript-sdk](https://github.com/modelcontextprotocol/typescript-sdk)).
- À l'inverse (concession), les moteurs "SOTA" les plus qualitatifs (XTTS-v2, Chatterbox natif, F5-TTS, Fish Speech, CosyVoice) sont **tous Python/PyTorch** sans binding Node officiel — ils resteront des sidecars HTTP quel que soit le langage du daemon, donc ce critère est neutre pour eux (note de veille `tts-locaux.md`).
- L'ingestion documentaire visée plus tard (pdf.js, mammoth, Readability) est nativement Node — un daemon Rust/Go devrait soit réimplémenter ces parseurs, soit les faire tourner dans un sidecar Node de toute façon, ce qui ruinerait l'argument "un seul langage" en faveur de Rust/Go (note de veille, confirmé par le CdC).

### Lecture audio native (le vrai point dur, indépendant du langage)

- **Aucune option Node "zero-compile" ne couvre pause + resume + seek + position** proprement : `node-speaker`/`naudiodon` exigent `node-gyp` (compilateur natif côté utilisateur) ; `audify` (RtAudio) a des prébuilds N-API mais **pas de pause ni de seek**, seulement start/stop + `streamTime` lecture seule ; `node-web-audio-api` (Rust/NAPI, prébuildé Windows/macOS/Linux x64+arm64) est maintenue en 2026 mais son modèle Web Audio n'a pas de `pause()` par source — il faut `AudioContext.suspend()/resume()` + recalcul d'offset pour le seek, une couche applicative à écrire dans tous les cas (note de veille `lecture-audio-native.md`, [node-web-audio-api](https://github.com/ircam-ismm/node-web-audio-api)).
- **mpv en sous-processus piloté par IPC** reste la seule voie qui donne pause/resume/seek/position **sans aucune compilation**, quel que soit le langage du daemon qui le pilote — Node, Rust ou Go spawnent tous `mpv` de la même façon via un pipe JSON ([mpv manual](https://mpv.io/manual/master/)). **Ce point ne favorise donc ni TypeScript ni Rust** : c'est un argument neutre, pas un point pour Node.
- Conséquence honnête : si `mpv` s'avère insuffisant (résolution fine du gapless, latence de démarrage, disponibilité garantie sur l'utilisateur cible), la seule alternative documentée avec prébuilds actifs est du **Rust via napi-rs** (`rodio`/`cpal`/`kira`) — aucun projet combinant concrètement l'un de ces crates avec napi-rs pour une extension VS Code n'a été trouvé, c'est un développement neuf dans les deux langages, mais l'outillage de packaging (napi-rs) est mûr : CI/CD prêt à l'emploi pour Windows/Linux/macOS/FreeBSD, flags `--use-napi-cross` documentés pour la cross-compilation ([napi-rs cross-build docs](https://napi.rs/docs/cross-build.en), [napi-rs GitHub](https://github.com/napi-rs/napi-rs)). **C'est l'argument central de l'option hybride : pas besoin de choisir Rust pour tout le daemon pour bénéficier de Rust là où il compte.**

### Packaging multi-plateforme

- `vsce package --target` supporte nativement `win32-x64/arm64`, `linux-x64/arm64/armhf`, `alpine-x64/arm64`, `darwin-x64/arm64`, `web` — la Marketplace sert automatiquement le bon binaire par plateforme ([VS Code docs — Publishing Extensions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)). Ce mécanisme est **identique que le binaire embarqué soit un module Rust (napi-rs) ou un exécutable Node SEA** — le coût de matrice CI est le même dans les deux cas, donc ce critère ne départage pas TS vs Rust/Go en soi.
- **Node SEA** (stable depuis Node 22, amélioré en Node 24/26) permet de compiler l'appli Node en un binaire natif unique sans Node/npm/`node_modules` visibles, à condition de bundler en un seul fichier CommonJS au préalable (esbuild/rollup) — donc un chemin "zéro install" existe pour Node lui-même, pas seulement pour un module natif ([Node.js docs — Single executable applications](https://nodejs.org/api/single-executable-applications.html), [notes.billmill.org — esbuild + SEA](https://notes.billmill.org/programming/javascript/Making_a_single-file_executable_with_node_and_esbuild.html)).
- Alternative déjà documentée dans la veille projet : réutiliser le Node embarqué de VS Code via `process.execPath`/`ELECTRON_RUN_AS_NODE` évite même d'embarquer un runtime — **mais c'est une voie fragile** : VS Code lui-même a un ticket ouvert pour "éliminer le besoin d'`ELECTRON_RUN_AS_NODE`" ([microsoft/vscode#137510](https://github.com/microsoft/vscode/issues/137510)), la variable fuit vers les sous-processus enfants et casse du code qui dépend d'Electron ou qui tourne sous Remote/WSL contre un serveur Node "vanilla" (le `server-cli.js` distant mappe `fs` vers `original-fs`, un module absent d'un Node standard — trouvé dans la note de veille `architectures-et-dialogue-vocal.md`, [microsoft/vscode#240901](https://github.com/microsoft/vscode/issues/240901)). **Conclusion honnête : ni Node SEA ni le Node d'Electron ne sont un solved problem — mais SEA est la voie la plus robuste et est spécifique à Node**, donc c'est un point pour TS (Go et Rust produisent un binaire natif nativement, sans avoir besoin d'un mécanisme équivalent à SEA — voir concessions).

### Productivité des agents IA de codage

- Rust a un **coût d'apprentissage documenté même pour les humains** (83 % des développeurs le trouvent difficile, 42 % s'inquiètent du temps avant productivité, cité par [Markaicode — TypeScript vs Rust](https://markaicode.com/vs/typescript-vs-rust/)) ; rien ne montre que les agents de codage LLM s'en sortent mieux structurellement que sur un langage à garbage collector et à surface syntaxique plus petite.
- Les benchmarks agentiques dédiés à Rust sont **récents et encore rares** : `Rust-SWE-bench` n'a été introduit que très récemment faute de benchmark repository-level pour Rust ([arxiv 2602.22764](https://arxiv.org/html/2602.22764v1)), ce qui est cohérent avec un corpus d'entraînement et un outillage agentique historiquement plus riches pour TypeScript/JavaScript (écosystème npm, volumes de code bien plus importants) — **c'est une inférence, pas une mesure directe de la qualité produite par les agents sur ce projet précis**.
- Aucune étude trouvée dans cette recherche ne mesure directement "taux de succès d'un agent Claude/Copilot sur une tâche TypeScript" vs "la même tâche en Rust" à effort constant — à traiter comme un vrai trou, pas comme tranché en faveur de TS malgré l'indice ci-dessus.
- Fait projet (donné, non re-dérivé) : l'équipe est "un humain (préférence Rust) + agents IA qui écrivent la majorité du code" — l'agent, pas l'humain, est le principal producteur de code au quotidien, ce qui pondère cet argument en faveur de TS plus que si l'humain codait lui-même.

### Sûreté

- La supply chain **npm** a connu en 2025-2026 des incidents sérieux et documentés : le ver **Shai-Hulud** (sept. 2025, >500 paquets compromis dont `@ctrl/tinycolor` à plus de 2M téléchargements/semaine) et sa suite "Second Coming" (nov. 2025, 1092 versions de paquets compromises, 796 paquets, 130M téléchargements mensuels cumulés), puis **IronWorm** (juin 2026) — qui a justement abandonné le JS interprété pour un **binaire Rust compilé de 976 Ko avec rootkit eBPF** afin d'échapper à la détection ([Microsoft Security Blog — ChainDrop/IronWorm](https://www.microsoft.com/en-us/security/blog/2026/08/04/chaindrop-supply-chain-compromise-anatomy-self-propagating-worm/), [Snyk — node-gyp compromise](https://snyk.io/blog/node-gyp-supply-chain-compromise-self-propagating-npm-worm-binding-gyp/)). **Point honnête** : c'est un vrai risque pour un projet Node avec beaucoup de dépendances, et npm v12 (juillet 2026) a dû bloquer les scripts d'installation par défaut en réponse.
- Contre-point tout aussi honnête : **IronWorm prouve que "écrire le binaire final en Rust" ne protège pas de la supply chain npm** — le vecteur d'attaque est le *registre de paquets et les scripts d'installation*, pas le langage cible ; un daemon Rust distribué via npm (ou construit avec des dépendances `cargo` tout aussi sujettes à compromission — voir `cargo`/crates.io, non recherché ici) n'est pas intrinsèquement plus sûr. La mitigation réelle (verrouillage des lockfiles, `npm ci`, désactivation des scripts d'installation, réduction du nombre de dépendances) est indépendante du langage du daemon.
- Non vérifié dans cette recherche : fréquence/gravité comparée des incidents sur crates.io (Rust) ou le module ecosystem Go — à ne pas présumer plus sûr sans preuve.

- Sur 956 tests unitaires + 63 tests d'intégration headless (fait projet donné), la répartition ci-dessus indique que la **grande majorité des suites de test sont déjà des suites vitest sans dépendance à `vscode`** : elles continueraient de s'exécuter à l'identique contre le code métier déplacé dans un daemon Node (aucune réécriture de harness, aucun portage vers un framework de test différent).
- **Conséquence directe** : basculer le cœur logique (TTS providers, parsing, chunking, gestion de cache, client Ollama) vers Rust/Go signifierait réécrire l'essentiel de ces ~11 200 lignes de logique **et** re-porter ou dupliquer ~11 700 lignes de tests vers un framework différent (aucun de ces tests ne "se traduit" automatiquement) — un coût qui n'existe pas dans l'option TypeScript, où seule la frontière IPC (extension ↔ daemon) est du code réellement neuf.
- Dossiers concrets déjà "prêts daemon" (aucun import `vscode` détecté dans leur périmètre principal) : `src/tts/` (ChatterboxProvider 16,6K, SystemTtsProvider 34,4K, OpenAICompatibleTtsProvider 7,5K, PiperSetup 12K, KokoroProvider 1,6K, ProviderRegistry 2,3K), `src/net/`, `src/parser/`, `src/pipeline/` — à vérifier fichier par fichier avant migration effective, mais la mesure agrégée ci-dessus est directement observable dans le dépôt.

### Coût de migration

- Réécrire ~11 200 lignes de logique métier + adapter ~11 700 lignes de tests vers un framework Rust (`cargo test`) ou Go (`go test`) est un chantier de plusieurs semaines minimum pour une équipe d'un humain + agents, sans gain de fonctionnalité immédiat pour l'utilisateur — coût non chiffré précisément ici (pas de données projet sur la vélocité de portage), mais son ordre de grandeur (dizaines de milliers de lignes testées) est un fait mesuré, pas une estimation.
- L'option hybride (Core TS + module Rust napi-rs pour l'audio seulement) limite ce coût à la seule zone où Rust apporte une preuve (accès bas niveau au device audio), sans toucher au reste.

### Maintenance

- Un seul langage/type-system entre l'extension VS Code et le daemon signifie des **types partagés sans codegen** (interfaces `TsRequest`, événements WebSocket, contrats de providers) — argument architectural standard, pas une mesure externe : à vérifier dans l'implémentation réelle plutôt qu'à présumer acquis.
- Le contrat le plus fragile déjà documenté dans ce projet (`shared-context.md`) — l'incompatibilité entre `OpenAICompatibleTtsProvider` et le vrai serveur Chatterbox communautaire (422 sans `model`/`voice`, forme de réponse `voices` différente, `language` ignoré sur `/v1/audio/speech`) — est un bug de **logique métier et de contrat HTTP**, pas un bug de langage : il se serait produit à l'identique en Rust ou en Go. Aucun des deux langages n'aurait empêché cette classe d'erreur.

## 3. Plan réaliste

1. **Extraire** les modules Node purs déjà identifiés (`src/tts/`, `src/net/`, `src/parser/`, `src/pipeline/`, chunking de phrases, cache Ollama) dans un paquet npm interne partagé par l'extension et un nouveau processus `daemon/`, sans changement de comportement — profite immédiatement des ~11 200 lignes et ~11 700 lignes de tests déjà mesurées.
2. **Démarrer le daemon** comme sous-processus Node bundlé (esbuild → un seul fichier CommonJS) packagé en **Node SEA** ([Node.js SEA docs](https://nodejs.org/api/single-executable-applications.html)) plutôt que de dépendre d'`ELECTRON_RUN_AS_NODE`, pour éviter la fragilité documentée en Remote/WSL ; exposer HTTP+WebSocket sur `127.0.0.1` avec un port éphémère + fichier de lock, un seul client (le pattern "un sidecar partagé par N fenêtres" est celui que documente le nouvel Agent Host de VS Code — note de veille `architectures-et-dialogue-vocal.md`).
3. **Lecture audio v1** : sous-processus `mpv` piloté par IPC JSON (pause/resume/seek/position confirmés dans la veille), zéro compilation, disponible sur les trois OS.
4. **Point de décision explicite** (spike chronométré, pas une intuition) : si `mpv` ne tient pas la latence de démarrage/gapless requise pour le surlignage synchronisé, écrire un **module natif Rust via napi-rs** (`cpal`/`rodio`) exposant `play/pause/seek/position` à Node, avec prébuilds CI par plateforme (napi-rs le supporte nativement) — c'est la seule zone du projet où le dossier Rust est aujourd'hui le plus solide, et où aucune alternative Node zero-compile mature n'existe.
5. STT/VAD plus tard : `sherpa-onnx` en addon Node prébuildé, cohérent avec le reste du daemon TS.
6. MCP server pour Claude Code : `@modelcontextprotocol/sdk` (TS officiel), même processus daemon ou processus dédié léger.

## 4. Concessions — où Rust et Go gagnent

- **Empreinte mémoire et débit bruts** : sur des benchmarks serveur HTTP génériques, Rust (Axum) et Go (Gin) battent significativement les stacks à VM géré en RAM et en req/s ([Markaicode](https://markaicode.com/vs/typescript-vs-rust/), [WriterDock](https://writerdock.in/blog/go-vs-rust-for-microservices-a-2026-performance-benchmark)) — même si la pertinence pour un daemon localhost mono-client n'est pas démontrée, l'écart existe et pourrait compter si le daemon devait un jour gérer beaucoup plus de charge concurrente.
- **Absence de pauses GC** : pour tout traitement audio bas niveau *réellement* temps réel (pas du chunk de phrase), Rust/Go (ou C++) restent le choix par défaut de l'industrie — c'est exactement pourquoi ce plan isole l'audio dans un module natif plutôt que de parier sur du Node pur.
- **Packaging natif "un seul binaire" sans étape supplémentaire** : Rust et Go compilent nativement vers un exécutable statique par plateforme depuis toujours ; Node a besoin du mécanisme SEA (stable seulement depuis peu, encore documenté comme évoluant activement de Node 22 à 26) pour obtenir un résultat équivalent — Rust/Go n'ont pas ce problème à résoudre.
- **napi-rs lui-même valide l'argument Rust pour du natif** : son outillage de cross-compilation et de prébuilds CI est mûr et taillé pour exactement ce genre de module — c'est un point pour Rust *dans son rôle de module natif*, pas pour "tout le daemon en Rust".
- **Sécurité mémoire par construction** : Rust élimine par le compilateur des classes entières de bugs mémoire qu'un module natif C/C++ (ou un binding mal écrit) pourrait introduire — pertinent seulement pour la brique audio native, pas un argument pour réécrire la logique métier HTTP/JSON qui n'a pas ce genre de risque en TypeScript.
- **Courbe d'apprentissage humaine** : si l'humain de l'équipe (qui préfère Rust) doit un jour déboguer manuellement le cœur du système sans agent IA disponible, Rust/Go avec typage plus strict au niveau mémoire peuvent réduire une classe de bugs — contrepoids à l'argument "productivité des agents", qui ne s'applique qu'au travail assisté par agent.

## 5. Faits non vérifiés / trous de recherche

- Latence audio mesurée en conditions réelles (Node+mpv vs Rust natif) pour ce pipeline précis : **non mesuré**, aucune source ne le documente pour ce cas d'usage exact.
- Comportement de l'activation utilisateur Chromium sticky bit sur un cycle hidden→shown avec `retainContextWhenHidden` dans un webview VS Code : **non documenté publiquement** (note de veille `lecture-audio-native.md`) — indépendant du langage du daemon mais affecte l'architecture globale.
- Licence exacte et matrice de plateformes prébuildées d'`audify` : **non confirmé** (page npm inaccessible pendant la veille, HTTP 403).
- Aucune mesure chiffrée trouvée du temps de build/coût CI d'une matrice `vsce --target` à 5+ cibles, ni de la taille de VSIX ajoutée par un binaire natif embarqué (Rust ou Node SEA) — **non chiffré dans les deux cas**.
- Comparaison directe et sourcée "taux de succès d'agents de codage LLM sur tâche équivalente TypeScript vs Rust" : **non trouvée** ; l'argument productivité repose sur des indices indirects (maturité de l'écosystème de benchmarks Rust, difficulté déclarée par des développeurs humains), pas sur une mesure agent-vs-agent.
- Fréquence/gravité comparée des incidents de supply chain sur crates.io (Rust) vs npm : **non recherché** dans cette passe — à ne pas présumer favorable à Rust sans vérification.
- Fichier par fichier, tous les modules listés comme "sans import vscode" dans `src/tts/`, `src/net/`, `src/parser/`, `src/pipeline/` n'ont pas été audités un par un pour d'autres couplages implicites à l'extension host (ex. `vscode.workspace.getConfiguration` appelé indirectement, chemins `context.globalStorageUri`) — seule la mesure agrégée par `grep` d'import direct a été faite ; une revue manuelle avant migration reste nécessaire.
