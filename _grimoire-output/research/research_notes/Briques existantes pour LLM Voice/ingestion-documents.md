# Ingestion "any document" → texte prêt pour la synthèse vocale (2026)

## Quelle chaîne pure-Node/WASM couvre PDF, DOCX, EPUB, HTML avec une qualité acceptable et sans Python sur la machine utilisateur ?

### Takeaway
Une chaîne 100% Node/WASM existe et fonctionne pour du texte "propre" (PDF natif, DOCX, EPUB, HTML) : `pdfjs-dist`/`unpdf` (PDF texte), `mammoth` (DOCX→HTML), `officeParser` (multi-format Node natif incl. ODT), `epub2`/`epubjs` (EPUB) et `@mozilla/readability` + `linkedom` (HTML). Mais dès qu'il faut du PDF scanné ou une extraction de très haute fidélité (tableaux complexes, mise en page multi-colonnes), les meilleurs outils (Docling, marker, MinerU, PyMuPDF, OCRmyPDF+PaddleOCR) sont tous Python — seul `tesseract.js`/`tesseract-wasm` offre un OCR pur WASM sans Python, avec une qualité inférieure aux outils Python/VLM sur les documents complexes.

### Cited Findings
- `pdfjs-dist` (Mozilla) est un renderer PDF complet en JS pur, extrait texte + annotations, alimente le lecteur PDF de Firefox, licence Apache-2.0 — [npm/GitHub](https://github.com/mozilla/pdfjs-dist/blob/master/LICENSE), [Libraries.io](https://libraries.io/npm/pdfjs-dist)
- `unpdf` (org UnJS) est un parseur PDF pur JS, zéro dépendance native, fonctionne sur Node/Deno/Bun/navigateur/Cloudflare Workers/Vercel/Lambda ; licence MIT ; décrit comme "alternative moderne activement maintenue à pdf-parse, non maintenu" — [GitHub unjs/unpdf](https://github.com/unjs/unpdf), [npm](https://www.npmjs.com/package/unpdf)
- `pdf-parse` enveloppe pdf.js avec une API minimale (texte + métadonnées + nb de pages), licence Apache-2.0 ; une source indique une dépendance au module `canvas` (bindings natifs) qui casse sur Lambda/Edge dans certaines versions — [comparatif PkgPulse](https://www.pkgpulse.com/blog/unpdf-vs-pdf-parse-vs-pdfjs-dist-pdf-parsing-extraction-nodejs-2026), [chudi.dev](https://chudi.dev/blog/serverless-pdf-processing-unpdf-vs-pdfparse)
- `mupdf` (Artifex, `mupdf.js`/WASM) fonctionne dans tous les runtimes JS (Node, Bun, navigateurs) et est réputé rapide, mais est distribué sous **AGPL-3.0-or-later** ou licence commerciale Artifex — [npm mupdf](https://www.npmjs.com/package/mupdf), [GitHub ArtifexSoftware/mupdf.js](https://github.com/ArtifexSoftware/mupdf.js/)
- `mammoth` (mwilliamson/mammoth.js) convertit DOCX→HTML en s'appuyant sur les styles sémantiques du document (Heading 1 → `<h1>`, etc.), licence **BSD-2-Clause** — [GitHub LICENSE](https://github.com/mwilliamson/mammoth.js/blob/master/LICENSE), [npm](https://www.npmjs.com/package/mammoth)
- `officeParser` (harshankur, fork actif) est une librairie Node/Browser qui parse docx, pptx, xlsx, odt, odp, ods, pdf, rtf, csv, md, html en un AST unique et peut générer Markdown/HTML/CSV/RTF/PDF/texte brut/chunks RAG ; supporte les fichiers protégés par mot de passe ; 568 942 téléchargements/semaine contre 8 362 pour docx4js — [GitHub harshankur/officeParser](https://github.com/harshankur/officeParser), [npm trends](https://npmtrends.com/docx-parser-vs-docx4js-vs-officeparser)
- `docx4js` existe comme alternative, licence **MIT**, mais beaucoup moins populaire (8 362 téléchargements/semaine) — [npm docx4js](https://www.npmjs.com/package/docx4js)
- `epub2` (149 954 téléchargements/semaine, 27 étoiles GitHub, dernière publication ~2023) et `epub.js`/`epubjs` (5 807 étoiles mais dernière publication ~2022) sont tous les deux jugés non activement maintenus en 2026 ; le paquet `epub` (2.1.1) semble publié plus récemment (~6 mois avant l'analyse) — [npm trends epub vs epub.js vs epub2](https://npmtrends.com/epub-vs-epub.js-vs-epub2-vs-epubjs-vs-react-reader)
- `@mozilla/readability` (Apache-2.0) est le port JS autonome de l'algorithme derrière le Reader View de Firefox ; nécessite une implémentation DOM côté Node — `jsdom` (complet, MIT, mais lourd : le coût de démarrage à froid domine le pipeline) ou `linkedom` (plus léger/rapide, "même exactitude que jsdom sur le corpus testé, avec un coût de démarrage ~3× inférieur", mais légèrement moins conforme aux specs) — [GitHub mozilla/readability](https://github.com/mozilla/readability), [analyse BulkMD](https://bulkmd.app/blog/readability-vs-trafilatura-extractors)
- Tesseract.js compile le moteur C++ Tesseract en WebAssembly pour tourner dans le navigateur ou Node sans backend serveur, supporte 100+ langues ; alternative plus légère : `tesseract-wasm` (robertknight) — [GitHub robertknight/tesseract-wasm](https://github.com/robertknight/tesseract-wasm), [projectnaptha.com](https://tesseract.projectnaptha.com/)
- Les meilleurs outils de conversion PDF→Markdown en 2026 (Docling, marker, MinerU, PyMuPDF/pdfplumber, OCRmyPDF, PaddleOCR, Nougat) sont tous des paquets **Python**, sans équivalent Node natif de qualité comparable — [comparatif Docling/Marker/MinerU 2026](https://adityamangal98.medium.com/docling-vs-marker-vs-mineru-the-ultimate-open-source-pdf-parser-benchmark-2026-which-is-best-a36ecbb6c6b1)

### Inferences
- Pour un socle 100% Node/WASM sans Python : `pdfjs-dist` ou `unpdf` pour le PDF texte, `mammoth` pour DOCX, `officeParser` comme filet de sécurité multi-format (dont ODT et PDF simple), `epub2` (malgré maintenance stagnante, plus utilisé qu'epub.js) ou une implémentation maison via JSZip + parsing OPF/XHTML + Readability pour EPUB, et `@mozilla/readability` + `linkedom` pour le HTML/web.
- `mupdf.js` offre probablement la meilleure qualité d'extraction WASM pure, mais son AGPL-3.0 impose soit une divulgation du code source complet du démon, soit l'achat d'une licence commerciale Artifex — à traiter comme un choix structurant de licence, pas juste technique.
- Pour le PDF scanné, l'absence d'équivalent Node/WASM de qualité Docling/PaddleOCR signifie que `tesseract.js`/`tesseract-wasm` est la seule option "zéro Python", avec un compromis qualité assumé (cf. question OCR ci-dessous) ; un palier Python optionnel (Docling/OCRmyPDF+PaddleOCR) reste la voie recommandée si l'utilisateur accepte cette dépendance en "tier avancé".

### Gaps
- Aucune mesure chiffrée et indépendante (précision, taux d'erreur) comparant directement la qualité texte de sortie de `unpdf`/`pdfjs-dist`/`officeParser` entre eux sur un corpus commun n'a été trouvée ; les comparatifs disponibles sont des articles de blog non académiques.
- Pas de confirmation officielle si `pdf-parse` dépend réellement du module natif `canvas` dans sa version courante (l'information vient d'un blog tiers, pas de la doc npm/GitHub officielle) — à vérifier avant décision d'architecture.
- Aucune alternative EPUB Node activement maintenue en 2026 n'a été identifiée avec certitude (candidats trouvés tous jugés stagnants).

## Quels outils préservent l'ordre de lecture et la structure suffisamment bien pour la narration (titres comme pauses, listes, ignorer pieds de page/numéros de page) ?

### Takeaway
Docling (Python, MIT) est le seul outil trouvé qui modélise explicitement l'ordre de lecture, sépare le "corps" du document de son "mobilier" (headers/footers/numéros de page, exclus du Markdown) et conserve la hiérarchie de titres/tableaux ; côté JS, `mammoth` convertit fidèlement les styles Word en balises sémantiques (H1, etc.) mais rien d'équivalent n'a été confirmé pour la détection automatique d'en-têtes/pieds de page en PDF pur JS.

### Cited Findings
- Docling (IBM) résout la séquence de lecture "comme un humain la suivrait" et stocke les composants dans cet ordre, si bien que le texte ne s'entrelace jamais entre colonnes ; les éléments reconnus comme en-tête/pied de page sont supprimés du Markdown pour livrer un contenu ininterrompu — [Docling docs — DoclingDocument](https://docling-project.github.io/docling/concepts/docling_document/)
- Le format `DoclingDocument` sépare explicitlement `body` (racine de l'arbre du contenu principal) et `furniture` (racine de l'arbre pour tout ce qui n'appartient pas au corps : en-têtes, pieds de page) ; il reconstruit aussi la structure ligne/colonne/en-têtes multi-niveaux des tableaux au lieu de les aplatir — [Docling docs](https://docling-project.github.io/docling/concepts/docling_document/)
- Docling ingère quasiment tout (PDF, DOCX, PPTX, XLSX, HTML, EPUB, images, et même email/audio), tourne sur CPU, licence **MIT** — [Medium comparatif 2026](https://adityamangal98.medium.com/docling-vs-marker-vs-mineru-the-ultimate-open-source-pdf-parser-benchmark-2026-which-is-best-a36ecbb6c6b1)
- Sur le benchmark olmOCR-bench cité (source secondaire, non vérifiée de façon indépendante) : marker 2 obtient 76,0% à 2,9 pages/s, MinerU 72,7% à 0,54 page/s, Docling 50,3% à 2,1 pages/s — mais l'article précise que Docling est "presque certainement meilleure en déploiement réel avec son mode VLM activé", et que le backend VLM de MinerU a été explicitement exclu du test — [MarkTechPost](https://www.marktechpost.com/2026/07/24/datalab-marker-v2-vs-mineru-docling-and-liteparse-benchmark-breakdown/), [Lumien AI](https://lumienai.com/news/marker-2-vs-mineru-docling-liteparse-olmocr-bench-benchmark)
- MinerU serait particulièrement fort sur les mises en page complexes et le contenu CJK ; pour les tableaux et les PDF scientifiques, MinerU obtiendrait le meilleur score CDM sur les formules — [comparatif Medium](https://adityamangal98.medium.com/docling-vs-marker-vs-mineru-the-ultimate-open-source-pdf-parser-benchmark-2026-which-is-best-a36ecbb6c6b1)
- `mammoth` convertit "tout paragraphe avec le style Heading 1 en éléments `<h1>`", plutôt que de tenter de recopier la mise en forme visuelle — préserve donc la structure sémantique des titres Word — [npm mammoth](https://www.npmjs.com/package/mammoth)
- `pdf.js` fournit `getTextContent()` qui renvoie des items de texte positionnés (matrice de transformation → x/y/largeur/hauteur) mais **sans structure sémantique** — pas de notion native de titre, paragraphe ou pied de page ; c'est une liste de fragments de texte positionnés qu'il faut réinterpréter par heuristique — [issue mozilla/pdf.js #5643](https://github.com/mozilla/pdf.js/issues/5643), [issue #7396](https://github.com/mozilla/pdf.js/issues/7396)

### Inferences
- Pour un vrai rendu "narration" (pauses aux titres, saut des pieds de page/numéros), un outil doté d'un modèle structurel explicite comme Docling (furniture vs body) est fortement supérieur à une extraction brute pdf.js/pdf-parse, qui nécessiterait de recoder soi-même des heuristiques de détection d'en-tête/pied de page/numéro de page (répétition inter-pages, position en haut/bas de page).
- Le compromis "Node pur mais sans structure" vs "Python riche en structure (Docling)" est le nœud central de l'architecture : si la lecture à voix haute doit gérer intelligemment titres/listes/tableaux et ignorer les artefacts de mise en page PDF, un palier Python (Docling) apporte une valeur significative que le monde Node ne couvre pas encore.

### Gaps
- Aucune donnée trouvée sur la façon dont `unpdf` ou `officeParser` détectent (ou non) les en-têtes/pieds de page/numéros de page en PDF — probablement aucun mécanisme dédié, mais non confirmé explicitement dans la documentation consultée.
- Pas de benchmark indépendant (hors articles de blog/produits commerciaux) trouvé pour noter objectivement la fidélité de préservation de structure ; les chiffres cités (olmOCR-bench) proviennent de billets de blog non académiques et doivent être traités avec prudence.

## Comment mapper les segments parlés vers les positions source (page + bbox pour PDF, plages DOM pour HTML) pour un surlignage synchronisé ?

### Takeaway
pdf.js expose nativement de quoi reconstruire des boîtes englobantes par item de texte (page + matrice de transformation → x/y/largeur/hauteur, convertible en coordonnées PDF via `viewport.convertToPdfPoint()`), ce qui permet un mapping segment-parlé→bbox si l'on conserve les offsets de caractères lors de la segmentation en phrases ; côté HTML, le mapping repose sur les API DOM standard (`Range.getClientRects()`, `Selection`) appliquées **avant** que l'extraction (Readability) ne clone/mute le DOM, car l'extraction perd la correspondance avec les nœuds originaux si elle n'est pas faite avec précaution.

### Cited Findings
- `getTextContent()` de pdf.js renvoie des items de texte contenant le texte et une matrice de transformation donnant la position ; on extrait `item.transform[4]`/`item.transform[5]` pour les coordonnées x/y, plus largeur/hauteur — [Sensible.so blog](https://www.sensible.so/blog/solving-direct-text-extraction-from-pdfs), [Nutrient.io blog](https://www.nutrient.io/blog/pdfjs-text-highlight-annotations/)
- Les annotations/surlignages peuvent être stockés en espace de coordonnées PDF via `viewport.convertToPdfPoint()`, ce qui découple la position stockée du zoom/rendu courant — [Medium — PDF Highlighter dynamique](https://medium.com/@aalam-info-solutions-llp/building-a-dynamic-pdf-highlighter-in-react-a-scalable-layout-agnostic-approach-22ed400c9809)
- Pour la sélection de texte, on peut s'appuyer sur les API DOM standard (`getSelection`, `getClientRects`) sur la couche texte de pdf.js, en convertissant les rectangles client en coordonnées relatives à la page en soustrayant `canvasWrapper.getBoundingClientRect()` — une sélection sur plusieurs lignes produit plusieurs rectangles, chaque fragment de ligne rendu ayant sa propre boîte englobante via `range.getClientRects()` — [Nutrient.io blog](https://www.nutrient.io/blog/pdfjs-text-highlight-annotations/)
- Pour le HTML, `@mozilla/readability` a besoin d'un DOM (jsdom ou linkedom) et son fonctionnement consiste à analyser/élaguer le DOM pour isoler l'article ; aucune source consultée ne documente un mécanisme intégré de conservation des références aux nœuds DOM originaux post-extraction — [GitHub mozilla/readability](https://github.com/mozilla/readability)

### Inferences
- Architecture de mapping recommandée pour le PDF : conserver, lors du parsing pdf.js, un tableau `{page, charStart, charEnd, bbox}` par item de texte au fil de l'extraction ; puis, lors de la segmentation en phrases (étape suivante), calculer pour chaque phrase l'offset de caractères dans le flux de texte concaténé, et retrouver les items pdf.js (et donc les bbox) qui se chevauchent avec cet intervalle — c'est la même logique que le "walk" de `range.getClientRects()` mentionné pour la sélection de texte, mais appliquée hors-DOM sur les métadonnées pdf.js.
- Architecture de mapping recommandée pour le HTML : effectuer la segmentation de phrases sur le DOM vivant (avant ou en parallèle de Readability) en conservant un `Range` DOM par phrase (via `document.createRange()` + offsets de noeuds texte), pour pouvoir ensuite appeler `range.getClientRects()` à la volée dans la vue de lecture ; si Readability doit être utilisé pour isoler l'article, il faut appliquer l'extraction sur une **copie**, retenir la liste des nœuds retenus, puis retrouver leurs équivalents dans le DOM original (par ex. via un identifiant injecté avant clonage) pour reconstruire les Ranges.

### Gaps
- Aucune bibliothèque ou pattern "prêt à l'emploi" trouvé pour maintenir automatiquement la correspondance segment-de-phrase ↔ Range DOM à travers une passe Readability ; c'est un point d'implémentation propre au projet, pas un composant open source existant identifié.
- Pas de source trouvée décrivant comment DOCX/EPUB (mammoth, epub2) exposent des positions dans le fichier source (offset XML, id de paragraphe) pouvant servir de base à un mapping analogue au bbox PDF ou au Range HTML — à investiguer séparément si le surlignage doit aussi couvrir DOCX/EPUB.

## Quelles sont les meilleures pratiques de normalisation du texte français avant TTS (nombres, dates, unités, acronymes, identifiants de code) ?

### Takeaway
Il existe de bonnes briques ponctuelles pour la conversion nombre→lettres en français (`n2words`, `to-words`, `written-number`), mais aucun paquet npm "tout-en-un" de normalisation TTS française (nombres + dates + unités + sigles + code) n'a été identifié ; l'état de l'art méthodologique le plus documenté (classes sémiotiques, normalisation contextuelle) vient de l'écosystème Python (NVIDIA NeMo-text-processing, WFST), et les moteurs TTS eux-mêmes (Piper, Kokoro/misaki) ne semblent pas fournir de normalisation française complète prête à l'emploi — Piper fait une normalisation générique (nombres/symboles/abréviations) en C++ avant de passer à espeak-ng pour la phonémisation.

### Cited Findings
- `n2words` (forzagreen) convertit les nombres en toutes lettres dans 70+ langues dont le français, zéro dépendance, ~2 Ko gzippé par langue — [GitHub forzagreen/n2words](https://github.com/forzagreen/n2words), [npm](https://www.npmjs.com/package/n2words)
- `to-words` convertit les nombres en mots dans 135 locales avec support devise, ordinaux et BigInt, positionné comme migration depuis `number-to-words`, `written-number`, `num-words` ou `n2words` — [npm to-words](https://www.npmjs.com/package/to-words)
- `written-number` supporte anglais, portugais, espagnol et français, avec options de langue et de séparateur — plus ancien, pas de confirmation de maintenance active — [npm written-number](https://www.npmjs.com/package/written-number)
- En typographie française : espace entre nombre et unité (5 km, 30 °C), séparateur de milliers par espace insécable ; pour les dates, les mois ne s'abrègent pas et le format JJ/MM/AAAA est déconseillé en style éditorial soigné ; deux dates se séparent par un trait d'union sans espaces (ex. 1939-1945) ; abréviations courantes : M., Mme, Dr, cf., p., pp. — [TERMIUM Plus — Guide du rédacteur](https://www.btb.termiumplus.gc.ca/redac-chap?lang=fra&lettr=chapsect1&info0=1.2)
- La normalisation de texte (TN) pour la TTS convertit la forme écrite en forme "verbalisée" à prononcer (ex. "$123" → "one hundred and twenty three dollars") ; NVIDIA `nemo_text_processing` gère plusieurs classes sémiotiques (nombres, heures, dates) via des transducteurs à états finis pondérés (WFST, bibliothèque Pynini), avec une variante rapide déterministe et une variante "context-aware" — Python uniquement — [GitHub NVIDIA/NeMo-text-processing](https://github.com/NVIDIA/NeMo-text-processing), [docs NVIDIA](https://docs.nvidia.com/nemo-framework/user-guide/25.07/nemotoolkit/nlp/text_normalization/nn_text_normalization.html)
- Piper effectue une normalisation générale (nombres, symboles, abréviations) puis une détection de langue et une phonémisation via espeak-ng (qui produit des phonèmes IPA) ; ce pipeline a été réimplémenté en C++ pour du TTS embarqué basse latence — le compromis assumé est l'héritage des erreurs de prononciation occasionnelles d'espeak-ng sur les mots rares — [GitHub OHF-Voice/piper1-gpl](https://github.com/OHF-Voice/piper1-gpl), [Cekura.ai](https://www.cekura.ai/discover/piper-tts)
- `espeak-ng`, phonémiseur à base de règles utilisé par Piper, supporte le français parmi 100+ langues, licence **GPL-3.0** — [GitHub piper-phonemize](https://github.com/rhasspy/piper-phonemize)
- `misaki` (moteur G2P de Kokoro) supporte le français (préfixe de voix `f`) parmi cmn/en-gb/en-us/fr-fr/it/ja, avec des contributions natives par langue installables séparément (ex. `pip install misaki[en]`) ; licence Apache — mais la licence des données/lexiques n'est "pas déclarée en amont" selon un projet tiers intégrant misaki, donc rien n'est empaqueté par prudence — [PyPI misaki](https://pypi.org/project/misaki/), [rapport intégration Kokoro d'un projet tiers](https://github.com/DeepBlueDynamics/hyperia/pull/231)

### Inferences
- Pour une normalisation française avant TTS, il faudra très probablement composer soi-même plusieurs briques : `n2words` (ou `to-words`) pour les nombres cardinaux/ordinaux, des règles maison (regex + tables) pour dates/unités/sigles/abréviations en s'appuyant sur les conventions typographiques françaises documentées, et un traitement séparé des identifiants de code (à épeler lettre par lettre ou à translittérer selon convention camelCase/snake_case) qui n'est couvert par aucun composant identifié.
- Le fait que Piper et misaki délèguent une bonne partie de la normalisation "générique" à des règles internes (C++ pour Piper, tables préconfigurées pour misaki) suggère que, si l'un de ces moteurs est choisi comme backend TTS final, une partie du travail de normalisation basique (nombres/symboles) pourrait déjà être gérée en aval — mais il resterait risqué de compter dessus pour du français technique/riche (variable de code, unités composées), qui devrait être pré-traité en amont, avant d'atteindre le moteur TTS.

### Gaps
- Aucun paquet npm ou WASM de normalisation TTS française complète (nombres+dates+unités+sigles, sensible au contexte) n'a été trouvé ; c'est probablement une lacune réelle de l'écosystème JS et un axe de développement interne nécessaire.
- Pas de documentation trouvée confirmant précisément **comment** Piper (C++ text processing pipeline) traite spécifiquement le français (dates, unités) au-delà de la déclaration générique "numbers, symbols, and abbreviations" — la portée exacte des règles françaises intégrées reste inconnue.
- Pas de confirmation sur la qualité de misaki en français par rapport à l'anglais (le projet est présenté comme centré sur l'anglais avec extensions communautaires par langue) — à tester empiriquement si Kokoro est retenu comme moteur vocal.
- Aucune information trouvée sur la gestion spécifique des blocs de code, URLs et tableaux au moment de la synthèse vocale (au-delà de l'intuition qu'il faut les détecter en amont et les remplacer par une description ou un épellation) — sujet non couvert par les sources trouvées, à traiter comme un choix de conception produit plutôt qu'une brique existante.

## Existe-t-il des pipelines open source "lire n'importe quel document à voix haute" réutilisables intégralement (licence permettant) ?

### Takeaway
Il existe des projets qui se présentent explicitement comme des alternatives open source à Speechify capables de lire PDF/EPUB avec des modèles locaux (OpenWebTTS), mais leur stack et licence précises restent peu documentées publiquement ; Calibre a un pipeline de lecture à voix haute mature et très bien documenté (visionneuse + moteur Piper ou TTS système), mais c'est une application desktop Python/Qt GPL-3.0, pas une librairie embarquable ; les fonctionnalités "Read Aloud" de Firefox et Edge reposent en partie sur du code réutilisable (Readability.js pour Firefox) mais la synthèse et la mise en surbrillance elles-mêmes ne sont pas des composants open source détachables.

### Cited Findings
- OpenWebTTS (Gyyyn/OpenWebTTS, fork sgj0/tts) se décrit comme "alternative open source à Speechify et ElevenLabs" fonctionnant localement, utilisable avec n'importe quel moteur TTS, lisant PDF/EPUB/autres documents sans abonnement ni tracking ; son `BUILD.md` mentionne un packaging en application de bureau via **PyWebView** (pas Electron) avec des builds Flatpak pour Linux — stack donc hybride Python (PyWebView) plutôt que Node pur — [GitHub Gyyyn/OpenWebTTS](https://github.com/Gyyyn/OpenWebTTS), [BUILD.md](https://github.com/Gyyyn/OpenWebTTS/blob/master/BUILD.md)
- Calibre utilise, pour son lecteur intégré (E-book viewer), soit le moteur neuronal **Piper** soit les services de synthèse vocale du système d'exploitation ; le mode Piper est local uniquement (aucune donnée envoyée dans le cloud) — [documentation calibre](https://manual.calibre-ebook.com/viewer.html), [OMG Ubuntu — calibre 7.2.1](https://www.omgubuntu.co.uk/2024/11/calibre-7-2-1-brings-read-aloud-fixes-new-audio-overlay-)
- Calibre propose aussi, dans son outil d'édition de livre, la génération d'overlays audio via Piper pour que le livre reste "lisible à voix haute" même dans des lecteurs sans capacité TTS — [OMG Ubuntu](https://www.omgubuntu.co.uk/2024/11/calibre-7-2-1-brings-read-aloud-fixes-new-audio-overlay-)
- Le Reader View de Firefox (extraction d'article) repose sur l'algorithme devenu le paquet open source `@mozilla/readability` (Apache-2.0), réutilisable indépendamment ; sa fonction "Read Aloud" ne s'active que si l'OS dispose des informations de synthèse vocale dans la langue de l'article — la synthèse elle-même passe par les capacités TTS du système, pas par un composant Mozilla dédié — [support Mozilla](https://support.mozilla.org/en-US/kb/firefox-reader-view-clutter-free-web-pages), [GitHub mozilla/readability](https://github.com/mozilla/readability)
- Edge Read Aloud est présenté comme la fonctionnalité de lecture à voix haute intégrée la plus aboutie des navigateurs majeurs : voix neuronales Microsoft prêtes à l'emploi, support natif des PDF, fonctionne sur presque toute page, surlignage mot par mot ; c'est un produit propriétaire Microsoft, sans architecture technique publique détaillée trouvée — [readaloudreader.com](https://readaloudreader.com/blog/edge-read-aloud/)
- L'extension de navigateur "Read Aloud: A Text to Speech Voice Reader" est citée comme la meilleure alternative open source à Speechify parmi les extensions, lisant le contenu de n'importe quelle page en un clic, en plusieurs langues, avec réglages de vitesse/hauteur — [AlternativeTo](https://alternativeto.net/software/speechify/?license=opensource)

### Inferences
- Aucun pipeline trouvé ne peut être repris "intégralement" tel quel pour un démon Node/TypeScript : OpenWebTTS est proche en ambition produit mais s'appuie sur Python/PyWebView, pas Node ; Calibre est une application Qt/Python monolithique ; Firefox/Edge sont des fonctionnalités de navigateur non détachables (à l'exception de Readability.js, déjà identifié comme composant réutilisable pour l'extraction HTML).
- La stratégie la plus réaliste reste donc l'assemblage de briques (extraction par format + segmentation + normalisation + moteur TTS) plutôt que la réutilisation d'un pipeline "lecture de n'importe quel document" complet existant — aucun projet ne remplit tous les critères (Node/TS natif, licence permissive, multi-format, maintenu) simultanément.

### Gaps
- Licence précise d'OpenWebTTS non trouvée (aucune mention explicite de fichier LICENSE dans les résultats de recherche) — à vérifier directement sur le dépôt avant toute réutilisation de code.
- Licence précise de l'extension "Read Aloud" (ken107 ou équivalent) non confirmée par les sources consultées.
- Aucune architecture technique publique détaillée trouvée pour Edge Read Aloud (propriétaire) — seulement des descriptions côté utilisateur final.

### Inferences
- La colonne licence fait apparaître un clivage net entre deux familles d'outils à très forte qualité mais copyleft fort/AGPL (MuPDF, PyMuPDF) et des outils plus permissifs mais parfois moins riches en structure (pdf.js, unpdf, Docling en MIT) — le choix de licence doit être fait consciemment dès le début de l'architecture, car il conditionne si le produit final doit être lui-même open source (AGPL) ou peut rester propriétaire.
- Le tableau confirme qu'aucun composant Node/WASM ne couvre à la fois "structure riche" et "licence permissive" pour le PDF — c'est le compromis central à trancher pour ce projet.

### Gaps
- Plusieurs licences précises n'ont pas pu être confirmées dans le temps imparti (linkedom, sbd, n2words, to-words, written-number, epub2, epubjs, officeParser en détail, OpenWebTTS) — marquées "Inconnu" ci-dessus ; une vérification directe des fichiers LICENSE de chaque dépôt est recommandée avant intégration en production.
- Aucune donnée de performance/qualité chiffrée et indépendante (précision d'extraction, taux d'erreur OCR) n'a pu être vérifiée pour la majorité des outils au-delà des affirmations de blogs et de la documentation officielle des projets eux-mêmes.
