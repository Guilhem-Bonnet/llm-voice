# Contrôle de lecture natif et lecture gapless pour un daemon Node.js (2026)

Scope: capacités concrètes de start/pause/seek/position/stdin-PCM/sélection de sortie pour les lecteurs natifs pilotables depuis un daemon Node.js sur Linux/macOS/Windows, plus les patterns connus de chaînage gapless de chunks TTS et les splitters de phrases Node/TS pour texte LLM en streaming. Ne recouvre pas la politique autoplay Chromium ni l'inventaire général des addons Node (traité dans une autre passe).

## Which single option per OS gives start + pause/resume + position with a preinstalled binary and no compile step? Where does that fail?

### Takeaway
Aucun OS n'offre un binaire préinstallé combinant nativement start + pause/resume programmatique + position sans détour : Linux a `aplay -i` mais le pause/resume y est verrouillé à un clavier de terminal interactif (`isatty` check, pas de signal), macOS n'a que `afplay` qui n'a ni pause ni position exposée, et Windows n'a aucun lecteur CLI préinstallé avec pause — il faut passer par un objet .NET/COM piloté en PowerShell (`System.Windows.Media.MediaPlayer` a Pause+Position, mais démarre une VM PowerShell à chaque appel).

### Cited Findings
**Linux**
- `aplay` (ALSA) : `-i, --interactive` documente le pause/resume via la touche espace/entrée pendant la lecture, `-D/--device` sélectionne le périphérique PCM par nom, `-t` accepte `raw` comme type de fichier et `-r/-c/-f` fixent rate/channels/format — mais aucune option de seek ni de requête de position n'apparaît dans le man page. — [aplay(1) man page](https://manpages.debian.org/testing/alsa-utils/aplay.1.en.html)
- Le pause/resume interactif d'`aplay` est **gated par un test `isatty` sur stdin** : un ticket ouvert (« enhancement », assigné à takaswie, aucune réponse mainteneur, aucune PR) demande explicitement de le rendre pilotable par script/automation, en proposant soit de retirer le check `isatty`, soit d'ajouter un contrôle par signal `SIGUSR2` — aucune des deux options n'est implémentée à ce jour. — [alsa-project/alsa-utils issue #155](https://github.com/alsa-project/alsa-utils/issues/155)
- `pw-cat`/`pw-play` (PipeWire) : options confirmées — `--raw/-a` pour lire/écrire des échantillons bruts, `--rate`, `--channels`, `--format`, `--channel-map`, `--target` (sélection du node cible, `auto` par défaut, ou ID/nom de node) et `--volume`. **Aucune option de pause, seek, ou requête de position de lecture n'est documentée.** — [pw-cat man page (Debian)](https://manpages.debian.org/experimental/pipewire-bin/pw-cat.1.en.html)
- `pacat`/`paplay` (PulseAudio) : lit depuis un fichier ou **stdin** par défaut si aucun fichier n'est donné ; `--raw` est le mode par défaut pour `pacat`/`parec`/`pamon` ; `--latency=BYTES` et `--latency-msec=MSEC` configurent explicitement la latence (sinon le serveur choisit, généralement haute pour l'économie d'énergie) ; `--device=SINKORSOURCE` sélectionne le sink/source par nom symbolique. **Aucune option de pause/cork ni de requête de position** n'apparaît dans le man page (le `--verbose` ne fait que dumper le temps de lecture courant sur stderr, en sortie seule, pas une requête interrogeable). — [pacat(1) man page (Debian)](https://manpages.debian.org/testing/pulseaudio-utils/pacat.1.en.html)
- `mpv` (avec `--input-ipc-server`) : le socket JSON IPC (Unix domain socket, ou named pipe sur Windows) permet d'envoyer des commandes JSON `{"command": [...]}` — la propriété `pause` peut être lue/écrite (touche `p`/`SPACE` en usage clavier documenté, la property est pilotable via `set_property`/`get_property` en IPC), les propriétés `playback-time` et `time-pos` donnent la position de lecture courante, `--gapless-audio` existe comme option de configuration pour la lecture sans coupure entre pistes, `--demuxer=rawaudio` avec les options `--demuxer-rawaudio-*` permettent de nourrir du PCM brut (y compris via stdin en utilisant `-` comme nom de fichier), et `--audio-device` sélectionne la sortie matérielle. Le protocole IPC est explicitement documenté comme **non sécurisé** (« no authentication, no encryption »), prévu seulement pour du contrôle local. — [mpv manual](https://mpv.io/manual/stable/), [mpv IPC docs](https://github.com/mpv-player/mpv/blob/master/DOCS/man/ipc.rst)
- `ffplay` : contrôles clavier interactifs documentés incluent `p`/`SPACE` pour pause et flèches pour seek ; `-nodisp` désactive l'affichage vidéo et `-autoexit` quitte à la fin de lecture — utile en mode audio pur/headless. — [ffplay keyboard shortcuts](https://linuxcommandlibrary.com/man/ffplay)
- Le protocole `pipe` de FFmpeg (`ffmpeg-protocols.html`) documente que `pipe:0`/`pipe:1`/`pipe:2` correspondent aux descripteurs stdin/stdout/stderr, et que sans numéro spécifié stdout sert par défaut en écriture, stdin par défaut en lecture. Pour du PCM brut, il faut explicitement déclarer `-f s16le -ar <rate> -ac <channels>` avant `-i -` (ou `pipe:0`) car le PCM n'a pas d'en-tête. Exemple documenté : `ffmpeg ... -f s16le ... - | ffplay -f s16le -ar 48k -`. — [FFmpeg Protocols Documentation](https://ffmpeg.org/ffmpeg-protocols.html)
- **Aucune option de pause pilotable par IPC/stdin n'a été trouvée documentée pour ffplay** au-delà du contrôle clavier interactif (donc nécessite un pty pour être piloté par un daemon, comme pour `aplay -i`).

**macOS**
- `afplay` : options confirmées — `-v/--volume` (0=silence, 1=normal, jusqu'à 255), `-r/--rate` (vitesse de lecture, limites pratiques ~0.4 à 3.0), `-t/--time` (durée de lecture limitée), `-q/--rQuality` (qualité du rate-scaling). **Aucune option de pause, ni de requête de position, n'apparaît** ; la commande bloque jusqu'à la fin de la lecture (à lancer en arrière-plan pour ne pas bloquer le shell). — [ss64 afplay reference](https://ss64.com/mac/afplay.html)
- `ffplay`/`mpv` sont installables via Homebrew mais ne sont **pas préinstallés** sur macOS — mêmes capacités IPC/pause/position que documentées ci-dessus pour Linux une fois installés.

**Windows**
- `System.Media.SoundPlayer` (.NET, accessible en PowerShell) : expose `Play()` (asynchrone) et `PlaySync()` (synchrone, bloquant jusqu'à la fin). `LoadAsync`/`Load` permettent de précharger le WAV en mémoire pour réduire la latence de démarrage des appels suivants. Si le fichier n'est pas chargé/échoue, `PlaySync` joue un bip par défaut. **Aucune méthode Pause ni propriété Position n'existe sur cette classe.** — [SoundPlayer.PlaySync (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/api/system.media.soundplayer.playsync)
- `System.Windows.Media.MediaPlayer` (WPF, accessible via PowerShell en chargeant l'assembly `PresentationCore`) : expose `Play`, `Pause`, `Stop`, ainsi que les propriétés `Position`, `Volume`, `IsMuted`, `PlaybackRate`. Note documentée : après un `Pause()`, la valeur de `Position` peut ne pas être précise ; pour une position frame-accurate il faut appeler `StepForwardOneFrame` juste après `Pause()` avant de lire `Position`. — [How to control a MediaElement (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/how-to-control-a-mediaelement-play-pause-stop-volume-and-speed)
- `WMPlayer.OCX` (COM, Windows Media Player) : en PowerShell, `$wmp = New-Object -ComObject wmplayer.ocx` puis `$wmp.controls.play()`, `$wmp.controls.pause()`, `$wmp.controls.stop()`. La position est lisible/réglable via `controls.currentPosition` (en secondes) et `controls.currentPositionString` (format HH:MM:SS). — [PowerShell and Windows Media Player (James O'Neill's Blog)](https://jamesone111.wordpress.com/2008/10/21/powershell-and-windows-media-player-part-2/), [Windows Media Player 11 SDK IWMPControls.pause](https://learn.microsoft.com/en-us/previous-versions/aa388749(v=vs.85))
- Aucune des deux options .NET/COM ci-dessus n'a été confirmée dans cette passe comme prenant du **PCM brut en flux via stdin** — elles opèrent sur des fichiers/URLs, pas sur un pipe. C'est une lacune documentaire (gap ci-dessous).
- `ffplay`/`mpv` peuvent être embarqués comme binaires portables par plateforme (bundling) pour retrouver les mêmes capacités IPC/gapless/pause que sur Linux — c'est l'option suggérée pour uniformiser le comportement cross-OS.

### Inferences
- Sur Linux comme sur macOS, la seule voie pour obtenir start+pause+seek+position+stdin-PCM+device-selection en un seul processus long-lived avec un binaire déjà présent dans la plupart des installations de bureau modernes est **mpv avec `--input-ipc-server`**, à condition que mpv soit installé (il ne l'est pas nativement sur macOS, ni sur Windows) — ce qui pousse vers le bundling d'un binaire mpv/ffplay portable pour une expérience identique sur les trois OS plutôt que de dépendre d'un lecteur « préinstallé ».
- Sur Windows, démarrer un objet PowerShell (`System.Windows.Media.MediaPlayer` ou `WMPlayer.OCX`) implique de lancer un processus `powershell.exe`/`pwsh.exe` par session de lecture (ou de garder un processus PowerShell persistant en dialoguant via stdin), ce qui expose le daemon Node au coût de démarrage de l'hôte PowerShell — un facteur de latence à mesurer, non chiffré par les sources trouvées dans cette passe (voir Gaps).
- Le pattern `aplay -i` et le clavier interactif de `ffplay` partagent la même limitation : le pause/resume suppose un terminal interactif (`isatty`), donc un daemon Node devrait allouer un pseudo-tty (pty) pour simuler la frappe clavier — une contrainte d'implémentation non triviale par rapport à un vrai contrôle IPC/socket comme celui de mpv.

### Gaps
- Aucune source consultée ne documente une capacité stdin-PCM native pour `System.Media.SoundPlayer`, `System.Windows.Media.MediaPlayer` ou `WMPlayer.OCX` — ces trois API Windows semblent conçues pour des fichiers/URLs, pas des pipes ; non confirmé dans un sens ou dans l'autre par une doc Microsoft explicite trouvée ici.
- Latence de démarrage concrète de `powershell.exe`/`pwsh.exe` sur Windows 11 (chiffres) : la recherche n'a pas produit de source chiffrant ce coût de démarrage ; seule une note générale sur le préchargement (`LoadAsync`) pour réduire la latence de lecture (pas de démarrage du process) a été trouvée.
- Comportement de sessions WASAPI multiples/exclusivité sur Windows 11 lors de lectures successives via ces API : non trouvé dans cette passe.
- Statut de présence de `wmplayer.exe`/`WMPlayer.OCX` sur des installations Windows 11 récentes (Windows Media Player legacy a été marqué en déclin dans les versions récentes de Windows) : non confirmé par une source fraîche dans cette passe — à vérifier séparément avant de s'appuyer dessus en production.
- Aucune confirmation trouvée qu'`ffplay` accepte des commandes de pause via son option `-nodisp` en mode purement headless sans clavier accessible (le contrôle clavier documenté suppose une fenêtre ou un terminal attaché) — donc l'utilisabilité de `ffplay -nodisp` pour un pause programmatique par un daemon reste incertaine.

## Is streaming raw PCM into one long-lived player process a reliable gapless strategy, and how to compute the played position?

### Takeaway
Concaténer/streamer du PCM brut sur stdin d'un processus lecteur unique et longue durée est le pattern dominant utilisé par les outils analysés (RealtimeTTS, Pipecat) pour obtenir du gapless sans crossfade — la position se calcule en général par comptage d'octets écrits divisé par le débit (sample_rate × channels × sample_width), et non par une requête native au lecteur, car aucun des lecteurs CLI étudiés (`pw-cat`, `pacat`, `aplay`, `ffplay`) n'expose une commande de requête de position lisible par un contrôleur externe.

### Cited Findings
- RealtimeTTS (`stream_player.py`, KoljaB/RealtimeTTS) utilise une `queue.Queue` pour accumuler les chunks audio bruts dans un `AudioBufferManager`, consommés par un thread de lecture unique (`_process_buffer()`) qui écrit sur un flux PyAudio unique et continu — **les chunks sont concaténés directement, sans crossfade**. La position de lecture est suivie par une variable `self.seconds_played`, incrémentée à chaque écriture de sous-chunk selon `seconds_played += len(sub_chunk) / (rate * sample_width * channels)`, utilisée ensuite pour déclencher les callbacks de timing de mots (`timing.start_time <= self.seconds_played`). Le pause fonctionne via un `pause_event` qui fait dormir le thread de lecture en boucle jusqu'à un clear ; le stop via un flag `immediate_stop`. — [RealtimeTTS stream_player.py](https://raw.githubusercontent.com/KoljaB/RealtimeTTS/master/RealtimeTTS/stream_player.py)
- Pipecat (`pipecat-ai`) représente chaque chunk audio TTS via une classe `TTSAudioRawFrame` ; le transport de sortie (`BaseOutputTransport`) maintient un `bytearray` comme buffer d'entrée et documente un mécanisme récent qui **« pads and flushes trailing audio shorter than one chunk before processing TTSStoppedFrame, preventing end-of-turn audio clipping »** — un pattern de gapless par gestion explicite du dernier chunk incomplet plutôt que par crossfade. — [pipecat.transports.base_output docs](https://reference-server.pipecat.ai/en/latest/_modules/pipecat/transports/base_output.html), [Pipecat TTS docs](https://docs.pipecat.ai/pipecat/learn/text-to-speech)
- `pacat` (PulseAudio) documente que la callback `stdin_callback()` de `pacat` appelle `pa_stream_writable_size()` pour savoir combien d'octets le sink peut absorber avant de lire davantage de stdin — un mécanisme de contrôle de flux (backpressure) natif pour l'alimentation stdin en continu. — [pacat man page discussion (ArchWiki summary)](https://wiki.archlinux.org/title/Pacat)
- `pacat`/`paplay` exposent `--latency=BYTES` / `--latency-msec=MSEC` pour configurer explicitement la latence du tampon, sinon le serveur choisit une latence généralement haute (économie d'énergie) — cette latence configurée est le paramètre à soustraire du décompte d'octets écrits pour approximer la position réellement *entendue* plutôt que la position *écrite*. — [pacat man page (Debian)](https://manpages.debian.org/testing/pulseaudio-utils/pacat.1.en.html)
- mpv documente `--gapless-audio` comme option dédiée à la lecture sans coupure/silence entre pistes, et les propriétés `playback-time`/`time-pos` comme moyen natif d'obtenir la position de lecture courante — contrairement à `pw-cat`/`pacat`/`aplay`/`ffplay` qui n'exposent aucune requête de position interrogeable en dehors de leur propre affichage texte. — [mpv manual](https://mpv.io/manual/stable/)
- Pour le Web Audio API (référence pour le pattern de scheduling, applicable via `node-web-audio-api`), le pattern documenté pour enchaîner des buffers sans coupure est : décoder chaque chunk en `AudioBuffer`, créer un `AudioBufferSourceNode` par chunk, et appeler `start(nextTime)` avec `nextTime` accumulé (`nextTime += audioBuffer.duration` après chaque chunk) plutôt que de rejouer un seul node. — [MDN AudioBufferSourceNode.start()](https://developer.mozilla.org/en-US/docs/Web/API/AudioBufferSourceNode/start)
- Une limitation documentée de ce pattern de scheduling Web Audio est une **race condition** : si l'horloge de l'`AudioContext` avance pendant l'exécution de la boucle de scheduling, certains temps de départ calculés peuvent se retrouver dans le passé — un buffer programmé dans le passé démarre alors immédiatement au lieu du temps prévu, ce qui décale son point de départ réel et peut faire chevaucher le buffer suivant (source de gaps/artefacts audio). — [WebAudio/web-audio-api issue #2636](https://github.com/WebAudio/web-audio-api/issues/2636)
- GStreamer (`gst-play-1.0`) documente une option `--gapless` dédiée pour activer la lecture sans coupure entre pistes ; `gst-launch-1.0` peut être piloté par signaux Unix `SIGUSR1` (retour à `GST_STATE_PLAYING`) et `SIGUSR2` (passage à `GST_STATE_NULL`, donc un « stop » plutôt qu'un vrai pause/resume au niveau pipeline). — [gst-play-1.0 docs (Oracle mirror)](https://docs.oracle.com/cd/E75432_01/html/E71066/gst-play-1-0-1.html), [NVIDIA developer forum thread on gst-launch SIGUSR1/2](https://forums.developer.nvidia.com/t/cant-pause-resume-gst-launch-with-sigusr1-2-signal/220171)
- Le protocole Wyoming (utilisé par Home Assistant / `wyoming-satellite`) est un protocole événementiel basé sur des lignes JSON (JSONL) échangées le plus souvent via stdin/stdout (ou TCP pour un usage distant), pour orchestrer wake-word, STT et TTS entre services ; le dépôt `wyoming-satellite` documente plusieurs modes de satellite (`AlwaysStreamingSatellite`, `VadStreamingSatellite`, `WakeStreamingSatellite`) selon la stratégie de streaming audio. — [rhasspy/wyoming-satellite](https://github.com/rhasspy/wyoming-satellite), [Wyoming Protocol – Home Assistant docs](https://www.home-assistant.io/integrations/wyoming/)

### Inferences
- Le pattern qui ressort de RealtimeTTS et Pipecat est cohérent : **concaténation pure de PCM (pas de crossfade)** dans un flux/pipe unique vers un seul processus/stream de sortie, avec la position calculée côté application par comptage d'octets écrits (converti en secondes via le débit PCM) plutôt que par une requête au lecteur — ce qui est nécessaire de toute façon puisque aucun des lecteurs CLI Linux étudiés (`pw-cat`, `pacat`, `aplay`) n'expose de requête de position native.
- Pour une position *jouée* (par opposition à *écrite*), il faut soustraire la latence du tampon de sortie ; `pacat`/`paplay` exposent cette latence en paramètre configurable (`--latency-msec`), ce qui permet de la connaître a priori côté application sans avoir besoin de l'interroger dynamiquement au runtime — mais aucune source consultée ne documente d'API pour interroger la latence *réelle* restante en cours de lecture sur PipeWire/PulseAudio (au-delà de ce qui a été explicitement configuré au lancement).
- mpv se distingue nettement du reste de l'écosystème CLI Linux/macOS en étant le seul à exposer nativement `time-pos`/`playback-time` interrogeables en IPC — ce qui en fait le candidat le plus direct pour une implémentation de position sans reconstruction manuelle par comptage d'octets, si mpv (ou un binaire embarqué) est acceptable comme dépendance.

### Gaps
- Aucune source consultée ne détaille une méthode native pour interroger la **latence PipeWire/Pulse en cours de lecture** (dynamique, pas seulement la valeur configurée au lancement) — la question posée dans l'objectif (« PipeWire/Pulse latency query ») reste sans réponse documentée trouvée dans cette passe.
- Aucune source trouvée ne documente explicitement la mécanique interne du crossfade vs. concaténation pour mpv en mode `--gapless-audio` avec un flux stdin multi-chunks (l'option est documentée pour l'enchaînement de pistes/fichiers de playlist, pas explicitement pour un flux stdin PCM continu multi-chunks) — à vérifier séparément si ce mode précis est nécessaire.
- Le format exact des messages `audio-start`/`audio-chunk`/`audio-stop` du protocole Wyoming (`snd` service) n'a pas pu être extrait en détail depuis les sources trouvées (la doc Home Assistant/`wyoming-satellite` décrit l'architecture générale mais pas le schéma JSON précis de ces événements) — nécessiterait de lire directement le schéma Python du paquet `wyoming` (PyPI) pour confirmation.

## Does node-web-audio-api cover all three OS with pause/resume/position and gapless scheduling, and what are its open issues?

### Takeaway
`node-web-audio-api` (ircam-ismm) fournit des binaires prébuilts pour Linux (x64 gnu, arm gnueabihf, arm64 gnu), macOS (x64, aarch64) et Windows (x64, arm64), et expose `AudioContext.currentTime` ainsi qu'un `suspend()`/`resume()` implicite pour le pause/resume — mais sur Linux les binaires sont **construits avec le backend Jack** (nécessitant `pipewire-jack` installé pour fonctionner sous PipeWire), la sélection fine de device/sink reste peu documentée (principalement une option `sinkId: {type: 'none'}` pour les environnements sans sortie audio comme Docker/CI), et un bug ouvert concerne une fuite de CPU par nœud `AudioWorkletProcessor` qui continue d'être traité après que `process()` retourne `false`.

### Cited Findings
- Binaires prébuilts documentés : Windows (x64, arm64), macOS (x64, aarch64), Linux (x64 gnu, arm gnueabihf, arm64 gnu) — tous les binaires Linux sont construits avec le flag `jack`. — [ircam-ismm/node-web-audio-api README](https://github.com/ircam-ismm/node-web-audio-api)
- Citation directe : « All provided Linux binaries are built with the `jack` flag, which should work either with properly configured Jack or pipewire-jack backends. » — [ircam-ismm/node-web-audio-api README](https://github.com/ircam-ismm/node-web-audio-api)
- `AudioContext.currentTime` est décrit comme le temps en secondes depuis que l'`AudioContext` a été *resumed*, calculé comme le nombre d'échantillons divisé par le sample rate — la même sémantique que le standard Web Audio, utilisable pour du tracking de position. — [ircam-ismm README / Timing and Scheduling tutorial](https://ircam-ismm.github.io/webaudio-tutorials/scheduling/timing-and-scheduling.html)
- Pour les environnements sans sortie audio (Docker, CI), le README documente une option d'initialisation `sinkId: { type: 'none' }`. La variable d'environnement `WEB_AUDIO_LATENCY=playback` est documentée pour créer le contexte audio avec un hint de latence de type lecture (plutôt qu'interactif) — utile pour augmenter la taille de rendu (ex. jusqu'à 1024 frames) et éviter des soucis avec le backend ALSA par défaut. — [ircam-ismm/node-web-audio-api README](https://github.com/ircam-ismm/node-web-audio-api)
- Le README liste explicitement des limitations connues : `AudioBuffer#getChannelData` est implémenté mais **pas fiable dans certaines situations** (recommandation d'utiliser `copyToChannel`/`copyFromChannel` à la place) ; le support du streaming est minimal (`MediaStreamSourceNode` fourni, mais d'autres fonctionnalités MediaStream reportées). — [ircam-ismm/node-web-audio-api README](https://github.com/ircam-ismm/node-web-audio-api)
- Issue ouverte #202 : un `AudioWorkletProcessor` dont `process()` retourne `false` continue d'être appelé à chaque quantum de rendu même après déconnexion du node et suppression de toutes les références JS — le node ne devient jamais inactif et le CPU s'accumule par node. — [ircam-ismm/node-web-audio-api issue #202](https://github.com/ircam-ismm/node-web-audio-api/issues/202)
- Pour `audify` (RtAudio), la classe `RtAudio` documente : `openStream` (ouvre un flux avec paramètres output/input, format, sample rate, taille de frame — retourne la taille de frame réellement utilisée), `start()`/`stop()` pour démarrer/arrêter le flux, `write(pcm)` pour « queue » du nouveau PCM de sortie (la longueur du buffer doit être frame_size × channels × sample_size), la propriété `streamTime` pour le temps écoulé depuis le démarrage du flux (≥ 0.0), et `getDevices()`/`getDefaultInputDevice()`/`getDefaultOutputDevice()` pour la sélection de device. **Aucune méthode de pause dédiée n'est documentée** — seuls start/stop existent, et il n'y a pas de méthode `chooseDevice` distincte (la sélection se fait via les paramètres passés à `openStream`). Audify/RtAudio couvre nativement ALSA/JACK/PulseAudio/OSS sur Linux, CoreAudio/JACK sur macOS, et DirectSound/ASIO/WASAPI sur Windows. — [Audify.js RtAudio class docs](https://almoghamdani.github.io/audify/classes/RtAudio.html), [audify GitHub README](https://github.com/almoghamdani/audify)

### Inferences
- Pour `node-web-audio-api`, le pause/resume peut vraisemblablement s'implémenter via `AudioContext.suspend()`/`.resume()` (méthodes standard du Web Audio API qu'implémente ce module) combiné avec le tracking de `currentTime`, mais **aucune source consultée dans cette passe ne cite explicitement `suspend()`/`resume()` par leur nom dans la documentation ircam-ismm** — seule la mention générale « Supports suspend/resume functionality for pause/play operations » a été retrouvée via une synthèse de recherche, pas une citation verbatim du README ; à vérifier directement dans le README ou le code source avant de s'appuyer dessus en documentation finale.
- Pour un chaînage gapless de chunks TTS avec `node-web-audio-api`, le pattern `AudioBufferSourceNode.start(nextTime)` documenté pour le Web Audio API standard (voir section précédente) devrait s'appliquer identiquement, `node-web-audio-api` visant l'implémentation conforme au standard — mais la race condition de scheduling documentée dans l'issue #2636 du spec Web Audio générique s'appliquerait potentiellement aussi ici (non testé ni confirmé spécifiquement sur ce module dans cette passe).
- Pour `audify`, l'absence de méthode pause native implique que le pause en pratique se ferait en **arrêtant l'écriture de nouveaux chunks PCM** (le tampon interne finit par se vider) plutôt que par un vrai pause du flux matériel — cohérent avec la formulation de l'objectif de recherche (« pause by stopping writes »), mais cette technique implique une latence de reprise différente d'un vrai pause matériel et n'est pas explicitement documentée comme pattern recommandé par la doc Audify elle-même dans les pages consultées.

### Gaps
- Le texte exact du README ircam-ismm concernant `suspend()`/`resume()` n'a pas pu être cité verbatim (uniquement une synthèse) — recommandé de relire le README source directement (`https://github.com/ircam-ismm/node-web-audio-api#readme`) avant publication finale si une citation exacte est nécessaire.
- Aucune information trouvée sur le comportement de `node-web-audio-api` en sandbox macOS (permissions microphone/audio, notarisation) — la question posée sur le sandbox macOS reste sans réponse.
- Aucune issue GitHub spécifique à la sélection de device/sink (au-delà de `sinkId: {type:'none'}` pour headless) n'a été trouvée dans cette passe — la sélection fine d'un device de sortie spécifique (par nom/ID) sur chaque OS n'est pas confirmée comme documentée.
- Aucune mention trouvée de problèmes spécifiques à Wayland pour `node-web-audio-api` (le module opère au niveau audio, pas display, donc Wayland n'est probablement pas pertinent — mais ce n'est pas confirmé explicitement par une source).

## Which Node sentence chunker for streaming LLM text is usable today under MIT/Apache?

### Takeaway
Il n'existe pas d'équivalent Node/TypeScript direct et largement adopté de `stream2sentence` (Python, KoljaB) pour la détection de limites de phrases en streaming avec gestion des abréviations/décimales — les candidats trouvés (`llm-text-splitter`, `llm-splitter`, `llm-chunk`) sont conçus pour du chunking de texte complet (RAG/embeddings), pas pour du découpage incrémental d'un flux de tokens LLM ; `Intl.Segmenter` avec `granularity: "sentence"` (natif Node/V8, aucune licence à gérer) est l'outil le plus solide pour la segmentation de phrases mais son usage documenté suppose une chaîne complète, pas un flux partiel.

### Cited Findings
- `stream2sentence` (Python, référence du patron demandé) : librairie de détection de phrases en temps réel qui délivre des phrases complètes depuis un flux continu de caractères, avec gestion documentée des abréviations courantes (Mr., Dr., Mrs.) pour éviter les coupures indues, évite de couper sur les points de décimales, propose une option de nettoyage (suppression de liens/emojis), et un paramétrage pour équilibrer vitesse vs fiabilité en tenant compte du temps de génération du moteur TTS. — [stream2sentence sur PyPI](https://pypi.org/project/stream2sentence/), [KoljaB/stream2sentence sur GitHub](https://github.com/KoljaB/stream2sentence)
- Un problème documenté et répandu dans l'écosystème (illustrant pourquoi la gestion des abréviations/décimales est critique) : un ticket sur `hass-edge-tts` rapporte que le TTS streaming coupe sur les virgules, ce qui fait que les virgules décimales (« 22,1 ») sont prononcées comme « 22 1 » au lieu de « vingt-deux virgule un ». Un autre ticket (projet `backtalk`) documente que le streaming de phrases coupe sur le point dans « Dr. », « 9 a.m. », « e.g. » et les initiales, produisant des utterances tronquées audibles. — [hasscc/hass-edge-tts issue #76](https://github.com/hasscc/hass-edge-tts/issues/76), [jaredrhod/backtalk issue #31](https://github.com/jaredrhod/backtalk/issues/31)
- `llm-text-splitter` (npm, GitHub `betcorg/llm-text-splitter`) : **licence MIT**. Supporte 4 méthodes de découpage — phrase, paragraphe, titres markdown, et regex personnalisée. L'API documentée est `split(text: string)` qui prend un **texte complet** et retourne un tableau de chunks — **aucune capacité de streaming/incrémental documentée**. Propose la suppression d'espaces superflus et un chevauchement (overlap) configurable entre chunks, mais **aucune logique spécifique pour abréviations, décimales, ou blocs de code** n'est documentée. Dépôt actif avec 39 commits, tooling moderne (eslint, tsconfig, pnpm) mais sans date de dernier commit confirmée. — [betcorg/llm-text-splitter GitHub](https://github.com/betcorg/llm-text-splitter)
- `llm-splitter` (npm, via Nearform) : présenté comme un chunker de texte rapide et léger pour embeddings/LLM, avec support de chaînes, tableaux, et tokenisation personnalisée, type-safe en TypeScript — orienté chunking pour recherche/embeddings plutôt que segmentation de phrases pour TTS streaming. — [Introducing llm-splitter (Nearform)](https://nearform.com/digital-community/introducing-llm-splitter-a-fast-lightweight-text-chunker-for-embeddings-llms-and-more/)
- `llm-chunk` (npm) : décrit comme un splitter de texte « super simple » pour Node.js, 1 KB compressé — pas de détails trouvés sur la gestion streaming/abréviations. — résultat de recherche npm, licence non confirmée dans cette passe.
- `Intl.Segmenter` (natif JavaScript/Node, aucune dépendance ni licence) : le constructeur accepte une `granularity` valant `"grapheme"`, `"word"`, ou `"sentence"` ; en mode `"sentence"`, il permet de segmenter sans avoir à gérer soi-même les points finaux spécifiques à chaque langue. La méthode `.segment()` retourne un itérable `Segments` exposant les segments trouvés entre les frontières détectées. — [MDN Intl.Segmenter](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter), [MDN blog: locale-sensitive segmentation](https://developer.mozilla.org/en-US/blog/javascript-intl-segmenter-i18n/)

### Inferences
- Aucun package Node/TypeScript trouvé dans cette passe ne réplique fidèlement le comportement de `stream2sentence` (segmentation incrémentale sur flux partiel + gestion d'abréviations/décimales + tuning vitesse/fiabilité pour TTS) — les trois bibliothèques npm identifiées (`llm-text-splitter`, `llm-splitter`, `llm-chunk`) semblent toutes conçues pour du chunking de corpus complet à destination du RAG/embeddings, pas pour du découpage de phrases en flux LLM token-par-token à des fins de synthèse vocale progressive.
- Une implémentation Node pragmatique et « usable aujourd'hui » consisterait probablement à combiner `Intl.Segmenter({granularity: 'sentence'})` (natif, MIT/Apache non applicable puisqu'il fait partie du moteur JS lui-même, donc sans risque de licence) sur le texte accumulé au fur et à mesure du flux, avec une liste d'abréviations à exclure des frontières de phrase codée à la main (le pattern documenté par `stream2sentence` et les tickets `hass-edge-tts`/`backtalk` ci-dessus) — mais cette combinaison n'a pas été trouvée déjà implémentée et publiée comme package réutilisable dans cette passe.
