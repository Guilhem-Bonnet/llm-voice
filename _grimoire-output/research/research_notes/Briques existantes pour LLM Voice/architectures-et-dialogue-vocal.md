# Reference Architectures: VS Code Sidecar Extensions & Local Voice Conversation Pipelines (2026)

## Which sidecar pattern lets us ship one VSIX with zero install and still run audio playback outside the extension host and webview? What are the pitfalls (multiple windows, remote/SSH/WSL, Codespaces)?

### Takeaway
Every mature extension that needs a heavier local process either (a) runs its "core" logic in-process inside the extension host's own Node.js runtime (Continue.dev on VS Code), or (b) spawns a standalone, bundled Node/native binary and talks to it over JSON-RPC on stdio or a local socket (Cody agent, rust-analyzer, Jupyter kernels via ZeroMQ). None of the researched sources documented lock-file/port-discovery or single-instance-across-windows mechanisms in detail, but VS Code's own 2026 "Agent Host" feature formalizes this exact problem with a dedicated process (local utility process or remote server) reachable over a JSON-RPC protocol (AHP) via WebSocket remotely or an in-process message port locally — explicitly designed so sessions can run locally, in a Dev Container, or remotely, and survive window close. For audio playback specifically, the constraining fact is `ExtensionKind`: UI extensions always execute on the user's local machine, while workspace extensions run wherever the workspace lives (which can be remote/SSH/WSL/a container/Codespaces) — so any component that must produce sound on the user's speakers has to be (or delegate to) a UI-kind extension host component, never the workspace-side sidecar.

### Cited Findings
- Continue.dev: "Continue follows a 'Sidecar' architecture where the IDE extension communicates with a core process," but on VS Code specifically "the extension runs the core backend in-process within the Node.js runtime," while on IntelliJ the core runs as "a separate Node.js process" communicating over "JSON over stdin/stdout or TCP." — [DeepWiki: System Architecture](https://deepwiki.com/continuedev/continue/2.1-system-architecture), [DeepWiki: Communication Flow](https://deepwiki.com/continuedev/continue/2.4-communication-flow)
- Sourcegraph Cody: "`@sourcegraph/cody-agent` implements a JSON-RPC server to interact with Cody via stdout/stdin," intended for non-ECMAScript clients (JetBrains, Neovim); "both the agent server and client run on the same computer and there can only be one client per server," and "a Cody agent is a standalone Node.js/TypeScript process." — [npm: @sourcegraph/cody-agent](https://www.npmjs.com/package/@sourcegraph/cody-agent)
- rust-analyzer: the language-server binary is downloaded into the extension's own install directory (`~/.vscode/extensions/rust-lang.rust-analyzer-...` locally, `~/.vscode-server/extensions` under Remote/WSL, with a NixOS-specific copy under `globalStorage`), and the extension prompts to download/update the matching binary version automatically. — [rust-analyzer VS Code book](https://rust-analyzer.github.io/book/vs_code.html)
- Jupyter (vscode-jupyter): "VS Code spawns the kernel process and communicates with the kernel process directly over zmq (without the need to install Jupyter or Python)"; if ZeroMQ is unavailable it falls back to launching `jupyter notebook|lab` and using the Jupyter Server HTTP API instead. — [vscode-jupyter wiki: Kernel Discovery](https://github.com/microsoft/vscode-jupyter/wiki/Kernel-Discovery-(architecture)), [General overview of Kernel Discovery & Execution](https://github.com/microsoft/vscode-jupyter/wiki/General-overview-of-Kernel-Discovery-&-Execution-in-Jupyter-(&-extension))
- Tabnine: ships a native binary inside the extension (requires glibc ≥2.28, Vulkan or LLVMPipe); it was refactored so "deep local model evaluation" runs in its own process (`TabNine-deep-local`) exposing "a TCP endpoint that the main Tabnine binary can communicate with" — explicitly done to cut per-window memory footprint by sharing one local-inference process instead of one per window. — [Tabnine architecture docs](https://docs.tabnine.com/main/welcome/readme/architecture), [DEV: Tabnine shared process announcement](https://dev.to/tabnine/major-announcement-tabnine-significantly-reduces-memory-footprint-by-using-a-single-shared-process-for-local-inference-g6e)
- VS Code Agent Host (Microsoft, blogged 2026-08-26): "a dedicated process that owns sessions and can run locally as a VS Code utility process or remotely as a standalone server," using "a message port for local IPC and AHP JSON-RPC over WebSocket for remote connections," with "immutable state with pure reducers for synchronized session data" and clients subscribing to URI-addressed channels; sessions "continue after you close the folder or editor window where they started" and can "run on your machine, inside a Dev Container, or on a remote machine." — [VS Code docs: Agent Host architecture](https://code.visualstudio.com/docs/agents/concepts/agent-host), [VS Code blog: Introducing the Agent Host](https://code.visualstudio.com/blogs/2026/08/26/agent-host-architecture)
- `ExtensionKind`: `["ui"]` extensions "are always run on the user's local machine"; `["workspace"]` extensions "require access to workspace contents and need to run where the workspace is located, either on the local or remote machine"; `["ui","workspace"]` prefers local but falls back to workspace-side, and vice versa for `["workspace","ui"]`. — [VS Code docs: Supporting Remote Development](https://code.visualstudio.com/api/advanced-topics/remote-extensions)
- `vscode.env.asExternalUri`: used "for port forwarding without launching a new browser window," forwards HTTP/HTTPS traffic from local OS to the remote host running the webview's server; "the URI passed back by the API may not reference localhost at all" (important for Codespaces' browser editor, where localhost cannot be used); results should not be cached because forwarded tunnels can be closed by the user; in the Codespaces browser editor "the forwarding mechanism ... currently supports only http and https requests." — [VS Code docs: Remote Development FAQ / Remote extensions guide](https://code.visualstudio.com/api/advanced-topics/remote-extensions)
- Dev Containers CLI: "Your editor (VS Code, JetBrains, the CLI) reads a devcontainer.json file, builds or pulls an image, starts the container, mounts your source code, and connects to it"; the VS Code Dev Containers extension "includes a variation of the Dev Container CLI." — [containers.dev: Supporting tools](https://containers.dev/supporting), [VS Code docs: Dev Container CLI](https://code.visualstudio.com/docs/devcontainers/devcontainer-cli)
- `ELECTRON_RUN_AS_NODE`: VS Code's `process.execPath` is the Electron helper, not a plain Node binary; when spawning, "the cliCommand prefers a real node on the same PATH and only falls back to the helper with `ELECTRON_RUN_AS_NODE` set on the spawn itself"; critically, "in VSCode's `server-cli.js`, it checks for the `ELECTRON_RUN_AS_NODE` environment variable, and if it's present it maps the `fs` module to point to the `original-fs` module" — a module "present in Electron, but not in base NodeJS; base NodeJS is what's used by the VSCode remote server," so carrying this env var into a subprocess spawned from a remote extension host can break it. — [GitHub issue discussion, muncherelli PR #140](https://github.com/8BitScript/8bitscript/pull/140), [GitHub issue microsoft/vscode#240901](https://github.com/microsoft/vscode/issues/240901)
- AudioLens (a VS Code audio-analysis extension) handles the Remote-SSH split explicitly by reading audio files from the remote workspace but rendering/playing them "in a local VS Code Webview" — i.e., playback stays client-side even when the files/logic are remote. — [Simon's Dream Universe: Introducing AudioLens](https://simzhou.com/en/posts/2026/introducing-audiolens-audio-inspection-analysis-extension-vscode/)

### Inferences
- For a zero-install VSIX that must play audio locally even under Remote-SSH/WSL/Dev Containers/Codespaces, the safest pattern is to mark the playback-owning component `extensionKind: ["ui"]` (so it always runs on the user's physical machine) and keep any heavier LLM/TTS orchestration logic in a workspace-side sidecar process (spawned the way Cody's agent or rust-analyzer's server binary are), communicating between the two extension hosts via VS Code's built-in cross-extension-host messaging rather than trying to stream raw audio over `asExternalUri`, which the sources show is HTTP(S)-only in the Codespaces browser case and not built for arbitrary local process spawning on the client.
- Relying on `ELECTRON_RUN_AS_NODE` to avoid bundling a Node binary is a known fragile shortcut: it works for a purely local spawn but the same code path breaks once the extension runs against a plain (non-Electron) remote server, per the `server-cli.js`/`original-fs` finding — a genuine "zero install, works everywhere" sidecar should bundle its own Node runtime or a compiled binary per platform (as rust-analyzer and Tabnine do) rather than depend on Electron's Node-emulation flag.
- The single-instance-across-windows problem (one sidecar shared by N VS Code windows) is explicitly solved architecturally by VS Code's new Agent Host (a session-owning process addressable by multiple clients over AHP), which is the closest documented analogue found to "one shared local server, N thin UI clients."

### Gaps
- No source found describing GitLens' or Live Share's own internal sidecar/lock-file/port-discovery mechanics specifically (Live Share search results surfaced VS Code's unrelated, newer "Agent Host" feature and general collaboration docs, not Live Share's session-server internals) — this needs a dedicated follow-up against the Live Share extension source or Microsoft Learn docs.
- No source found on how any of these pairs (extension + sidecar) are tested (e.g., integration test harnesses spinning up both the extension host and the sidecar) — flagged as an open question for the report.
- Copilot's own agent-host implementation details beyond the general AHP protocol description were not independently verified against Copilot's source (the VS Code docs describe the platform-level Agent Host, which multiple "first-party agent adapters" plug into, but a specific vendor-level (Tabnine, Copilot) crash-recovery/reconnect policy was not found).

## How do mature voice pipelines cut a streaming LLM answer into TTS-ready sentences with low latency and keep gapless playback?

### Takeaway
The two production pipelines with public documentation (Pipecat, RealtimeTTS) converge on the same design: buffer streaming LLM tokens until a sentence-boundary heuristic fires (punctuation-based, with guards against abbreviations/decimals and a minimum-length threshold), then hand that sentence to TTS while the previous sentence's audio is still playing; both also expose a lower-latency "raw token" mode that trades prosody/batching for responsiveness. Turn-taking frameworks (LiveKit) separately layer VAD + a semantic/audio turn-detector model on top of this to decide when the user has actually finished talking and it's safe to start generating a response, and use word-level TTS timestamps to cut audio cleanly on interruption.

### Cited Findings
- Pipecat: "by default, TTS aggregates streaming tokens into complete sentences before synthesis (`TextAggregationMode.SENTENCE`)," with sentence detection following the TTS service's configured `language`; developers can switch to `TextAggregationMode.TOKEN` to stream tokens directly to TTS "reducing latency but potentially affecting speech quality." — [Pipecat docs: Text to Speech](https://docs.pipecat.ai/pipecat/learn/text-to-speech)
- Pipecat's sentence buffer "accumulates tokens and yields complete sentences," detecting "sentence-ending punctuation (., !, ?) followed by whitespace," "excludes false positives from abbreviations and decimal numbers," and "enforces a minimum sentence length of 10 characters to avoid sending fragments to TTS"; in sentence mode this adds roughly "200-300ms per sentence" of latency. — [futureagi.com: How to Optimize Pipecat Voice Agent Latency in 2026](https://futureagi.com/blog/how-to-optimize-pipecat-latency-2026/)
- Pipecat's frame-based pipeline "streams text frames from LLMService into TTSService natively," and ensuring every downstream service consumes `TextFrame` as it arrives "can save 300-600ms off P95 latency"; end-to-end latency is "often under 200ms" in sentence mode, with audio bytes streaming back and playing immediately. — [Pipecat docs: Text to Speech](https://docs.pipecat.ai/pipecat/learn/text-to-speech)
- Pipecat uses word-level timestamps (e.g., from Cartesia) so that on interruption it can "accurately capture which words were spoken up to that point, enabling better context management." — [Pipecat docs: Text to Speech](https://docs.pipecat.ai/pipecat/learn/text-to-speech)
- RealtimeTTS: sentence splitting during streaming synthesis uses "stream2sentence's nltk+rule-based consensus mode," letting it process fragments "as they arrive from LLMs without waiting for complete sentences"; it supports generator-based input so "text to arrive mid-playback," and offers direct playback, WAV-file, or chunk-callback output modes; one engine (Qwen) reports "~81ms predicted audible onset on tested hardware." — [RealtimeTTS README](https://github.com/KoljaB/RealtimeTTS/blob/master/README.md)
- LiveKit Agents' recommended (default) turn-detector model "predicts end of turn from both the meaning of speech and its acoustic properties, on top of VAD," combining audio+text signals; alternative modes are VAD-only ("minimal latency" or for languages the model doesn't cover) and STT-endpointing (using the STT provider's own phrase-end signals, e.g. AssemblyAI/Deepgram Flux) while VAD still independently drives interruption detection. — [LiveKit docs: Turn detection configuration](https://docs.livekit.io/agents/v1/build/turn-detection/configuration/)
- LiveKit's "adaptive" interruption mode (default on LiveKit Cloud with most STT providers) "distinguishes intentional interruptions from conversational backchanneling," using a model that "analyzes the user's audio stream within the first few hundred milliseconds of detected speech" during the agent's turn; a "vad" mode is also available using raw speech start/stop cues, plus false-interruption recovery and minimum duration/word thresholds. — [LiveKit blog: Solving unwanted interruptions with Adaptive Interruption Handling](https://livekit.com/blog/adaptive-interruption-handling), [LiveKit docs: Turn detection configuration](https://docs.livekit.io/agents/v1/build/turn-detection/configuration/)
- Wyoming protocol (used by Home Assistant Assist) has explicit streaming message types for chunked STT/TTS: `transcript-start`/`transcript-chunk`/`transcript-stop` and `synthesize-start`/`synthesize-chunk`/`synthesize-stop`, plus `voice-started`/`voice-stopped` VAD events — a transport-level analogue to sentence/streaming chunking, independent of any specific chunking heuristic. — [Wyoming protocol repo](https://github.com/OHF-Voice/wyoming)

### Inferences
- The reusable pattern for a Node/TS implementation is: (1) a sentence-boundary detector modeled on Pipecat's/stream2sentence's rules (punctuation + abbreviation/decimal exceptions + minimum length) rather than naive `split('.')`; (2) a small look-ahead/double-buffer so sentence N+1's TTS synthesis starts while sentence N is still playing, which is how both pipelines describe achieving "audio plays immediately" without gaps; (3) treating turn-detection (when to *start* generating a reply) as a separate concern from sentence-chunking (how to *stream* the reply), layering VAD plus, ideally, a semantic/acoustic turn model as LiveKit does, rather than relying on VAD silence timeouts alone for barge-in responsiveness.

### Gaps
- No concrete open-source Node/TypeScript equivalent of Python's `stream2sentence` library was identified in this research pass; this should be checked directly against npm in a follow-up.
- The exact low-level audio-buffering/scheduling technique used to guarantee "gapless" playback (e.g., ring buffers, Web Audio API precise scheduling, or simple sequential-queue playback) was not documented in the fetched Pipecat/RealtimeTTS pages beyond the high-level "streams and plays immediately" description.

## Which of these are Node/TypeScript (reusable directly) vs Python (patterns only)?

### Takeaway
Almost all of the named open-source voice-pipeline projects (Pipecat, LiveKit Agents' documented turn-detector, Vocode, RealtimeTTS/RealtimeSTT, Kyutai Moshi/Unmute, the VoiceMode MCP server) are Python, so they are reusable only as *design patterns*, not as libraries to import into a Node/TS codebase. On the VS Code/sidecar side, by contrast, Continue.dev's core and Sourcegraph's Cody agent are both explicitly Node.js/TypeScript and directly reusable or forkable; the Wyoming protocol and MCP itself are transport/protocol specifications (JSONL+PCM over TCP; JSON-RPC-based tool-calling) that are language-agnostic and straightforward to implement natively in Node.

### Cited Findings
- Cody: "a Cody agent is a standalone Node.js/TypeScript process responsible for LLM communication and document context parsing." — [npm: @sourcegraph/cody-agent](https://www.npmjs.com/package/@sourcegraph/cody-agent)
- Continue.dev: on VS Code, "the extension runs the core backend in-process within the Node.js runtime" (i.e., TypeScript). — [DeepWiki: System Architecture](https://deepwiki.com/continuedev/continue/2.1-system-architecture)
- RealtimeTTS: "is Python-only with no Node.js or TypeScript support mentioned in documentation," requiring Python 3.11+ for some engines. — [RealtimeTTS README](https://github.com/KoljaB/RealtimeTTS/blob/master/README.md)
- Vocode: "is exclusively Python-based," though "there's a separate React SDK available for JavaScript/TypeScript integration, allowing frontend applications to interface with Vocode's backend services" — i.e., the JS piece is a thin client, not the orchestration engine. — [Vocode GitHub / docs](https://github.com/vocodedev/vocode-core), MIT license confirmed.
- VoiceMode MCP server install command is `claude mcp add --scope user voicemode -- uvx --refresh voice-mode` (`uvx` = Python's uv-based runner), indicating a Python implementation. — [VoiceMode GitHub](https://github.com/mbailey/voicemode)
- Wyoming protocol is "basically JSONL + PCM audio" over TCP, i.e., transport/format-defined rather than language-bound, released under the MIT license. — [Wyoming protocol repo](https://github.com/OHF-Voice/wyoming)

### Inferences
- Given this split, a Node/TS-first local product will need to either (a) treat Python voice components (RealtimeTTS/RealtimeSTT, Vocode, Moshi/Unmute) as external sidecar processes reached over a protocol like Wyoming or a bespoke JSON/WebSocket API — itself an instance of the sidecar architecture researched in part 1 — or (b) reimplement the specific patterns (sentence-chunking rules, turn-detection layering) natively in TypeScript, since no ready-made Node library performing an equivalent role surfaced in this research.

### Gaps
- LiveKit Agents' language coverage was not fully disambiguated: this research only confirmed the documented turn-detection *behavior*, not whether LiveKit ships an official Node.js/TypeScript Agents SDK with equivalent turn-detection support alongside its Python SDK — needs direct verification against LiveKit's SDK docs/repo list.
- Kyutai Moshi/Unmute's implementation language(s) and exact license were not confirmed beyond "open-source" / self-hostable claims from kyutai.org; needs a direct repo/license check.

## Is there an MCP server or CLI pattern that lets Claude Code / other agents speak or listen locally, and how do they capture the agent's output (hooks, transcripts)?

### Takeaway
VoiceMode (mbailey/voicemode) is a concrete, MIT-licensed MCP server built exactly for this: it lets Claude Code (and other MCP-capable agents) have "natural voice conversations," and it is installed as a normal MCP server (`claude mcp add ... uvx voice-mode`) that exposes voice as a tool the agent calls, rather than as an out-of-band transcript-scraping hook — though this research could not confirm from the fetched material whether it also offers a Claude Code hook-based mode.

### Cited Findings
- "VoiceMode brings natural voice conversations to Claude Code and other AI coding assistants, and is open-source, local-first, and OpenAI-compatible." Install: `claude mcp add --scope user voicemode -- uvx --refresh voice-mode`. — [VoiceMode GitHub](https://github.com/mbailey/voicemode), [LobeHub: voice-mcp](https://lobehub.com/mcp/mbailey-voice-mcp)
- "For privacy-focused or offline usage, voice-mcp supports local speech services like Whisper.cpp for local speech-to-text and Kokoro for local text-to-speech," both exposing OpenAI-compatible APIs so the same integration code can point at local or cloud engines. — [Gist: Voice Mode for Claude Code setup guide](https://gist.github.com/jlmalone/02d09aeb4e09890a8a9e7c2333a18377), [VoiceMode GitHub](https://github.com/mbailey/voicemode)
- "When local voice isn't an option, VoiceMode Connect provides remote voice through a web app or mobile device by adding the VoiceMode MCP server to Claude and opening app.voicemode.dev on a phone or browser." — [VoiceMode.dev](https://voicemode.dev/)
- VoiceMode is MIT-licensed. — [VoiceMode GitHub](https://github.com/mbailey/voicemode)

### Inferences
- The dominant 2026 pattern for giving a coding agent voice I/O is an MCP server exposing an explicit tool (e.g., a "converse"/"speak"/"listen" tool) that the agent calls as part of its normal tool-use loop, giving the agent (not an external hook) control over when to talk — this differs from a hook-based approach that would mirror all textual output to TTS regardless of the agent's own judgment.

### Gaps
- Could not confirm from the fetched VoiceMode README/GitHub page whether it additionally integrates via Claude Code's hook system (e.g., a `Stop` hook auto-speaking final responses) as opposed to being purely MCP-tool-driven; the fetched content described the MCP/tool architecture but not hook-level integration in detail.
- Other named tools in the assignment (talk-to-claude, generic "whisper dictation MCP" servers) were not researched in this pass due to the tool-call budget; flagged as a gap for a follow-up search specifically on those names.

## What do these projects do for local-only guarantees (no egress) and for tests without a human listener?

### Takeaway
Local-only operation is explicitly designed for in the Home-Assistant/Wyoming ecosystem and in VoiceMode (both can run fully offline with local STT/TTS engines, falling back to cloud only if a cloud API key is explicitly configured); Open WebUI + Speaches is another self-hostable stack achieving the same locally. No source in this research pass documented an automated testing strategy for voice quality/correctness without a human listener — this appears to be an unaddressed gap across all reviewed projects' public documentation.

### Cited Findings
- Home Assistant / Wyoming: "Home Assistant's Wyoming protocol connects local wake word detection (openWakeWord or microWakeWord), speech-to-text (Whisper), text-to-speech (Piper), and intent handling into a voice pipeline where your audio stays inside your LAN." The Wyoming integration was introduced in Home Assistant 2023.5 and, as of the source consulted, is used by "9.1% of the active installations." — [botmonster.com: Home Assistant can hear your wake word with no cloud](https://botmonster.com/smart-home/home-assistant-voice-pipelines-local-wake-word-wyoming/), [Home Assistant Wyoming integration docs](https://www.home-assistant.io/integrations/wyoming/)
- VoiceMode "works offline - optional local voice services" via Whisper.cpp + Kokoro; cloud usage requires the user to explicitly "export OPENAI_API_KEY," i.e., no egress unless deliberately configured. — [VoiceMode GitHub](https://github.com/mbailey/voicemode)
- Open WebUI + Speaches: a self-hosted voice stack where Speaches provides local STT/TTS (default STT model `Systran/faster-whisper-small`) to Open WebUI's Admin Panel audio settings via an OpenAI-compatible endpoint; the documented prerequisite is roughly "14 GB of available VRAM to run the LLM, STT, and TTS models simultaneously" locally. — [Olares docs: Configure voice interactions in Open WebUI](https://www.olares.com/docs/use-cases/openwebui-audio)
- Kyutai's Unmute and Moshi are described as fully open-source and self-hostable ("every component open-source"), positioned specifically so developers can run real-time voice AI without depending on a cloud provider. — [kyutai.org/unmute](https://kyutai.org/unmute/)
- RealtimeTTS carries a licensing caveat relevant to "local-only" claims at the product level: although the library is MIT, "Engine providers, model weights, voice data, datasets, generated audio, and third-party services can have separate terms," so a fully local, license-clean deployment requires checking each selected engine individually (e.g., some listed engines are cloud APIs like ElevenLabs/Azure/OpenAI, not local). — [RealtimeTTS README](https://github.com/KoljaB/RealtimeTTS/blob/master/README.md)

### Inferences
- "Local-only" in this space is generally a *configuration choice* layered on top of pipelines that otherwise default to (or equally support) cloud providers, rather than an architectural guarantee baked into the pipeline itself (Pipecat, LiveKit Agents, and Vocode all list numerous cloud STT/TTS/LLM providers as first-class options) — a genuinely no-egress product must actively pin the configuration to local engines (Whisper.cpp, Kokoro, Piper) and, per the RealtimeTTS caveat, verify per-engine licensing/data terms rather than trusting the library's own top-level license.

### Gaps
- No project reviewed documented a testing methodology for voice quality/correctness that doesn't require a human listener (e.g., transcript round-trip diffing, audio fingerprinting, or synthetic MOS scoring); this was not mentioned in any of the fetched pages (Pipecat docs, RealtimeTTS README, LiveKit docs, VoiceMode README, Wyoming repo). This should be treated as an open research question rather than assumed absent — direct inspection of each project's CI configuration/test suite (outside this pass's tool budget) would be needed to answer it definitively.
- Pipecat's and LiveKit Agents' own top-level open-source licenses were not confirmed in the fetched pages (no explicit license text appeared in the content retrieved) — needs a direct check of each project's `LICENSE` file.
- Sourcegraph Cody agent's license could not be confirmed in this pass: the intended fetch of `npmjs.com/package/@sourcegraph/cody-agent` for deeper detail returned an HTTP 403; only the earlier WebSearch summary of that page was available as a source.
