# Projets équivalents / concurrents de "LLM Voice"

Périmètre couvert : (a) extensions VS Code de lecture à voix haute / TTS, (b) fonctionnalités voix natives de VS Code / Copilot, (c) outils "parler à son agent de code" (Claude Code, Copilot, Cursor, aider), (d) applications desktop open-source de lecture à voix haute / assistants vocaux locaux.

Note méthodologique : les "installs" et "stars" ci-dessous sont les chiffres lus au moment de la recherche (fin septembre 2026) sur le Marketplace VS Code ou GitHub ; ils évoluent en continu. Aucune date de dernière activité précise n'a pu être confirmée pour plusieurs extensions Marketplace (le Marketplace n'affiche pas toujours de date lisible) — c'est noté explicitement comme lacune plutôt que deviné.

## Quelles extensions VS Code font du text-to-speech / lecture à voix haute aujourd'hui, comment jouent-elles l'audio, et quels sont leurs avis/plaintes ?

### Takeaway
Il existe déjà au moins une dizaine d'extensions VS Code de lecture à voix haute (majoritairement markdown), avec un chevauchement direct et frappant sur le positionnement de LLM Voice — en particulier **Markdown Read Aloud (Piper)** (Piper local, nettoyage markdown, offline) et **Markdown TTS: Read Aloud & AI Narration** (multi-moteurs + narration IA + résumé de git diff par la voix) ; toutes ont une traction encore faible (quelques centaines d'installs, peu ou pas d'avis), ce qui suggère un marché naissant et peu consolidé plutôt que déjà verrouillé par un leader.

### Cited Findings
- **Markdown Read Aloud (Piper)** — [Marketplace](https://marketplace.visualstudio.com/items?itemName=Larsini.offline-markdown-read-aloud) — Licence MIT — TypeScript/VS Code extension — v1.0.1 — 362 installs, 0 avis. Lit le Markdown/texte en local via **Piper** (~25 Mo + 60-110 Mo/voix), **Supertonic 3** (meilleure qualité, ~180 Mo) ou **Pocket TTS** (expérimental, plusieurs Go). Joue l'audio soit dans un **webview panel** (cross-plateforme), soit via des lecteurs système (PowerShell/Windows, `afplay`/macOS, `aplay`/`paplay`/`play`/`ffplay`/Linux). Nettoie la syntaxe markdown, retire les blocs de code par défaut, remplace les images par leur alt-text. **Défauts constatés** : le surlignage de phrase se désactive si le document est édité pendant la lecture ; les lecteurs système ne permettent pas de vraie pause ; le catalogue de voix Piper nécessite Internet (l'usage 100% offline est limité à 3 voix intégrées) ; l'export Supertonic est mono-process (pas de parallélisation).
- **Markdown TTS: Read Aloud & AI Narration** — [Marketplace](https://marketplace.visualstudio.com/items?itemName=AbhishekShr.markdown-tts) — Gratuit (licence non précisée sur la page) — 379 installs, 0 avis, pas de date de mise à jour affichée. Combine TTS offline (SAPI/Windows via PowerShell, `say`/macOS) et **voix neurales Microsoft Edge en ligne** (400+ voix, streaming pour fichiers longs). Ajoute une **narration IA** ("bring your own key" OpenAI/Anthropic/Groq/Gemini) qui explique le contenu, et une fonctionnalité de résumé vocal de `git diff` (local, sans envoyer tout le repo). C'est la fonctionnalité la plus proche de ce que LLM Voice appelle "profils de narration (réécriture LLM)". **Défauts** : sur Linux, seul le moteur Edge est disponible (pas d'offline natif) ; le parsing markdown se fait par regex (pas un vrai parseur) ; ajuster la vitesse sur le moteur Edge introduit ~1 minute de retard sur le chunk en cours de lecture.
- **ElevenLabs Text-to-Speech for VSCode** — [Marketplace](https://marketplace.visualstudio.com/items?itemName=lekman.tts-code) — Gratuit, statut "Preview" — 2 040 installs, 0 avis. Moteur **cloud ElevenLabs uniquement** (nécessite un compte/clé API), limité aux fichiers `.md`/`.txt`. Offre un **surlignage de texte synchronisé** avec la lecture (référence UX directe pour le "synchronized highlighting" visé par LLM Voice) et un export MP3. Clés API stockées via `SecretStorage` de VS Code (bonne pratique de sécurité à reprendre). **Défaut** : dépendance 100% cloud, pas d'option locale, coût par caractère ElevenLabs.
- **VS Code Speech (bierner.speech) / Read Aloud text (azu)** — [github.com/mattbierner/vscode-speech](https://github.com/mattbierner/vscode-speech), [github.com/azu/vscode-read-aloud-text](https://github.com/azu/vscode-read-aloud-text) — Licence MIT. `azu/vscode-read-aloud-text` : 40 commits, 15 stars, 5 forks, 5 issues ouvertes, **semble peu actif** (pas de date de dernier commit affichée mais faible engagement global) ; utilise les moteurs TTS de l'OS via la librairie `say.js`, avec surlignage de la portion lue, options `speech.voice`/`speech.speed`. Architecture "native" (pas de webview) — pattern réutilisable pour un moteur "voix système" simple.
- **Mimo TTS Markdown Reader** et **Vocalize MD** existent également sur le Marketplace (lus dans les résultats de recherche) mais n'ont pas été inspectés en détail — voir Gaps.
- **Speechify (hddevteam)** — [github.com/hddevteam/speechify](https://github.com/hddevteam/speechify) — Licence MIT — architecture TypeScript — 6 stars. Convertit texte sélectionné/document en fichiers audio (MP3/WAV/OGG) via clic droit. Trois backends : **Azure Speech Services** (cloud, 200+ voix, 60+ langues, styles émotionnels, rôles narrateur/jeune/âgé), **CosyVoice** (local, FastAPI) et **Qwen3-TTS + MLX-Audio** (local, Apple Silicon). Interface bilingue EN/CN. **Défaut** : fichiers >10 Mo de texte peuvent prendre plusieurs minutes ; rate limiting Azure possible en heures de pointe ; les "voice roles" ne sont dispos que sur certaines voix neurales.
- **Feature request non résolue côté VS Code core** : l'issue [microsoft/vscode#298581](https://github.com/microsoft/vscode/issues/298581) demande un TTS intégré au preview Markdown — confirmée non implémentée nativement, ce qui laisse la porte ouverte à une extension tierce dédiée au markdown.
- **Plaintes utilisateurs documentées** : un développeur dyslexique signale sur GitHub que la fonctionnalité "read aloud" de VS Code/Copilot Chat ne s'arrête pas correctement même à la fermeture de VS Code, et que chaque phrase est précédée du mot "agent" (bruit vocal parasite) — [source discutée dans les résultats de recherche, issue liée à microsoft/vscode](https://github.com/microsoft/vscode/issues/296720). Une autre issue ouverte demande explicitement plus de contrôles sur le read-aloud du Chat (position de départ, navigation, vitesse, lecture du texte visible uniquement) : [microsoft/vscode#301431](https://github.com/microsoft/vscode/issues/301431). Une autre signale que le TTS auto-synthétisé lit du contenu verbeux en cours de génération (tool calls, "thinking") au lieu de la seule réponse finale : [microsoft/vscode#296720](https://github.com/microsoft/vscode/issues/296720).

### Inferences
- Le marché des extensions VS Code de lecture à voix haute est fragmenté et à faible traction (aucune extension identifiée ne dépasse ~2 000 installs), ce qui indique une opportunité de différenciation plutôt qu'un espace saturé — mais aussi un signal de risque : ces produits n'ont peut-être pas encore trouvé leur audience/traction.
- Le pattern architecture le plus solide pour un usage 100% local (comme visé par LLM Voice) est **process externe (Piper/say/espeak) + player système ou webview**, pas un moteur TTS embarqué en JS pur — c'est ce que font Markdown Read Aloud (Piper) et azu/vscode-read-aloud-text.
- La fonctionnalité "surlignage synchronisé" existe déjà comme différenciateur perçu (ElevenLabs extension, Markdown Read Aloud) — LLM Voice devra au moins égaler ce comportement.
- Les plaintes recensées (impossible d'arrêter la lecture, lecture de contenu verbeux/intermédiaire au lieu de la réponse finale) pointent directement vers deux exigences produit pour LLM Voice : un contrôle stop/pause fiable, et le fait de ne lire QUE la réponse finale de l'agent (pas les étapes intermédiaires) — ce que LLM Voice prévoit déjà ("lire les réponses finales... à la demande").

### Gaps
- Pas de date de dernière mise à jour fiable trouvée pour Markdown Read Aloud (Piper) et Markdown TTS (le Marketplace n'affiche pas de date lisible dans les extraits récupérés) — à vérifier directement sur la page marketplace si la date exacte est nécessaire.
- **Mimo TTS Markdown Reader** et **Vocalize MD** (trouvées en recherche mais non inspectées) : licence, stack, activité et avis restent inconnus.
- Aucun avis/note (rating) chiffré n'a été trouvé pour la quasi-totalité de ces extensions (0 review sur plusieurs) — impossible de citer un score de satisfaction utilisateur au-delà des plaintes qualitatives trouvées sur le repo VS Code core.

## Que font exactement les fonctionnalités voix natives de VS Code 1.13x / Copilot (`agents.voice.*`, dictée, `ms-vscode.vscode-speech`), quel TTS (cloud vs local), et comment cela contraint le positionnement d'une extension tierce ?

### Takeaway
VS Code a une fonctionnalité **Voice Mode** native et expérimentale (`agents.voice.*`) qui fait à la fois du speech-to-text (dictée) ET lit les réponses de l'agent à voix haute, avec transcription locale par défaut sur desktop (modèle Nemotron on-device) et fallback cloud uniquement sur VS Code for the Web — mais elle ne couvre que les réponses de chat/agent en conversation vocale continue, pas la lecture à la demande de n'importe quel document (Markdown, PDF...), ce qui laisse un espace clair pour LLM Voice sur le cas d'usage "lecture de documents" et "profils de narration".

### Cited Findings
- Réglages officiels documentés dans VS Code : `agents.voice.enabled` (active le Voice Mode mains-libres), `agents.voice.handsFree` ("enables Voice Mode to start listening again after the agent finishes speaking"), `agents.voice.voice` (choix de la voix pour la lecture), `agents.voice.speakResponses` (contrôle si l'agent lit ses réponses à voix haute), `agents.voice.showTranscript` (affiche la transcription dans le champ de saisie), `agents.voice.language` (langue système ou auto-détection) — [VS Code docs — Voice support](https://code.visualstudio.com/docs/configure/accessibility/voice).
- Speech-to-text : **on-device par défaut sur desktop**, modèle local `nemotron-3.5-asr-streaming-0.6b`, fonctionne hors-ligne après le téléchargement initial ; supporté sur Windows (x64/Arm64), macOS (Apple Silicon), Linux (x64/Arm64, glibc ≥ 2.34). **En ligne uniquement sur VS Code for the Web**, qui streame l'audio vers le "Microsoft AI voice service" cloud faute de support on-device dans le navigateur — [VS Code docs — Voice support](https://code.visualstudio.com/docs/configure/accessibility/voice).
- Le moteur TTS précis utilisé par `agents.voice.speakResponses` n'est pas documenté en détail dans la doc officielle consultée — **gap explicite**, voir ci-dessous.
- Le Voice Mode et la dictée intégrée sont explicitement marqués **"expérimental et peut changer ou être retiré"** — [VS Code docs — Voice support](https://code.visualstudio.com/docs/configure/accessibility/voice).
- L'extension **VS Code Speech** (`ms-vscode.vscode-speech`, éditeur Microsoft) comble les lacunes de plateforme où le on-device n'est pas supporté (Mac Intel, systèmes 32-bit, Linux musl) — [Marketplace](https://marketplace.visualstudio.com/items?itemName=ms-vscode.vscode-speech) ; ajoute la dictée on-device et le contrôle vocal de Copilot Chat via le mot d'activation "Hey Code", dans 26 langues, sans clé API ni compte, avec raccourci par défaut Ctrl+Alt+V — [willowvoice.com](https://willowvoice.com/blog/ai-voice-dictation-vs-code), [aquavoice.com](https://aquavoice.com/blog/voice-dictation-for-vs-code).
- La demande explicite d'un TTS automatique pour toutes les réponses de Copilot Chat (issue [microsoft/vscode#266638](https://github.com/microsoft/vscode/issues/266638)) a été **fermée comme "not planned"** par l'équipe VS Code — le besoin existait dans la communauté (accessibilité, multitâche) mais Microsoft l'a orienté vers le Voice Mode conversationnel plutôt qu'un simple toggle "lire toutes les réponses".
- Plaintes utilisateurs sur le TTS natif de Copilot Chat : impossible d'arrêter la lecture même en fermant VS Code, chaque phrase préfixée par le mot "agent" (bruit) ; demande de contrôles supplémentaires (position, navigation, vitesse, lecture du seul texte visible) restée en feature request ouverte ([microsoft/vscode#301431](https://github.com/microsoft/vscode/issues/301431)) ; lecture de contenu intermédiaire verbeux (tool calls, "thinking") plutôt que la réponse finale uniquement ([microsoft/vscode#296720](https://github.com/microsoft/vscode/issues/296720)).

### Inferences
- La stratégie de Microsoft est clairement "conversation vocale intégrée à l'agent Copilot", pas "lecteur universel de documents" : LLM Voice n'est donc pas en concurrence frontale sur son cas d'usage principal (lire du Markdown/PDF/DOCX à la demande, avec des profils de narration réécrits par LLM), mais devra coexister proprement avec `agents.voice.speakResponses` si l'utilisateur a les deux activés (risque de double lecture / conflit UX à anticiper).
- Le choix de Microsoft de garder le on-device par défaut sur desktop confirme que le "local-first" est un standard attendu par les utilisateurs VS Code sur ce type de fonctionnalité, ce qui valide le positionnement local-first de LLM Voice (Piper/Chatterbox/voix système) plutôt qu'un choix uniquement cloud.
- Le fait que #266638 (TTS générique pour tout le chat) ait été fermé "not planned" signifie que Microsoft ne compte probablement pas construire cette fonctionnalité précise en dehors du Voice Mode conversationnel — c'est un boulevard produit pour une extension tierce ciblant justement "lire la réponse finale à la demande, sans mode conversation mains-libres".

### Gaps
- Le moteur TTS exact utilisé côté sortie audio par `agents.voice.speakResponses` (nom du modèle, local ou cloud, langues supportées) n'a pas été trouvé dans la documentation officielle consultée — à re-vérifier via les notes de version VS Code 1.13x (`code.visualstudio.com/updates/v1_137` a été identifié en recherche mais pas explicitement récupéré/confirmé pour ce point précis).
- Impossible de confirmer si `agents.voice` couvre aussi Copilot Chat "classique" (non-agent) ou seulement le nouveau mode Agents/Agent window — la doc parle d'"agents" et de "Agents window" sans clarifier totalement le périmètre exact par rapport à l'ancien Copilot Chat.

## Quels projets permettent d'écouter les réponses de Claude Code / Copilot / Cursor en TTS, et comment capturent-ils la réponse (hooks, transcripts, API) ?

### Takeaway
L'écosystème "écouter son agent de code" est déjà dense côté Claude Code (au moins 8 projets identifiés, tous en 2025-2026, tous MIT, tous petits en traction sauf VoiceMode qui a une vraie communauté), avec deux mécanismes de capture dominants — le **hook `Stop`** de Claude Code (lecture après coup) et le **relais/proxy de flux de tokens** (lecture en streaming, phrase par phrase) — ce dernier étant la référence architecturale directe pour la fonctionnalité future de LLM Voice "écoute en direct d'une réponse LLM en streaming".

### Cited Findings
- **VoiceMode** (mbailey) — [github.com/mbailey/voicemode](https://github.com/mbailey/voicemode) — Licence MIT — Python 3.10-3.14 — **1,4k stars, 195 forks, 2 149 commits**, développement actif. Le projet le plus mature/populaire de la catégorie. Serveur **MCP** compatible Claude Code ; STT via **Whisper.cpp local** (ou API OpenAI en fallback) et TTS via **Kokoro local** (ou fallback OpenAI TTS) ; conversation vocale naturelle mains-libres. Multi-plateforme : Linux, macOS, Windows (natif/WSL), NixOS. C'est la référence la plus proche d'une future fonctionnalité "conversation vocale avec des modèles locaux (Ollama)" pour LLM Voice, bien que VoiceMode cible Claude Code/API plutôt qu'Ollama spécifiquement — **à vérifier si Ollama est supporté** (non confirmé dans la lecture).
- **Claude Read Aloud** (MichaelPGifford) — [github.com/MichaelPGifford/claude-read-aloud](https://github.com/MichaelPGifford/claude-read-aloud) — Licence MIT — **10 stars**, 8 commits. C'est le concurrent le plus proche conceptuellement de LLM Voice côté "lire du Claude Code" : combine un **plugin Claude Code** + une **extension VS Code** avec bouton haut-parleur dans le chat. Capture la réponse en lisant directement **le fichier de transcript de session** (chemin fourni via hooks), pas d'API de scraping fragile. TTS : voix système (macOS `say`, Linux `speech-dispatcher`, Windows SAPI), **Kokoro local** (54 voix, ~340 Mo), ou APIs payantes (Speechify ~$10/M caractères, ElevenLabs ~$5/mois, OpenAI ~$15/M caractères), ou moteurs personnalisés en ligne de commande (Piper, etc.). **Défauts** : réponses tronquées à 12 000 caractères, les blocs de code sont annoncés comme "code omis" (pas lus), lecture auto désactivée par défaut ; l'intégration bouton-dans-le-chat repose sur un **patch local des fichiers de l'extension Claude Code** ("userscript-style local mod", avec sauvegarde/restauration automatique) — une approche fragile qui peut casser à chaque mise à jour de Claude Code.
- **Claude Voice** (cris-m) — [github.com/cris-m/claude_voice](https://github.com/cris-m/claude_voice) — Licence MIT — **4 stars**, 9 commits, Python 3.11+ (3.12+ pour Kokoro), requiert Claude Code ≥1.0.33. Capture via **plusieurs hooks Claude Code** : `SessionStart`, `InstructionsLoaded` (injecte des instructions de résumé TTS au modèle), `Notification`, `PreToolUse`/`PostToolUse` sur Bash (annonce la fin des commandes), et `Stop` (extrait le résumé final à lire). TTS : **Kokoro** (ONNX, ~100 Mo), **Chatterbox** (avec clonage de voix, ~1 Go), **MLX-Audio** (Apple Silicon only, ~1,4 Go). Multi-OS annoncé (macOS/Windows/Linux) mais MLX-Audio réservé à macOS Apple Silicon.
- **Claude Code TTS** (ybouhjira) — [github.com/ybouhjira/claude-code-tts](https://github.com/ybouhjira/claude-code-tts) — Licence MIT — **21 stars, 14 forks** — écrit en **Go**, packagé comme plugin **MCP**. Hook `Stop` qui lit automatiquement la première phrase de chaque réponse Claude, sans configuration. TTS via **API OpenAI (`tts-1`)**, ~$0,015/1000 caractères — donc payant, dépendance cloud. Pool de workers concurrents, lecture protégée par mutex pour éviter le chevauchement audio, cross-plateforme (afplay/mpv/ffplay/mpg123/PowerShell). Limite de 4 096 caractères par requête, file d'attente de 50 jobs.
- **Duck Talk** (dhuynh95) — [github.com/dhuynh95/duck_talk](https://github.com/dhuynh95/duck_talk) — Licence MIT — **24 stars, 1 fork, 341 commits**, CI/CD actif — c'est la **référence architecture directe** pour "écoute en direct d'une réponse LLM en streaming" visée par LLM Voice : un relais Mac (`server.ts`/`session.ts`, TypeScript côté serveur, SwiftUI côté app iOS) intercepte les **tokens bruts en sortie de Claude Code** et les envoie immédiatement à **Google Gemini TTS**, avec lecture phrase par phrase au fur et à mesure de la génération (latence ajoutée ~1 ms par le relais). STT également via Google Gemini Live. Nécessite Node 22+, clé API Gemini (offre gratuite disponible). **Limite notée par les auteurs eux-mêmes** : la "boucle de calibration audio" d'une version web antérieure n'a jamais été portée à l'architecture actuelle.
- Autres projets identifiés mais non inspectés en détail (voir Gaps) : **backtalk** (jaredrhod, "hearing and voice run on free local models, no API keys"), **claude-call** (caiovicentino, Whisper local + edge-tts, sans clé API), **JARVIS** (ethanplusai, assistant vocal macOS), **claude-code-voice-skill** (abracadabra50, parler à Claude par téléphone), **voice-shell** (ykuwai, reconnaissance vocale navigateur ou on-device Whisper), **claude-voice** (jvosloo, push-to-talk Whisper + TTS neural Piper, macOS).
- Côté Claude Code core : une demande d'accessibilité native "Built-in option to speak Claude's responses aloud" est ouverte sur le repo officiel — [anthropics/claude-code#58429](https://github.com/anthropics/claude-code/issues/58429) — confirmant que ce n'est **pas encore une fonctionnalité native** d'Anthropic, laissant le champ aux plugins tiers.
- Côté Cursor : **Voice Mode natif** ajouté dans Cursor 2.0 (29 octobre 2025) — speech-to-text intégré pour contrôler l'Agent (raccourci Ctrl+M ou Cmd+Shift+Space), mais **c'est uniquement de la dictée (entrée), pas de lecture à voix haute des réponses** ; limites : pas de mot d'activation, pas d'édition vocale, pas de caractères spéciaux, ne fonctionne pas dans l'éditeur/Cmd+K/terminal — [willowvoice.com](https://willowvoice.com/blog/best-voice-input-tools-cursor-ai-editor), [aquavoice.com](https://aquavoice.com/blog/voice-coding-cursor-claude-code).
- Côté aider : la commande **`/voice`** transcrit la voix en texte dans le chat aider (entrée uniquement, pas de lecture de sortie), via **PortAudio** ; aucune fonctionnalité TTS de sortie native trouvée dans aider lui-même — [aider.chat/docs/usage/voice.html](https://aider.chat/docs/usage/voice.html). Le projet tiers **colossus** (richardanaya) ajoute une couche voix temps réel autour d'aider avec un paramètre `--voice` proposant des voix façon OpenAI (alloy, ash, coral, echo, fable, onyx, nova, sage, shimmer) — [github.com/richardanaya/colossus](https://github.com/richardanaya/colossus) — non inspecté en détail (licence/stars inconnus).

### Inferences
- Deux architectures de capture de la réponse coexistent : **post-hoc via hook `Stop` + lecture du transcript de session** (majorité des projets Claude Code — simple, robuste, mais latence = attente de la fin complète de la réponse) vs **interception du flux de tokens en direct** (Duck Talk seul exemple clair trouvé — plus complexe, mais c'est le seul chemin vers la fonctionnalité "live streaming" visée par LLM Voice). LLM Voice devra probablement commencer par le pattern hook/transcript (comme la version actuelle "lire les réponses finales à la demande") avant d'investir dans un relais de streaming façon Duck Talk.
- Le patch local des fichiers d'extension Claude Code par Claude Read Aloud ("userscript-style") est un pattern à éviter pour LLM Voice : il est fragile aux mises à jour de l'outil ciblé, contrairement à une lecture de fichier de transcript stable ou un hook officiel documenté.
- Cursor et aider n'ont **aucune fonctionnalité de lecture de réponse à voix haute native** — l'input vocal (dictée) y est bien plus mature que l'output vocal. C'est un angle mort confirmé où un outil comme LLM Voice (ou une extension dédiée) pourrait apporter de la valeur si son périmètre s'étendait un jour au-delà de Claude Code/Copilot.
- La plupart de ces plugins Claude Code sont mono-mainteneur, très jeunes (quelques commits à quelques centaines), et à très faible traction (4 à 24 stars) à l'exception de VoiceMode — le segment "TTS pour Claude Code" est donc un marché de niche encore expérimental, pas dominé par un acteur installé, ce qui recoupe le constat fait pour les extensions VS Code.

### Gaps
- Support explicite d'**Ollama** (modèles locaux) non confirmé pour VoiceMode ni pour aucun des autres projets cités — c'est une fonctionnalité future annoncée par LLM Voice ("conversation vocale avec des modèles locaux via Ollama") pour laquelle aucun équivalent direct n'a été trouvé et confirmé dans cette recherche ; à creuser spécifiquement si cette fonctionnalité devient prioritaire.
- Licence, stars et activité de **backtalk**, **claude-call**, **JARVIS**, **claude-code-voice-skill**, **voice-shell**, **claude-voice (jvosloo)** et **colossus** n'ont pas été vérifiées (seuls les titres/descriptions issus des résultats de recherche ont été utilisés) — à confirmer avant de les citer comme sources fiables dans le rapport final.
- Aucune fonctionnalité TTS native pour Copilot Chat en dehors de VS Code Agents/Voice Mode n'a été trouvée séparément (GitHub Copilot lui-même, hors VS Code, n'a pas été investigué spécifiquement — p.ex. Copilot dans JetBrains/Neovim).

## Quelles applications desktop open-source de lecture à voix haute universelle / assistants vocaux locaux existent, et lesquelles pourraient servir de référence UX ou architecture ?

### Takeaway
Deux références solides et actives existent pour l'architecture "lecture locale universelle" : **Speech Note / dsnote** (Linux, Qt, MPL-2.0, 1,7k stars, très riche en moteurs TTS/STT mais lourd à installer) et **PiperRead** (Linux Wayland/X11, MIT, plus léger mais confidentiel avec 0 star) — toutes deux confirment le pattern "process TTS externe + player audio système", et Speech Note en particulier est une bonne référence pour le multi-moteur et le multilingue, tandis que PiperRead est une meilleure référence pour la simplicité et la latence.

### Cited Findings
- **Speech Note (dsnote)** (mkiol) — [github.com/mkiol/dsnote](https://github.com/mkiol/dsnote) — Licence **MPL-2.0** — **1,7k stars, 73 forks, 27 watchers, 1 667 commits**, 147 issues ouvertes (développement actif). Application desktop **Qt** pour Linux (distribution principale via Flatpak/Flathub, packages Arch/openSUSE/RHEL/Fedora) et Sailfish OS. Prise de notes, lecture et traduction avec **STT offline** (Coqui STT, Vosk, whisper.cpp), **TTS offline** (espeak-ng, MBROLA, Piper, Coqui TTS, RHVoice, Mimic3, Kokoro, Parler-TTS, F5-TTS, S.A.M. — 11+ moteurs), et **traduction machine** (Bergamot Translator) — tout 100% local/offline. Fonctionnalité notable : **lecture de sous-titres synchronisée avec timestamps** (ajustement de vitesse pour matcher la durée du sous-titre) — pattern transposable au "surlignage synchronisé" de LLM Voice. Raccourcis clavier globaux, insertion de texte dans la fenêtre active, intégration ligne de commande. **Défaut majeur** : poids d'installation très lourd (Flatpak de base 3,6 Go décompressé, add-ons GPU 9 à 55 Go) ; une variante "tiny" existe (170 Mo) pour un usage basique seulement.
- **PiperRead** (RonanDavalan) — [github.com/RonanDavalan/PiperRead](https://github.com/RonanDavalan/PiperRead) — Licence MIT — **0 star**, 59 commits. Solution légère pour Linux (Wayland et X11, détection automatique du protocole d'affichage), avec une interface Windows plus limitée (presse-papiers uniquement, pas de sélection souris). Lit à voix haute le texte sélectionné à la souris ou copié dans le presse-papiers via **Piper TTS local** (appelé comme process externe, pas redistribué), intégration ALSA, 100% offline. **Markdown-aware** : retire le balisage Markdown avant synthèse. Performances : ~1,3 s de latence au lancement (lanceur), 168 ms pour l'interface "résidente" (déjà en mémoire) — donnée utile de référence de latence pour LLM Voice.
- Sourcés en recherche mais non approfondis : **Read Text Extension + Piper TTS** (intégration LibreOffice/Piper), listing SourceForge "Best Open Source Linux Text to Speech Software 2026" (agrégateur, pas une source primaire) — voir Gaps.
- Aucun assistant vocal desktop "conversation avec un LLM local" généraliste (hors écosystème Claude Code, cf. section précédente) n'a été identifié dans cette partie de la recherche — les résultats sur ce type de requête ont surtout renvoyé vers des outils de lecture de texte/dictée, pas vers des assistants vocaux conversationnels génériques type "Rasa"/"Mycroft".

### Inferences
- Le compromis "richesse de moteurs vs poids d'installation" observé chez Speech Note (11+ moteurs mais 3,6+ Go) est un contre-exemple direct à éviter pour LLM Voice si la promesse est la légèreté ; PiperRead (mono-moteur, installation minimale, latence <200 ms en mode résident) est la référence à suivre pour l'expérience "lecture instantanée".
- La fonctionnalité de lecture de sous-titres synchronisés par timestamp de Speech Note est probablement le pattern le plus proche déjà existant du "surlignage synchronisé" que LLM Voice vise pour les documents — à étudier en détail si LLM Voice veut industrialiser cette fonctionnalité au-delà du markdown simple.
- Le marché des assistants vocaux desktop généralistes anciens (Mycroft, etc.) semble absent des résultats récents 2025-2026 pour ce type de requête, ce qui suggère soit un déclin de cette catégorie soit une recherche à recadrer avec des requêtes plus spécifiques (nom de projets connus) plutôt que des mots-clés génériques — voir Gaps.
- Aucun des deux projets desktop trouvés ne cible Windows/macOS de façon égale à Linux (Speech Note a des builds Linux/Sailfish, PiperRead a un "Windows interface-only version" limité) — cela recoupe le positionnement "Linux-first" demandé pour cette recherche mais signale aussi que le marché desktop TTS open-source est structurellement Linux-centrique, contrairement à VS Code où les extensions ciblent nativement les 3 OS.

### Gaps
- Projets historiques d'assistants vocaux open-source généralistes (Mycroft AI, Rhasspy en tant que plateforme complète au-delà du moteur Piper, Home Assistant Voice) n'ont pas été recherchés spécifiquement dans cette session — recommandé si le rapport final doit couvrir la catégorie "assistant vocal domestique/desktop" de façon plus large.
- Aucune date de dernier commit précise n'a été confirmée pour PiperRead (0 star rend le signal de traction faible mais l'activité récente n'a pas pu être datée avec certitude).
- Le support du français n'a pas pu être vérifié précisément pour Speech Note ni PiperRead au-delà de la mention générale "wide range of languages" — à vérifier directement sur les pages de langues supportées si le critère francophone est décisif pour une comparaison finale.
- Aucune application desktop citée ne fait de "réécriture par LLM" (profils de narration) avant lecture — cette fonctionnalité, centrale dans le positionnement de LLM Voice, ne semble avoir d'équivalent que côté extensions VS Code (Markdown TTS: Read Aloud & AI Narration) et pas côté applications desktop pures.
