# Local (on-device) TTS engines/servers for a Node.js/TypeScript app (VS Code extension + local daemon), French quality focus — as of 2026-09

## Comparison table: engine-by-engine specs

### Takeaway
No single engine satisfies every requirement. For the "no Docker, no Python" default path, the realistic options are **Piper** (native binary or `onnxruntime`-loaded model), **Kokoro** (via `kokoro-js`/`onnxruntime-node`/`onnxruntime-web`, WASM or native), and **sherpa-onnx** (prebuilt N-API addon, ships VITS/Matcha/Kokoro/Supertonic models). Everything GPU-heavy and "SOTA quality" (XTTS-v2, Chatterbox, F5-TTS, Fish Speech/OpenAudio, CosyVoice, Zonos, Dia, Orpheus) is Python/PyTorch-based and needs a sidecar process (Docker or a Python venv) to reach Node — none of them ship official Node bindings or ONNX-runtime-node packages.

### Inferences
- The project's "no Docker, no Python" default path realistically narrows to three families: **Piper** (binary or `piper-tts` pip package used only as an optional advanced install), **Kokoro via `kokoro-js`/`onnxruntime-node`** (pure JS/ONNX, best fit for an in-process Node daemon), and **sherpa-onnx's Node N-API addon** (also pure native/ONNX, and it can load Kokoro, VITS/Piper, and Supertonic ONNX models through one API) — making sherpa-onnx a strong "one integration, many models" choice for the VS Code extension's daemon.
- For French quality specifically, community signals consistently rank **Kokoro** and **Piper's `tom`/`siwis` voices** as the most usable, CPU-friendly, no-GPU options; everything qualitatively "better" (XTTS-v2, Chatterbox Multilingual, CosyVoice3, F5-TTS, Fish/OpenAudio, Zonos) trades that for a GPU dependency and a Python/Docker sidecar.
- **Kyutai TTS** stands out as the only frontier model explicitly co-designed for French *and* true low-latency streaming (~220ms), making it the best target for a future "premium streaming" tier if a Python/Docker sidecar is acceptable — but its licence and Node-integration path were not confirmed in this pass.
- Given the dev machine's AMD RDNA4/ROCm GPU, **Chatterbox-TTS-Server** is notable as one of the few community servers to explicitly document ROCm support end-to-end, alongside CUDA and CPU.
- No OpenAI-compatible local server found in this research explicitly documents honoring a per-request `language` parameter as OpenAI's API defines it; all of them (Kokoro-FastAPI, OpenedAI-Speech, Speaches) instead select language implicitly through **voice** or **model** selection. This should be treated as a design constraint if the app wants to pass French text with a generic voice.

### Gaps
- Kyutai TTS's exact code/weights licence, official Node-integration path, and CPU viability were not confirmed — needs a direct read of the repo's `LICENSE` file and its Rust/Python inference options.
- No independent (Reddit/HN/forum) community quality thread was found specifically for MeloTTS-French, Fish Speech/OpenAudio French output, Zonos French output, or CosyVoice2-EU/CosyVoice3 French output — the table's French-quality notes for those rely on vendor-provided descriptions only, not third-party listening reports.
- Supertonic's exact licence terms ("respective licenses" of code vs. weights) and whether French is among its supported languages were not confirmed from primary sources in this pass.
- No explicit ROCm compatibility data was found for onnxruntime-node itself (only that ONNX Runtime's server-side ROCm execution provider was removed starting v1.23 in favor of MIGraphX) — this matters directly for the dev machine's AMD RDNA4 GPU and should be verified against the current onnxruntime-node release before assuming any GPU acceleration path works there; CPU execution provider remains the safe default.
- Direct, quantitative TTFA/streaming benchmarks were not found for Fish Speech/OpenAudio, Zonos, Dia, or Supertonic — flagged inline in the table above.

## Which engines run without Docker and without a Python installation on the user's machine (native binary or ONNX loaded from Node)?

### Takeaway
Three engine families meet this constraint cleanly: **Piper** (prebuilt native binaries for Linux/Windows, spawned as a subprocess, no Python needed if using the binary release rather than the pip package), **Kokoro** (via the `kokoro-js` npm package running on `onnxruntime-node`/`onnxruntime-web`, entirely in-process JS/WASM), and **sherpa-onnx** (prebuilt platform-specific N-API addons on npm, natively loading VITS/Piper/Kokoro/Supertonic ONNX models). Everything else in this research (XTTS-v2, Chatterbox, F5-TTS, Fish Speech, Orpheus, Dia, Kyutai, CosyVoice, Zonos) is Python/PyTorch-first and requires a sidecar process (Docker recommended, or a manually managed Python venv) to be reachable from Node.

### Cited Findings
- Legacy Piper ships standalone release artifacts: `piper_linux_x86_64.tar.gz`, `piper_linux_aarch64.tar.gz`, `piper_linux_armv7l.tar.gz`, and `piper_windows_amd64.zip` — no Python required to run these binaries — [rhasspy/piper releases via DeepWiki](https://deepwiki.com/rhasspy/piper/6-building-and-deployment).
- Reported caveats: some Linux release artifacts have contained only x64 builds despite being labeled for other architectures ([GitHub issue #263](https://github.com/rhasspy/piper/issues/263)), and macOS arm64-labeled release binaries were reported to actually be x86_64 ([GitHub issue #284](https://github.com/rhasspy/piper/discussions/379)) — binary releases should be verified per-platform before relying on them.
- The 2025 rewrite (`piper1-gpl`) is documented as a `pip install piper-tts` Python package with a CLI, HTTP server, and C API; no standalone binary release for the rewrite was found in this research — [README](https://github.com/OHF-Voice/piper1-gpl/blob/main/README.md).
- `kokoro-js` is an npm package with device targets `wasm`, `webgpu` (browser), and `cpu` (Node), i.e., it runs directly inside a Node process via `onnxruntime-node`/`onnxruntime-web` with no Python or Docker — [HF post by Xenova](https://huggingface.co/posts/Xenova/503648859052804), [npm](https://www.npmjs.com/package/kokoro-js).
- sherpa-onnx publishes prebuilt native Node addons per platform on npm (e.g. `sherpa-onnx-linux-x64`, `sherpa-onnx-darwin-x64`) built with `node-addon-api`, supporting sync/async workers and multi-threading — [nodejs-addon-examples README](https://github.com/k2-fsa/sherpa-onnx/blob/master/nodejs-addon-examples/README.md).
- Supertonic "runs natively via ONNX," which sherpa-onnx has added support for — implying it can also be reached without Python/Docker through the sherpa-onnx Node addon — [supertone-inc/supertonic README](https://github.com/supertone-inc/supertonic).
- espeak-ng (system fallback) is a native binary with multiple Node bindings, including a WASM build (`@echogarden/espeak-ng-emscripten`) requiring no native compilation — [npm search](https://www.npmjs.com/search?q=keywords%3Aespeak).

### Inferences
- For the VS Code extension + local daemon architecture, the lowest-friction default path is **sherpa-onnx's Node addon**, since it is a single dependency that can load Piper-compatible VITS voices, Kokoro, and Supertonic — covering French support and reasonable quality without any Python or Docker requirement.
- Piper's binary releases are a good CPU-only fallback/complement but need per-platform validation given the documented mislabeled-architecture bugs.

### Gaps
- Whether `piper1-gpl` (the 2025 GPL-3.0 rewrite) has since gained a standalone binary release (as opposed to only the `pip` package) was not confirmed.
- Confirmed macOS arm64 (Apple Silicon) native binaries for either Piper or sherpa-onnx were not directly verified in this pass beyond the general npm platform-package listing.

## Which offer native French voices (not English voices cloned) and how do they sound according to community feedback?

### Takeaway
Piper (siwis/upmc/tom/gilles) and Kokoro both ship dedicated, purpose-trained French voices with some direct community commentary; MeloTTS, Chatterbox Multilingual, CosyVoice3/CosyVoice2-EU, Orpheus (French finetune), Kyutai, Zonos, and Fish Speech/OpenAudio all claim native French support but mostly lack independently sourced (non-vendor) quality feedback in what was found.

### Cited Findings
- Piper French voices and feedback: `fr_FR-siwis-medium` is "very slightly more robotic and some words are less well pronounced than with other solutions, but considering the speed advantage, it remains competitive," with "normal speaking voice rhythm" — [quick-tts.com](https://quick-tts.com/voice/fr-fr-siwis-medium/).
- `fr_FR-upmc-medium` has a documented speed problem: "The French Voice TTS - upmc (medium) speak too quickly to be understandable" — [Home Assistant core issue #105819](https://github.com/home-assistant/core/issues/105819).
- Comparative note: "the tom voice is cleaner than the SIWIS-derived voices for long-form prose, though SIWIS is the more academically standard French TTS corpus while Tom's recording is warmer" — [quick-tts.com/blog](https://quick-tts.com/blog/piper-voices-ranked.html).
- Kokoro ships expressive French voicepacks for both European and Canadian French as part of its 54 preset voices across 8 languages, and separately achieved 1st place in the HF TTS Arena for single-speaker quality overall (not French-specific) — [fal.ai](https://fal.ai/models/fal-ai/kokoro/french), [tts.ai](https://tts.ai/voices/kokoro/).
- MeloTTS has a dedicated `MeloTTS-French` checkpoint described (by MyShell, the vendor) as generating "high-quality French speech in real-time on CPU" — [promptlayer.com](https://www.promptlayer.com/models/melotts-french) — no independent listening-test source was found.
- Orpheus has a dedicated French research-release finetune (`canopylabs/3b-fr-ft-research_release`) — [Hugging Face](https://huggingface.co/canopylabs/3b-fr-ft-research_release) — no independent quality feedback found.
- Kyutai TTS 1.6B is explicitly "handling long texts and dialogs in English and French" as a native training target, not a cloned/finetuned add-on — [scalebytech.com](https://scalebytech.com/kyutai-introduces-2b-parameter-streaming-tts-with-220-ms-latency-trained-on-25-m-hours-of-audio).
- CosyVoice2-EU is described by its own authors as a "Europeanized CosyVoice2 for French & German" with "bilingual adaptation" — [GitHub](https://github.com/hi-paris/CosyVoice2-EU) — but the repo shows only ~18 stars and 17 commits, and is tagged "preprint in preparation," a low external-validation signal.
- Chatterbox Multilingual and CosyVoice3 both list French among their supported languages (20-23 and 9 languages respectively) without French-specific quality detail found — [resemble.ai](https://www.resemble.ai/learn/models/chatterbox-multilingual), [medium.com](https://ai-engineering-trend.medium.com/alibaba-open-sources-cosyvoice-3-a-new-benchmark-in-0-5b-parameter-speech-synthesis-7ddbb8e9ec22).
- Dia (Nari Labs) explicitly does **not** support French: "only supports English generation at the moment" — [MarkTechPost](https://www.marktechpost.com/2025/04/22/open-source-tts-reaches-new-heights-nari-labs-releases-dia-a-1-6b-parameter-model-for-real-time-voice-cloning-and-expressive-speech-synthesis-on-consumer-device/).

### Inferences
- Among engines with actual third-party (non-vendor) commentary, **Piper's `tom` and `siwis` voices** and **Kokoro's French voicepacks** are the safest starting bets for a default, no-GPU French voice; both have known minor quirks (Piper `upmc` speed bug; general "slightly robotic" character noted for Piper overall) rather than being unvetted.
- The larger, GPU-hungry multilingual models (Chatterbox Multilingual, CosyVoice3, Fish/OpenAudio, Zonos) likely sound more natural in French given their scale and training data breadth, but this project could not verify that claim with independent listening reports — it should be treated as an assumption to validate empirically (e.g., via the HF TTS Arena or Artificial Analysis Speech Arena, which are blind-preference benchmarks) rather than fact.

### Gaps
- No independent, dated community (Reddit/HN) thread specifically comparing French output across these models was found; the TTS Arena leaderboards found in this research report overall Elo (not French-specific breakdowns) — see the streaming/OpenAI sections below for what was found on those leaderboards.
- CosyVoice2-EU's low commit/star count suggests it may be an academic prototype rather than production-ready; this was inferred, not confirmed by an explicit maturity statement from the authors.

## Which support true streaming synthesis (audio before the full text is synthesized) for live listening of an LLM answer?

### Takeaway
True chunked/incremental streaming (audio available before the full text finishes synthesizing) is confirmed for **sherpa-onnx** (callback-based sample generation), **Kokoro-FastAPI** (with measured TTFA numbers), **XTTS-v2** (via `inference_stream()`, though GPU-dependent for low latency), **Kyutai TTS** (purpose-built "Delayed Streams Modeling," lowest confirmed absolute latency at ~220ms), **Orpheus** (~200ms, ~100ms with input streaming), and **CosyVoice2-EU/CosyVoice3** (explicit streaming mode, ~150ms first-packet claim for CosyVoice3). Piper, MeloTTS, and Dia are not architected as chunked streamers (they synthesize in one pass, though the pass itself is fast).

### Cited Findings
- sherpa-onnx's `OfflineTts` API supports "generate audio while receiving partial sample chunks through callback," and its React Native wrapper documents this as "lower time-to-first-byte and immediate playback while synthesis continues" — [DeepWiki](https://deepwiki.com/k2-fsa/sherpa-onnx/3.2-text-to-speech-(tts)), [mintlify.wiki](https://mintlify.wiki/xdcobra/react-native-sherpa-onnx/features/streaming-tts).
- Kokoro-FastAPI streaming benchmarks: "≈300ms (GPU) @ 400" chunk size, "≈3500ms (CPU) @ 200" on older CPUs, "<1s (CPU) @ 200 (Apple M3 Pro)" — [Kokoro-FastAPI README, via WebFetch].
- XTTS-v2 streaming: "total round-trip time to first chunk of as little as 200 milliseconds" claimed in one source, with other sources citing 320ms (RTX 5090) to ~600ms depending on configuration, via an `inference_stream()` generator — [baseten.co](https://www.baseten.co/blog/streaming-real-time-text-to-speech-with-xtts-v2/), [HF discussion #59](https://huggingface.co/coqui/XTTS-v2/discussions/59).
- Kyutai TTS 1.6B: "begins generating speech after only a few input words, keeping latency around 200-220 ms," and "on a single NVIDIA L40 GPU, it can support thirty-two simultaneous streams under 350 ms of end-to-end delay" — [scalebytech.com](https://scalebytech.com/kyutai-introduces-2b-parameter-streaming-tts-with-220-ms-latency-trained-on-25-m-hours-of-audio).
- Orpheus TTS: "~200ms streaming latency for realtime applications, reducible to ~100ms with input streaming" — [hackster.io](https://www.hackster.io/news/canopy-labs-releases-orpheus-a-permissively-licensed-llm-for-convincing-text-to-speech-afc64416767d).
- CosyVoice3: "first-packet synthesis latency as low as 150ms"; CosyVoice2-EU: "streaming and non-streaming synthesis" explicitly supported — [medium.com](https://ai-engineering-trend.medium.com/alibaba-open-sources-cosyvoice-3-a-new-benchmark-in-0-5b-parameter-speech-synthesis-7ddbb8e9ec22), [GitHub](https://github.com/hi-paris/CosyVoice2-EU).
- `kokoro-js` v1.2.0+ added streaming specifically to handle long text inputs beyond the model's max context — [HF post](https://huggingface.co/posts/Xenova/503648859052804).
- Piper/MeloTTS/Dia: no streaming/chunked-callback API was found documented for any of these three in this research; Piper and MeloTTS instead compensate with very low total (non-streamed) synthesis latency due to small, fast VITS-class models.

### Inferences
- For "live listening of an LLM answer" (i.e., speak-as-you-generate), the architecturally best-suited engines found are **Kyutai TTS** and **Orpheus** (both purpose-built for token-level low-latency streaming) if a GPU + Python/Docker sidecar is acceptable, and **sherpa-onnx** or **kokoro-js** if the constraint is "no Python/Docker, Node-native."
- Piper's lack of chunked streaming is likely not a practical problem for short-to-medium LLM replies, since its total synthesis time for a sentence is already very low on CPU — but it will not "start speaking" before a full sentence/chunk is handed to it, unlike the token-streaming models.

### Gaps
- No streaming/TTFA benchmark was found for Fish Speech/OpenAudio, Zonos, MeloTTS, Dia, or Supertonic.
- It's unclear from sources found whether Kyutai TTS's low-latency figures are achievable on CPU or only on the cited NVIDIA L40 GPU class hardware.

## Which OpenAI-compatible local servers are mature enough to be the "advanced" tier, and do they honor the `language` parameter?

### Takeaway
Three servers stand out as mature, actively used OpenAI-compatible `/v1/audio/speech` implementations: **Kokoro-FastAPI**, **OpenedAI-Speech** (Piper + XTTS-v2 backends), and **Speaches** (Piper + Kokoro backends, positioned as "Ollama for TTS/STT"); the community **Chatterbox-TTS-Server** and **chatterbox-tts-api** add a fourth option with native ROCm support. None of the sources found describe an explicit standards-compliant `language` request parameter being honored — all of them route language selection through **voice** or **model** choice instead, which the calling application needs to account for.

### Cited Findings
- Kokoro-FastAPI: "provides a Speech endpoint compatible with OpenAI's API specification, allowing use with the official Python client or standard HTTP requests," and documentation "doesn't explicitly detail a `language` parameter in requests—language selection appears tied to voice selection instead" — [Kokoro-FastAPI README, via WebFetch].
- OpenedAI-Speech: "accepts the same request format as OpenAI's `/v1/audio/speech` endpoint, then routes to local models like Piper (fast, low-footprint) or Coqui XTTS-v2 (higher quality, needs ~4 GB VRAM)" — [matatonic/openedai-speech](https://github.com/matatonic/openedai-speech), summarized via search.
- Speaches: "OpenAI API-compatible server supporting streaming transcription, translation, and speech generation, with Speech-to-Text powered by faster-whisper and Text-to-Speech using piper and Kokoro," positioned as aiming "to be Ollama, but for TTS/STT models" — [speaches-ai/speaches](https://github.com/speaches-ai/speaches).
- Chatterbox-TTS-Server (devnen): "flexible API endpoints (incl. OpenAI compatible), predefined voices, voice cloning… Runs accelerated on NVIDIA (CUDA), AMD (ROCm), and CPU" — this is one of the few servers found with **explicit documented AMD ROCm support**, relevant to this project's dev hardware — [GitHub](https://github.com/devnen/Chatterbox-TTS-Server).
- Community `chatterbox-tts-api` (travisvn): "OpenAI-compatible API with FastAPI performance, multilingual support in 22 languages, voice cloning, and Docker containerization" — [GitHub](https://github.com/travisvn/chatterbox-tts-api).
- Other OpenAI-endpoint emulators found but not TTS-model-local in the strict sense: `openai-edge-tts` proxies Microsoft Edge's **online** TTS service (not a local model) — [GitHub](https://github.com/travisvn/openai-edge-tts) — relevant only as a cloud-dependent fallback, not for this project's local-first requirement.
- LocalAI also exposes an OpenAI/ElevenLabs-compatible TTS API as part of a broader local-inference platform — [localai.io](https://localai.io/docs/features/text-to-audio/index.html).

### Inferences
- Given the dev machine's AMD RDNA4/ROCm GPU, **Chatterbox-TTS-Server** is the most directly relevant "advanced tier" candidate among the OpenAI-compatible servers found, since it is the only one in this research explicitly documenting a ROCm code path end-to-end (not just CPU/CUDA).
- Because none of these servers appear to expose a standards-following `language` parameter, the calling Node code will need to maintain its own voice→language mapping table regardless of which backend is chosen.

### Gaps
- No source directly quoting the OpenAI TTS API's own request schema (to confirm whether `language` is even a first-class OpenAI parameter, as opposed to being implied by `voice`) was fetched in this pass — this should be checked against OpenAI's own current API reference if precision on that point matters.
- Maturity signals (contributor count, release cadence, issue-resolution speed) were not directly compared across Kokoro-FastAPI, OpenedAI-Speech, Speaches, and Chatterbox-TTS-Server beyond the commit counts noted in the table.

## Any Rust or Node-native TTS runtimes (sherpa-onnx node addon, onnxruntime-node, candle-based) worth using to embed a model in-process?

### Takeaway
Three concrete in-process options were found: **sherpa-onnx's native Node addon** (most mature, multi-model, prebuilt per-platform), **`kokoro-js`/`onnxruntime-node` directly** (lightweight, Kokoro-specific), and an emerging **Rust `candle`-based crate called `any-tts`** (trait-based API covering Kokoro and several other models, with automatic CPU/CUDA/Metal backend selection) — though `any-tts` does not yet have a confirmed Node/N-API binding.

### Cited Findings
- sherpa-onnx ships a native Node.js addon (`node-addon-api`, C++) with prebuilt platform packages on npm, supporting TTS alongside ASR/VAD/speaker-ID, and recently added Supertonic TTS, ZipVoice TTS, and PocketTTS models — [nodejs-addon-examples README](https://github.com/k2-fsa/sherpa-onnx/blob/master/nodejs-addon-examples/README.md).
- `onnxruntime-node`'s execution-provider support: CUDA EP is available for Node.js bindings generally per ONNX Runtime docs, but **ROCm as a server-side ONNX Runtime execution provider was removed starting release 1.23**, with AMD recommending migration to the **MIGraphX** execution provider instead; DirectML EP is Windows-only — [onnxruntime.ai ROCm EP docs](https://onnxruntime.ai/docs/execution-providers/ROCm-ExecutionProvider.html), [onnxruntime.ai EP list](https://onnxruntime.ai/docs/execution-providers/). This is a direct concern for the project's AMD RDNA4/ROCm dev machine: GPU acceleration via `onnxruntime-node` on that hardware is not confirmed to work out of the box and CPU execution should be the assumed baseline unless MIGraphX support in the Node binding is separately verified.
- `any-tts` is described as "a Rust TTS library built around Candle with one trait-based API for Kokoro, OmniVoice, Qwen3-TTS, VibeVoice, VibeVoice Realtime, and Voxtral," with "automatic runtime preference selection for CPU, CUDA, or Metal," and a "Kokoro-82M TTS support" addition dated 2026-08-06 using "a from-scratch Rust G2P + candle-onnx synthesis pipeline" — [lib.rs/crates/any-tts](https://lib.rs/crates/any-tts), [docs.rs/any-tts](https://docs.rs/any-tts).
- `espeak-rs` provides "Rust bindings for espeak-ng exposed to Node via N-API," specifically to avoid the overhead of spawning a subprocess per phonemization call — [GitHub](https://github.com/SpeechifyInc/espeak-rs) — useful as a phonemizer building block even where it isn't itself a full TTS engine.

### Inferences
- Of the in-process options, **sherpa-onnx remains the most production-ready choice today** for a VS Code extension's local daemon: it is the only one with confirmed prebuilt Node N-API packages, multi-model support (VITS/Piper voices, Kokoro, Supertonic), and an explicit streaming/callback API.
- `any-tts` (candle-based) is a promising but early-stage alternative worth watching; since it's a Rust crate without a confirmed Node binding, using it from the Node daemon today would likely require building a custom N-API wrapper — extra engineering cost not currently justified unless sherpa-onnx proves insufficient.
- The AMD ROCm EP removal from ONNX Runtime (1.23+) means this project should not assume GPU acceleration is available via `onnxruntime-node`/sherpa-onnx on the dev machine's RDNA4 card without separately confirming MIGraphX support in whatever ONNX Runtime build those Node packages bundle; CPU-only should be the safe planning assumption for the ONNX-based path, while ROCm acceleration (if wanted) points toward the Python/PyTorch-based servers that explicitly document ROCm support (e.g., Chatterbox-TTS-Server, Kokoro-FastAPI's "AMD GPU (ROCm, experimental)" Docker image).

### Gaps
- Whether `any-tts` or any other candle-based crate has a maintained Node/N-API/napi-rs binding was not found — this would need direct investigation of the crate's own repository/docs.
- Whether the ONNX Runtime binaries bundled inside `onnxruntime-node` or sherpa-onnx's prebuilt npm packages include any AMD GPU execution provider (ROCm or MIGraphX) at all was not confirmed either way — the safest assumption, absent that confirmation, is CPU-only for the Node/ONNX path on this machine.
