## 7. Where the inbox stores entries — fields available to a decision, and persistence

| path:line | what it does | availability to the decision provider |
|---|---|---|
| `src/core/inbox.ts:21-30` (`InboxMessage`) | On-disk shape: `schemaVersion: 1`, `provider: InboxProviderId`, `sessionId`, `capturedAt` (epoch ms), `cwd?`, `title?`, `message: string`. | `message` (the full text), `provider` (`"claude-code"`/`"codex"`/etc.), `capturedAt`, `cwd`, `title` are all available as decision inputs; **no length/token-count field** is stored — the decision provider would compute `message.length`/token estimate itself from the string already in memory. |

No field for a persisted decision. |
| `src/core/inbox.schema.ts:41-49` (`InboxMessageSchema`) | Zod schema mirroring `InboxMessage` exactly, `z.object({ schemaVersion: z.literal(1), provider, sessionId, capturedAt, cwd?, title?, message })` — no `additionalFields`/passthrough. | A "decided profile" **cannot** be written back into the inbox JSON file itself: (a) the file is produced by an *external* process (Claude Code's hook, ADR-003 "the directory is the source of truth"; comment at `src/claude/InboxRepository.ts:7-9`: "the directory is written to by external, untrusted processes"), extension code never rewrites these files; (b) even if it did, `InboxMessageSchema` has no slot for it and is the single validation gate (`InboxRepository.scan`, `:106-188`, `InboxMessageSchema.safeParse(parsedJson)` at `:162`) — an extra field would just be dropped by Zod's default (non-passthrough) parsing, not preserved. |
| `src/claude/ReadStateStore.ts:1-38` (whole file) | Exactly the precedent for "extra per-entry state, kept *outside* the immutable inbox file": `ReadStateStore` interface (`isRead`/`setRead`/`cleanup`, `:8-13`), `InMemoryReadStateStore` default implementation (`:15-38`). Backed in production by `GlobalStateReadStore` (`src/claude/GlobalStateReadStore.ts`, not fully read here but named in `InboxRepository`'s header comment) on top of `context.globalState`, keyed by `entry.id`. | This is the concrete, already-built pattern for persisting a "decided profile per entry" (e.g. `DecisionStateStore.get(id): string | undefined` / `.set(id, profileId)`), side-car to the immutable file, exactly like read/unread state — `InboxRepository.scan()` already merges `readState.isRead(id)` into every `InboxEntry` at `:177`, so merging a `decidedProfileId` the same way is a direct structural analog, not a new mechanism. |
| `src/claude/InboxRepository.ts:106-188` (`scan`) | Builds every `InboxEntry` fresh on each call (no caching beyond the file itself + `ReadStateStore`), sorted by `capturedAt` desc (`:184`). | Because entries are rebuilt on every `scan()`/`list()` call, a decision computed once and persisted via a `ReadStateStore`-like side-car is the only way to avoid re-invoking Ollama on every inbox refresh/render — recomputing per-render would call the decision provider far more often than once-per-actual-read. |
